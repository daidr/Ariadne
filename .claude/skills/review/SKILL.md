# Ariadne PR 评审

评审的目标是：合入前拦住会让 Ariadne 偏离设计哲学、违反硬约束或出错的改动，并且只报告经过验证、值得作者花时间的问题。

先读 [docs/philosophy.md](../../../docs/philosophy.md) 和 [docs/architecture.md](../../../docs/architecture.md)，再读 [postmortems.md](./postmortems.md) 里的历史教训。本文的检查项都以它们为依据；三者冲突时以设计哲学为准，并在报告里指出冲突。

## 原则

- **整体看 PR。** Ariadne 刻意用少量、大粒度的 PR。评审时先建立全局视野：这个 PR 要达成什么、改了哪些层、各部分怎么串起来，再逐文件看。不要因为 PR 大就要求拆分；只有当 PR 混入了与目标无关的改动时才建议拆出去。
- **反过来也要指出过碎。** 如果一个功能被拆成了多个 PR、这个 PR 单独看缺少上下文（例如只有接口没有使用方、只有后端没有界面），在报告里说明，并建议后续把相关工作合在一个 PR 里。
- **只报真问题。** 每条问题都要给出具体的触发条件和错误结果（输入 / 状态 → 错误的输出 / 崩溃 / 违反的约束）。说不出触发条件的猜测不报；格式、lint 能自动发现的不报。
- **评审不改代码。** 评审讨论串只产出评审结论，修复由实现讨论串完成。
- **不批准、不合并。** 合并由 Dairyn 决定。

## 流程

### 1. 建立全局视野

1. 读 PR 标题、描述和全部提交信息，弄清目标与验收标准。若关联了计划节点，读节点的目标。
2. 读完整 diff（不要只看部分文件）。把改动按层归类：`i18n` / `core` / `plugin-sdk` / `server` / `web` / 文档 / 构建配置。
3. 在本地检出 PR 分支，打开改动涉及的上下游代码，而不只是 diff 里的行。

### 2. 跑检查

在 PR 分支上执行，并在报告里贴出结果（通过 / 失败及失败的关键输出）：

```sh
bun install --frozen-lockfile
bun run check    # 格式、lint、类型检查、测试
bun run build
```

`check` 或 `build` 失败本身就是阻塞问题。命令在本环境跑不了时，如实写明哪一步没跑、为什么。

涉及界面的改动，运行 `bun run dev` 实际打开页面看一遍（亮色、暗色各一次），确认没有报错、布局没有坏。

### 3. 逐项检查

按下面的清单看。前两节是硬约束，违反即阻塞。

#### 硬约束（阻塞）

- **不提及其他库。** 仓库里（代码、注释、文档、配置、依赖、提交信息）不得出现其他 UI 组件库或其他 harness / agent 框架的名字，也不写“参考了某某”之类的说明。检查 diff 新增的依赖和所有新增文字。
- **UI 只用 dou-ui。**
  - 不引入任何其他组件库、图标库或 CSS 框架。
  - dou-ui 已有的组件不手写替代品。
  - dou-ui 缺功能或有 bug 时，正确做法是上报给 Dairyn，而不是绕过去。看到以下迹象要追问是否在绕：用 `:deep()` 或全局选择器覆盖 `.dou-*` 内部样式、`!important`、复制组件内部实现、读写组件私有 DOM 结构、手写本应来自 dou-ui token 的颜色和尺寸。确认是 dou-ui 缺口的，列入报告的“dou-ui 缺口”一节。
  - 主题：整页主题由 `<html>` 上的 `data-dou-theme`（或 `useColorMode()`）提供，不手写 `body` 的背景、文字色、字体 token。
- **只用 Bun。** 不出现 `package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`；脚本里不用 `npm` / `npx` / `node` / `yarn` / `pnpm`；改了依赖就必须同步更新 `bun.lock`；运行时能力优先用 Bun 内置（如 `bun:sqlite`）。依赖版本写确切版本号。
- **提交信息**用中文的 conventional commits（`feat:`、`fix(web):` 等）。
- **i18n 中文优先。**
  - 用户可见的文字不硬编码在 Vue 模板、组件脚本或服务端响应里，一律走 `@ariadne/i18n`。
  - 新增文案先加到 `zh-CN`（它是 `MessageKey` 的来源），并同时补齐 `en`；两边的占位符 `{name}` 一致。
  - 服务端返回 `LocalizedMessage`（key + params），由前端翻译，不在服务端拼好文字。
  - AI 生成内容之外的界面文案，中文措辞自然，不是机翻腔。

#### 架构

- **依赖方向**：`i18n` ← `core` ← `plugin-sdk` ← `server`；`web` 只依赖 `i18n` 和 `core` 导出的**类型**（`import type`）。出现反向依赖或 `web` 引入 `core` 的运行时代码即阻塞。
- **事件溯源**：所有状态变化都是追加一条事件，投影在同一个事务里更新。看到直接写投影表、绕过 `EventStore` 改状态、把状态只存在内存里，都是问题。新事件类型要考虑：旧数据库重放时能否正确投影、投影表结构变化如何迁移。
- **可回放**：模型的每一次输入都应能从事件日志重建。不要把只存在于进程内存的内容喂给模型。
- **崩溃恢复**：进行中的工作重启后能续上；悬空的工具调用标记为中断，绝不重放有副作用的调用。
- **本地服务安全**：只监听 `127.0.0.1`；新增的每个路由（包括事件流、静态资源以外的接口）都经过 token 鉴权。
- **插件边界**：上层只依赖能力（`workspace`、`repo`、`tracker` 等），不依赖具体 provider；插件接口的改动要同步 `plugin-sdk` 的类型。
- **概念**：新增概念、设置项或开关时，确认它不能作为现有概念的属性、不能写成提示词、不能用默认值代替（设计哲学第 5 条）。不能的话要在 PR 描述里说明理由。

#### 设计哲学

- **可见先于自动**：新的自动行为在界面上有没有对应的可见状态？界面上的数字是否等于它链接的列表长度？健康状态是否不占位置？
- **计划修改留痕**：AI 对计划图的修改是否是带理由的 Revision，可查看差异、可回退？删除节点、改验收标准、改里程碑是否走确认？
- **不发过程消息**：AI 在回应用户、完成总结、遇到阻塞时发消息；长任务中出现用户能看着的东西（比如刚建好的产物）或要开始很久的步骤时，可以发一行提示，产物带链接。逐步进度走待办清单，不发消息。
- **不可撤销操作先问**：推送主分支、删除、对外发消息等是否进入“需要我”；可撤销操作是否直接做且事后可见。
- **打扰是成本**：多个待确认项是否合并成一张卡片；未确认事项是否阻塞了其他工作。

#### 正确性

- 错误路径：异常是否被吞掉；`DomainError` 与 500 的区分；用户输入的校验。
- 模型生成、直接交给 dou-ui 组件渲染的结构（仪表盘 props、白板节点、计划图等）：写入时按组件的类型声明校验，把错误返回给模型；渲染侧一个元素出错不能拖垮整页。评审时用一份类型错的数据实际打开一次页面。
- 并发与异步：竞态、未 await 的 Promise、事件流断线续传时的重复与丢失（按 `seq` 续传）。
- SQLite：事务边界、`strict` 模式下的参数绑定、WAL 下的并发写。
- 类型：没有无理由的 `any`、`as` 强转、`@ts-ignore` / `@ts-expect-error`。
- 前端：响应式丢失（解构 props / reactive）、未清理的监听与定时器、列表 `key` 稳定。
- 安全：工作区文件路径不能逃出工作区；执行命令不拼接未转义的输入；令牌和密钥不写进日志或事件。

#### 测试

- 新行为有 Vitest 测试覆盖，尤其是投影、阶段推导、鉴权和 i18n。
- 没有被跳过、被删除或被放宽断言来“变绿”的测试。
- 测试断言的是行为，而不是复述实现。

### 4. 验证每一条发现

报告前对每条问题再确认一次：能否指出具体文件和行号、能否描述触发它的输入或状态、它是否真的会发生（例如调用方是否已经保证了前置条件）。确认不了的删掉，或明确标注为“待确认”并写出需要谁确认什么。

### 5. 输出报告

报告用中文，结构如下：

```markdown
## 结论

可以合并 / 修改后合并 / 需要返工 —— 一句话理由

## 阻塞问题

1. `path/to/file.ts:42` 问题描述。触发：……→ 结果：……。建议：……

## 非阻塞建议

1. ……

## dou-ui 缺口

（需要上报给 Dairyn 改进 dou-ui 的问题；没有就写“无”）

## PR 粒度

（过碎、混入无关改动等；没有就省略）

## 已验证

- bun run check：通过 / 失败（关键输出）
- bun run build：通过 / 失败
- 界面：已在亮色 / 暗色下打开 …… / 未涉及界面
```

把报告作为一次 GitHub PR review 提交（类型为 comment，不 approve），阻塞问题尽量作为对应行的行内评论；同时在评审讨论串里回复结论和链接，由协调器转给实现讨论串处理。

修复推上来后，只复查修复涉及的部分和原有阻塞问题，不重新做全量评审，除非修复改动很大。

## 复盘：bug 漏过评审之后

只要一个 bug 在评审通过、合入之后才被发现，就做一次复盘，并更新本 skill。

1. **记录**：在 [postmortems.md](./postmortems.md) 末尾追加一条，包含：日期、引入 bug 的 PR、bug 的表现、根因、评审为什么没发现（清单里没有这一项 / 有但没执行 / 没跑相关命令 / 测试没覆盖 / 其他）、本次对 skill 的修改。
2. **改清单**：把教训变成一条**具体、可执行**的检查，加到上面对应的小节里（例如“新增事件类型时，用旧库重放一次验证投影”），而不是“更仔细一点”这类泛泛的话。如果是流程问题（比如没跑某个命令），改“流程”一节。
3. **保持精简**：先看能否合并或改写已有条目，而不是一直往下追加；清单变长时，删掉已经被 lint、类型检查或测试自动覆盖的条目。
4. **随修复一起提交**：skill 的更新和 bug 修复放在同一个 PR 里，不单独开 PR。
