# 设计哲学

Ariadne 是一个自己使用的 AI 协作工具。名字取自给迷宫里的人一团线的阿里阿德涅：AI 可以在迷宫里走得很深，但用户手里始终握着线头，知道它走到了哪、为什么这么走、怎么回来。

所有取舍都以下面两个目标为准：

- **掌控力**：用户随时知道 AI 在做什么、目标是什么、推进到了哪里。
- **低心智负担**：用户不需要自己统筹并行的会话，也不需要翻聊天记录来拼出进度。

## 五条原则

### 1. 可见先于自动

用户在任何时刻都能用一眼回答三个问题：

1. 现在有什么需要我？
2. 整体推进到哪了？
3. 某件事为什么变成现在这样？

做不到可见的自动化不做。健康的状态不占位置，界面上的每个数字都等于它所链接的列表长度。

### 2. 计划是一等公民

大需求先变成一张计划图，thread 是图上节点的执行者，而不是反过来从聊天里推断进度。AI 修改计划图必须留痕：每次修改都是一个带理由的修订，用户能看到改了什么、为什么改，并且可以回退。

### 3. 用户只和一个人说话

用户面对的是协调器。并行 thread 的调度、汇总、纠偏都由协调器消化，只把需要用户决定的事推给用户。协调器只在有结果、要决定、卡住时说话，平时的进度只体现在计划图和看板上。

### 4. 一切可回放

所有状态都从只追加的事件日志投影出来。模型看到的每一次输入都能从日志重建；界面只是投影的视图，刷新、断线、重启后看到的完全一致。

### 5. 少概念、少设置

新需求优先成为现有概念的属性，而不是新概念；能写成提示词的行为不做成开关；一个值适合几乎所有情况时，用默认值代替设置。

## 由此而来的约束

- 不可撤销的操作（推送到主分支、删除、对外发消息）一律先问用户；可以撤销的操作直接做，事后可见。
- thread 推送自己的分支、开 PR 属于可以撤销的操作：只动它自己的分支，PR 可以关闭，合并始终由用户决定，PR 和检查状态在界面上随时可见。例外是公开仓库：推上去的内容立即公开、无法收回，所以每个 thread 第一次推送前先问用户。用户关掉的 PR，thread 不自行重开。
- 一次只问一个具体的问题，用结构化的卡片，而不是埋在长段落里。
- 失败如实报告，草稿标明未完成，不为了避免提问而绕过限制。
- AI 只在三种时候发消息：回应用户的消息、完成任务时的总结、遇到阻塞时。实现过程中不发过程消息，现在在做什么、接下来做什么、在等什么，都由一张实时更新的待办清单表达。
- 打扰是成本：同一时段的多个待确认项合并成一张卡片，未确认的事项不阻塞其他工作。
