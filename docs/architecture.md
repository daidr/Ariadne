# 架构

本文描述 Ariadne 的领域概念与分层。设计取舍的依据见 [设计哲学](./philosophy.md)。

## 领域概念

| 概念                    | 定义                                                                                                       | 关键规则                                                                    |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Project 项目            | 工作的范围                                                                                                 | 持有项目来源、计划图、协调器、讨论串、artifacts 和项目记忆                  |
| Context Source 项目来源 | 某个 provider 的一个实例，如“本地目录 ~/code/x”                                                            | 声明自己提供哪些能力（见下文），一个 provider 可以只实现一部分              |
| Coordinator 协调器      | 每个项目一个长期会话，用户的主要对话对象                                                                   | 工具集小：改计划、开 / 停讨论串、给讨论串发消息、向用户要决定；不直接改代码 |
| Thread 讨论串           | 一个执行单元：一个会话 + 一个工作区                                                                        | 可绑定到计划节点；用结构化 Report 上报状态；用户可以直接进入对话            |
| Plan 计划图             | 项目的有向无环图：任务、里程碑、决策节点                                                                   | 每次修改是一个带理由的 Revision，可查看差异、可回退                         |
| Attention 待决定        | 一个等用户回答的界面块：选项、确认或表单                                                                   | 来自协调器、讨论串或系统，出现在提问的消息里，也统一出现在“需要我”列表      |
| Artifact 产物           | AI 产出的可归档产物：文档、画板、仪表盘                                                                    | 属于项目，可关联计划节点；每次修改是一个新版本；类型由插件注册              |
| Todo 待办清单           | 协调器和每个讨论串各一张，按步骤顺序显示在各自的对话里：做完的打勾，正在做、在等什么、接下来做什么一目了然 | 由 AI 用工具更新，每次更新是一个事件；取代过程消息                          |
| Event 事件              | 只追加的事实                                                                                               | 所有状态都由事件投影而来                                                    |

### 讨论串阶段

讨论串的阶段按“它在等谁”划分，从上到下第一条匹配的生效：

| 阶段      | 条件                                               | 是否需要用户 |
| --------- | -------------------------------------------------- | ------------ |
| `answer`  | 有未回答的 Attention                               | 是           |
| `stopped` | 被协调器或用户暂停，还没有继续                     | 否           |
| `working` | 正在执行一个回合                                   | 否           |
| `queued`  | 有新输入，在等槽位                                 | 否           |
| `blocked` | 上一回合失败（如模型请求出错），等用户重试         | 是           |
| `halted`  | 用户停止了上一回合，之后没有报告（审阅讨论串除外） | 是           |
| `blocked` | PR 的检查连续失败 3 次（见“仓库、PR 与 CI”）       | 是           |
| `working` | 最近的 Report 是 `ready`，还在交付前审阅           | 否           |
| `done`    | 最近的 Report 是 `ready`，之后已合入或已看完       | 否           |
| `review`  | 最近的 Report 是 `ready`                           | 是           |
| `blocked` | 最近的 Report 是 `blocked` 或 `failed`             | 是           |
| `done`    | 最近的 Report 是 `done`                            | 否           |
| `queued`  | 还没有开始过                                       | 否           |
| `idle`    | 最近的 Report 是 `waiting`（本轮结束）             | 否           |
| `silent`  | 上一回合正常结束却没有报告，也没有在等（`wait`）   | 是           |
| `working` | 其他情况：开始过、还没报告，或刚报告 `progress`    | 否           |

一个回合正常结束、讨论串却落在 `silent` 时，自动提醒它一次（`thread.nudged`，讨论串收到 `<report_missing>` 并被唤醒）；提醒后的那一回合还是没报告，就停在 `silent` 交给用户，直到下次报告之前不再提醒。`halted` 和 `silent` 都在“需要我”里，点“继续”再跑一个回合。

“停止”只结束正在跑的这一回合（输入框的按钮：有内容时是发送，输入框为空且在运行时是停止；或在输入框为空时 1.5 秒内连按两次 Esc），“暂停”是让整个讨论串停下来。协调器可以用 `stop_thread` 自己暂停一个讨论串，必须写明原因（如“方向跑偏了”“和另一个讨论串重复”）。界面上没有让用户手动暂停或接管的入口，记在用户名下的暂停只来自删除计划节点；这样暂停的讨论串只有用户能继续，协调器会收到说明，不再指望它。暂停时记一条 `thread.stopped`：正在跑的一回合和它的命令立即被中止，调度器的槽位随之空出；之后新到的消息只排队，不会启动它。讨论串面板顶部显示谁停的、为什么停，用户点“继续”、在讨论串里发消息或回答它的提问都会继续，三者一样记一条 `thread.resumed`；协调器也可以用 `resume_thread` 让自己停下的讨论串继续。继续后讨论串收到一条说明，带着当初停下的原因接着做；由用户继续时协调器也会收到。

`review` 只留给有改动要合并的讨论串：报告 `ready` 时，如果它既没有打开的 PR，分支上也没有基线之外的提交（或者根本没有工作区），这次报告记成 `done`，调研、写报告这类交付不会停在等审阅。只有没提交的改动时，报告被退回，让它先提交。

离开 `review` 有三条路。“改动已合入”指用户在报告之后合并了它的分支（见“查看与合并改动”），或者它的 PR 已被合并：用户审阅完、收下了，就不再留在“需要我”里。用户也可以点“看完了”，不合并就结束这次审阅（比如在别处合并了，或者不要了），记一条 `thread.reviewed`，协调器收到说明但不被唤醒，worktree 不会因此移除。点“还要改”打开讨论串、光标停在输入框里，用户发出消息后讨论串回到工作中。这两个按钮出现在讨论串卡片、“需要我”、讨论串列表和讨论串面板顶部。之后讨论串再报告 `ready`，又回到 `review`。

讨论串做完之后自己归档，不需要用户动手，也没有归档按钮：`done` 的讨论串在改动合入（合并了分支，或 PR 被合并）满一天、这一天里用户没再给它写消息时，或者完成后一周没有任何动静时，`ThreadView.archived` 为真，讨论串列表把它收进最后一组“更早”（默认折叠），输入框的 `@` 菜单不再列它；搜索、计划图节点和对话里的链接照常能打开。用户给它发消息它就回来（投影记 `landed_at` 和 `user_at`：合入之后用户又写过消息、或者它又报告过（那一轮的工作没有合入）的不算归档），直到下次合入满一天或再静一周。刚合入的先留在“已完成”，隔天才收走。归档只是视图上的推算，不写事件；还在等用户的讨论串不管多久都不归档。

未回答的问题排在 `done` 前面：讨论串报告完成时如果还有问题没答，它仍然停在 `answer`，问题也留在“需要我”里，直到用户回答。

“需要我”是服务端算出的一张列表：每个未回答的 Attention 一条，再加上每个处于需要用户阶段、但没有未回答 Attention 的讨论串一条。界面上所有“需要我”的数字都取这张列表的长度，前端不自己推导。

### 轮次与 agent loop

协调器和每个讨论串各有一个会话，会话里的 agent 一个回合一个回合地工作：

- 会话收到新输入（用户的消息、协调器转来的消息、讨论串的汇报、用户对问题的回答）后排队等一个回合。调度器按槽位启动：默认 3 个槽位，另留 1 个只给“回应用户消息”的一回合，用户不用排在后台工作后面。槽位数在“设置 → 模型”里可调，保存后立即生效：正在跑的一回合做完，新的一回合按新的上限启动。每个项目还可以在项目来源的设置里单独限制“这个项目最多同时工作”几个回合（`project.slots.set`），在总数之内再限一层，免得一个项目占满所有槽位；回应用户消息的一回合不受项目上限限制，仍可用留出的槽位。
- 一个回合里，agent 反复请求模型、执行模型调用的工具，直到模型不再调用工具。给用户的消息只通过工具发出：`send_message` 发一条消息，`post_ui` 发带界面块的消息，`edit_message` 改自己发过的消息。工具调用之外的文字谁也看不到：调工具那一步开头的一行只进状态栏；最后一步写了文字时（不管这一回合发没发过消息），在对话里告诉模型这段文字没发出去，让它再走一步（每回合一次），之后这句提醒也留在历史里那一步后面。`send_message` 不受项目工具开关影响，每个对话都有，评审讨论串也有。
- 对话里的几个小工具：`react` 给自己对话里别人的消息放一个表情（每条最多 3 个，可以撤回；`message.reacted`），用来代替“好的”“收到”这类消息；`send_message` 的 `replyTo` 引用同一对话里更早的一条消息，消息上方显示引用（发出时的前 120 字；引用中转消息时显示它转来的用户原话），`files` 带上工作区里的图片和文本文件或工具给的文件（`fil_…`），和用户的附件一样存进项目文件；`rename_thread` 改讨论串标题（讨论串改自己的，协调器改任意讨论串，`thread.renamed`）；`set_aside` 把讨论串放一放 1 到 30 天（讨论串放自己，协调器放任意讨论串，0 天表示收回），列表里移到“放一放”分组并显示提醒日期，到期时由定时器记一条 `thread.aside_due`，讨论串回到“需要我”，用户点“知道了”或给讨论串发消息就结束；`search_messages` 是只读的项目搜索，按新到旧给出消息原文的前 400 字和说话的人；`suggest_connector` 发一条带 MCP 服务卡片的消息，只带密钥的名字，卡片上点“添加”打开 MCP 设置并填好这个服务，保存后自动在这个项目里打开。
- `browser`：讨论串自己的无头浏览器，一个对话一个页面，跨调用保持状态。优先用本机的 Chrome、Edge 或 Chromium，没有的话第一次用时把 Chrome for Testing 的 headless shell 下到 `~/.ariadne/browser`。通过 DevTools 协议操作：`snapshot` 把页面写成文本，可操作的元素编上号（写进 `data-ariadne-ref`，下次快照前有效），`click`、`type`、`select`、`press`、`hover`、`scroll` 按编号操作（点击和按键是真实的输入事件），另有 `open`、`wait`、`screenshot`（窗口、整页最高 8000 像素、单个元素，超过 5 MB 改成 JPEG，存进项目文件）、`console`、`network`（失败和 4xx/5xx 的请求）、`evaluate`、`back`、`reload`、`close`。每个结果后面附上当前地址，以及新出现的报错数量和弹框（弹框自动确认）。闲置 10 分钟、讨论串汇报 done/failed/ready/blocked 或被停下、服务停止时关闭。SSH 和 daemon 工作区的浏览器还是在本机，但启动时带一个本机的 SOCKS5 代理（`--proxy-server` 加 `<-loopback>`），指向本机的地址经工作区连到远端机器的回环地址。`localhost`（末尾带点也算）、`*.localhost`、`127.x`、`0.0.0.0`、`::1`、`::`、`::ffff:127.x` 都算，域名先在本机解析，解析出这类地址的也算；连接由 daemon 的 relay `tcp` 通道承担（先连 127.0.0.1，不通再连 ::1）。没有 daemon、或 daemon 版本早于 `tcp` 通道（启动时探一次）时，SSH 用共享连接执行 `ssh -W localhost:<端口>`，sshd 会把 localhost 解析出的地址逐个试。其他地址直连解析出的那个地址，所以本机回环服务碰不到。汇报 `progress`、`waiting` 不关浏览器。所以模型写的 `http://localhost:3000` 原样能用，Host、跳转和 WebSocket 都和在远端打开一样。
- 一个回合没有步数上限，长任务不会做到一半被截断。防的是原地打转：同样的工具调用得到同样的结果，在最近 12 步里第 3 次出现时，结果后面附一句提醒模型换个做法（在等检查或回复就结束这一回合，到时会被唤醒）；第 4 次就停下这一回合，以失败结束并说明原因。不必相邻，两三个调用来回循环也算；隔很久才重读一次没变的文件不算。用户随时可以点停止。
- 每次模型回复（`turn.step`）和每个工具结果（`tool.finished`）都是事件。模型的输入每一步都从这些事件重建，所以一个回合可以重放，也可以在中断后接着做。
- 模型回复记下它看到的最新事件（`sawSeq`）。回复期间到达的输入排在这次回复之后，不会被当成已读，会再触发一个回合。
- 服务停止时正在进行的轮次记为 `interrupted`，下次启动时继续；没有结果的工具调用补一条错误结果。
- 仓库的 `AGENTS.md`：讨论串的工作区打开后，在一个回合开始时、工作区刚打开时和能改文件的工具（写文件、改文件、跑命令、分支操作、外部工具）跑过之后读工作区根目录的 `AGENTS.md`，只读的工具之后不再读，第一次读到或内容变了就记一条 `conversation.instructions`（内容和哈希，超过 1.6 万字截断），模型的系统指令里放最新记下的版本，所以每次请求仍能从日志重建。内容变了（包括讨论串自己改了它）或文件被删时，对话里在变化的位置给模型一条说明。对话里不给用户显示这些（用户不需要关心），只在追踪里能看到读到、改了和删了的记录。它放在名字带内容哈希的数据块里，同项目记忆一样闭合不了所在的块。这份文件来自仓库，不是用户说的话：它决定在这个仓库里怎么干活（命令、风格、目录），不能改变用户或协调器的要求、项目记忆和哪些事要用户点头，冲突时以后者为准。还没打开工作区的讨论串不读，读文件不会因此建出 worktree。子目录里的 `AGENTS.md` 不自动读：提示词让讨论串改某个子目录里的文件之前，先在那里和上层目录找一下，按最近的那份做。
- 重试窄而可见：只有模型插件标为可重试的错误（限流、服务过载或内部错误、已建立的连接被重置或超时、回复流没收完就断了）才自动重试，最多 4 次，等待从 1 秒起逐次翻倍，服务给了 `Retry-After` 就按它等。地址写错、域名解析不到、证书不对、连接被拒这类设置问题不重试，直接报错；`Retry-After` 超过 1 分钟（比如额度用完）也不重试，错误里写明要等多久。每次重试记一条 `conversation.model_retry`，对话里显示一行淡化的说明（第几次、等多久、原因）；失败那次已经流出来的文字丢弃，不当成回复。
- 备用模型：“设置 → 模型”里讨论串、协调器和分流各可再选一个备用模型。模型插件把限流、过载和服务端错误（429、5xx、Anthropic 的 overloaded / rate_limit / api_error）标为 `busy`；这类错误重试用完（或服务要等超过 1 分钟、不再重试）时，这一回合从这一步起换备用模型继续，记一条 `conversation.model_fallback`（从哪个换到哪个、原因），对话里一行淡化的说明，回合进行中状态行右侧写着“备用模型 …”，追踪里有一行“换模型”。换过之后上下文大小（输入框旁的环也按它算）、看不看图片、思考都按备用模型，没有自己模型的子调研也跟着用备用模型；备用模型也失败，这一回合照常失败。API Key 无效、请求格式不对这类换了模型也一样的错误不换。没有自己模型的角色（协调器跟讨论串、分流跟协调器）也跟着用那个角色的备用模型；子调研没有备用，失败时提问的一方拿到错误自己接着做。
- 其他模型错误（如 API Key 无效）、重试用完或用户点停止后，这一回合以失败结束，不会为触发这一回合的输入再自动重试，界面给出原因和“重试”；这一回合进行期间新到、模型还没看到的输入仍会排队处理。
- 回复被截断（超出单次回复的 token 上限，`turn.step` 的 `finish` 记为 `length`）时不把截断的文字当成完整回复，也不让这一回合失败：写到一半的那个工具调用丢掉，完整的照常执行，然后在对话里告诉模型回复被截断了、用户没看到，请它从断处接着、分小块写（大文件先写一部分再追加）。连续 3 步都被截断才以失败结束并说明原因。
- 一步里连着的只读工具调用（读文件、列目录、搜索、读计划和产物、抓网页等，`Tool.readOnly`）同时跑，其他调用按模型给的顺序一个一个跑；结果都按模型的顺序记下。提示词告诉模型：每一步都会把整段对话再读一遍，所以互不依赖的调用（几次读和搜索、`update_todo` 和它说的那个调用）放在同一步里发出；看文件用 `search`、`find_files`、`read_file` 而不是命令。
- 讨论串的文件工具：
  - GPT 和 Codex 系列的模型（模型名带 `gpt-`、`codex`，或是 `o3`、`o4-mini` 这类）改文件用 `apply_patch`，代替 `edit_file` 和 `write_file`：它们训练时就用这种补丁格式（`*** Begin Patch`、`*** Add/Update/Delete File:`、`*** Move to:`、`@@` 加上下文行和 `-`/`+` 行）。整份补丁先算好再写：有一段对不上就一个文件都不改，并说明哪几行没找到；行按原样、去掉行尾空白、去掉首尾空白、把弯引号和长横线当成直的，依次放宽去找，`@@` 后面的那行先定位。保留文件原来的换行符；新建已有文件时同 `write_file` 一样，文件在上次读写之后被改过就拒绝；所有要写、要删、要挪去的路径都在写之前检查，只能是工作区里的文件，不能是 `.git` 里的。写到一半失败（比如文件只读、被占用）时，结果说明停在哪里、哪些已经改了，不会让整个回合失败。别的模型照旧用 `edit_file`；外部 agent 程序（Codex 等）也照旧，它们自带同名的 `apply_patch`，会和它冲突。
  - `edit_file` 可以一次给多处修改（`edits`，按顺序应用，有一处失败就都不改）。`old` 原样找不到时，按行比较、忽略空白（缩进、行尾空格、换行符）再找一次，唯一时照改；只有一处修改时结果里直接给出改后的那几行（带行号，最多 20 行），让模型当场看到缩进，多处时说明宽松匹配的行号；还找不到就给出文件里最接近的几行（带行号）和第一处不同，模型不用再整篇重读。
  - `write_file` 覆盖已有文件前看它是否在讨论串上次读或写之后被改过（用户、命令或别的工具），改过就拒绝，让它先重读。记的是内存里的哈希，重启后不记得，就不拦。只读子调研里读到的不算讨论串读过。
  - 项目设置里的「改动后检查」：用户没写时由讨论串记下。项目还没有检查命令时，讨论串多一个 `note_check` 工具，新工作区打开时也提醒一句；第一个弄清仓库怎么检查代码的讨论串记下一条快的命令（类型检查或 lint，不是测试和构建），记之前先跑一次，命令本身不对当场能改。记下后别的讨论串不再有这个工具，只有记的那个讨论串能改自己记的；项目关掉了「命令」工具组时没有这个工具，记过的检查也不跑；用户的命令规则要询问或禁止的命令不能记，记下后规则变了也不再跑。用户在设置里改过或清空了输入框，就以用户的为准。每次 `edit_file`、`write_file`、`apply_patch` 之后在工作区里用项目的 shell 跑一次，`{file}` 换成改动的文件（按该 shell 的规则加引号）。通过只附一行，失败把退出码和输出（最多约 6000 字）附在这次修改的结果后面；输出和这个对话上一次失败时一字不差（项目里本来就有的报错）时只附一行“和上次一样”，旧工具结果被清理或总结之后再给全文；修改本身照样算成功。
  - `find_files` 按 glob 找文件（`**`、`{a,b}`、`[abc]`，不带 `/` 的模式匹配任意深度的文件名）。git 签出用 `git ls-files --cached --others --exclude-standard`，所以被忽略的文件不列；不是签出时用 `rg --files`，再没有就逐层列目录（跳过 `.git`、`node_modules` 和根目录 `.gitignore` 里的普通名字）。
  - `read_file` 读到的和这个对话上次用同样的 `offset`、`limit` 读到的一字不差，而且那次结果还在模型的上下文里（之后没有清理旧结果、没有总结、回合没有被停下）时，只回一句“没变，上次的结果仍然有效”。外部 agent 程序（Claude Code、Codex、ACP）自己保管和裁剪历史，不这样做。记在内存里，重启后照常给全文。
  - `search` 的结果按文件分组：文件名一行，下面是 `行号: 内容`，去掉缩进，单行超过 300 字截断；文件按路径排序。隐藏文件（`.github`、`.claude` 这类）照常搜，`.git` 不搜。可选 `glob`（如 `*.vue`、`src/**/*.ts`，规则同 `find_files`）和 `ignoreCase`；每个文件最多 50 行，总共最多 300 行。
  - `search` 和 `find_files` 不经过 shell：有 ripgrep 用 ripgrep，没有时 git 签出用 `git grep`，否则 `grep`，都没有（Windows 上不是签出又没装 ripgrep）就由服务端逐个文件读。程序直接起进程（工作区的 `execFile`），Windows 上也一样；本地以外的工作区（SSH、daemon）是 POSIX，参数按 bash 加引号。
- `run_command` 等到 `timeoutSeconds`（默认 120 秒）还没跑完时不再结束它，而是转到后台继续：结果里给出句柄和到那时的输出，之后用 `read_command_output` 接着读。长的构建或测试不会白跑一遍再重来。讨论串的后台命令已满 4 个时照旧到时结束。
- `run_command` 也可以一开始就放到后台（`background`）：立刻返回句柄（`cmd-1`）和头两秒的输出，用 `read_command_output` 读之后新来的输出（可等最多 60 秒）、`stop_command` 结束它和它起的进程。后台命令跨回合保留，每个讨论串同时最多 4 个，最长 8 小时；讨论串被停下、汇报 ready/done/failed/blocked、worktree 被移除、项目被删除或服务停止时一起结束（用户要自己试的那些在汇报 `ready` 时留着，见下），讨论串结束后它的后台命令连同输出一起丢掉。输出只在内存里保留最新的 200 万字；SSH 和 daemon 工作区收集输出时也边收边裁，不会随命令运行越积越多。服务异常退出（崩溃、被强杀）时没人收尾：Linux 的 bwrap 带 `--die-with-parent` 会一起结束，macOS 和 Windows 上后台命令（比如开发服务器）会一直留着，要手动结束。
- 后台命令也列在状态行里（输入框上方，回合之外也在）：每条一行，写着命令和跑了多久，点开看输出的末尾（打开时每秒取一次，不挪动模型自己读到的位置），可以停下。服务端在命令开始、结束和被清掉时通过事件流的 `background` 帧推送这个讨论串的列表，和正在跑的命令一样只在内存里。
- 后台命令在本机运行（本地目录、托管仓库的本地克隆）并在开头 2 万字的输出里打印了本机地址（`http://localhost:5173/`、`127.0.0.1`、`0.0.0.0` 这类）时，状态行在它后面给出链接，点开就是讨论串起的开发服务器。后台命令默认在讨论串汇报时结束，链接只在它工作时有：改了什么由汇报、截图和文档来说明，不靠留着服务器。用户明说要自己试（“起来我看看”）时，讨论串用 `keepForUser` 起这条命令，它在汇报 `ready` 之后留着，用户审阅时照样能点开；留到改动合并（或 PR 合并、关闭）、用户点“看完了”、worktree 被移除、讨论串被停下或汇报 done/failed/blocked。期间讨论串又被叫起来工作，命令还在：它的第一个工具结果后面附一句还在跑的命令和地址，让它接着用，不要再起一份。讨论串在同一个目录把同一条命令再放到后台一次时（改完重启开发服务器），先结束还在跑的那条再起新的，结果里说明；那条等了几秒还没退出就不起新的，如实告诉它，所以多轮返工不会攒下几个一样的服务器，也不会抢端口。每个讨论串 4 个、最长 8 小时的上限不变。SSH 和 daemon 工作区的命令跑在别的机器上，不给链接。讨论串面板顶部的分支标签点开是 worktree 的路径（worktree 已移除时是 `git switch <分支>`），可以一键复制，到终端里自己跑。
- `wait`：协调器和讨论串都可以“过一会儿再看”：给分钟数，或本地时间（`14:30` 指下一个 14:30，也可写日期），最长一周，再带一句到时要看什么。记一条 `conversation.wait_set`，模型随后结束这一回合；到点时记 `conversation.wait_ended`（`due`），对话收到 `<wait_over>` 和那句话并被唤醒，对话里一行淡化的“到点了，接着看：…”。等待期间状态行显示“等到 14:30”和那句话，用户可以“现在唤醒”（`now`，同样唤醒）或“取消”（不唤醒，模型下次工作时知道被取消了）。一个对话同时只有一个等待：再调用一次就替换，`cancel` 自己取消，这两种都不另行通知。其他输入照常唤醒它，等待留着。讨论串被停下时等待一并取消。等待记在事件里，服务重启后照样触发；停机期间到点的，启动时立即结束并唤醒。
- 定期任务：对协调器说一句（“每个工作日 9 点整理新 issue”），它用 `routine` 工具建（`add` 给那句话、星期几和本地时间，到分钟；`remove`、`list`），和记忆一样只在回应用户的回合里能增删。项目设置里列着已有的，可以改时间、停用和删除，不在那里新建。到点记一条 `routine.ran`，协调器收到 `<routine>` 和那句话被唤醒，协调器对话里一行折叠的“定期任务 · 09:00”，展开看那句话；设置里每条旁边是下次运行的时间。停机或机器睡眠期间错过的（晚了 5 分钟以上才发现）不补跑，下一次按时；把时间改到今天已经过去的时刻也不会马上跑。
- `research`：把需要大量查阅的问题交给一个只读子调研。它在独立的上下文里跑，用这个对话自己的只读工具（读文件、列目录、搜索、找文件、抓网页、读计划和产物等），最多 24 次请求，最后一次不给工具逼它作答；对话只拿回结论。模型在「设置 → 模型」的「子调研用」里选，留空用提问一方自己的模型。每次请求记一条 `research.step`（问题、回复、调用和结果、用量，系统提示和工具像 `turn.step` 一样按哈希存），token 计入这个对话；追踪里它挂在那次 `research` 调用下面，可以展开看每次请求和完整请求体。项目可在工具开关里关掉。
- 模型请求的无响应超时按“服务有没有发来任何东西”算：模型插件对每个流事件（包括 SSE 注释形式的保活）都交出一个 `alive`，思考内容攒齐才交出也不会被当成没响应。
- `run_command` 的结果是纯文本：退出码，然后是 stdout 和 stderr 两段。两段合计超过约 3 万字时从中间截掉，保留开头和更长的结尾，完整输出写进工作区的 `.ariadne/output/` 并在截断处给出路径，模型用 `read_file` 或 `search` 去查；`.ariadne/` 里放一个只含 `*` 的 `.gitignore`，不会出现在改动里。工作区插件本身只在超过 100 万字时截断，防内存用尽。交给模型和写进文件的输出去掉终端控制序列（颜色、光标、链接），用 `\r` 重画的进度行只留最后显示的那段。讨论串的命令默认带 `GIT_EDITOR=true`（项目环境变量可以覆盖），没写 `-m` 的 `git commit` 当场失败，不会等一个没人看得见的编辑器直到超时。
- 用户回答问题后，答案交给提问方（协调器或那个讨论串）并唤醒它，已经汇报完成的讨论串也一样。
- 对话很长时先腾地方：每一步开始前，如果模型的输入（上一步报告的输入 token 数，或按字数估算，取大者）超过模型上下文的六成（上下文超过 40 万的按 40 万算，所以 1M 的模型也在约 24 万时腾地方：每一步都要把整段输入再读一遍，大窗口是余量，不是要填满的大小），先把较早的长工具结果（超过 500 字或带图片的）换成一句占位（记一条 `conversation.results_cleared`，截到哪里），最近约四分之一阈值的结果保持原样；只有能省下至少 15% 并降到阈值的七成以下时才清理，清理了就不再总结。清理和摘要都会改变请求开头、让提示缓存从头来过，所以清完之后要再长一截才会有下一次。不够时不清理，直接请模型不带工具地把较早的历史（工具结果按原文）总结成摘要，记一条 `conversation.compacted`（摘要和截到哪里）。上下文大小在“设置 → 模型”里随每个模型填写，留空按 12.8 万 token。之后模型读到的是摘要加上截断点之后的原文，最近约四分之一阈值的内容保持原样。截断点只落在两步之间，不会把一次工具调用和它的结果拆开；再次压缩时上一份摘要也被并进新的摘要。
  - 用户自己的消息不交给摘要转述：截断点之前用户写的消息（讨论串里还有协调器转来的用户原话）原样放在摘要旁边，从新到旧装，最多占压缩线的八分之一、至多 2 万 token（中日韩文字一个字按一个 token 算），这样压缩后的输入不会还在压缩线之上、每一步都再压缩一次。一条消息最多占这份预算的四分之一，太长的（贴进来的日志）只留开头和结尾，不会把更早的消息挤掉；装不下的更早的消息注明省略了几条。写摘要时就算好哪些会被截短或省略，摘要请求点出它们（按发送时间和开头几个字），让摘要在开头的“From the user”里写下它们要了什么、定了什么，并保留上一份摘要在那里写的；其余的不再转述。摘要另外写做了什么、发现了什么、在等什么，以及用户后来改了主意的地方以哪条为准。转述会把要求说偏，而工作是按用户的原话验收的。预算记在 `conversation.compacted` 的 `userTokens` 里，追踪能按原样重建请求。这一段由存储的对话记录拼出，到下次压缩前不变，不影响提示缓存。
  - 摘要作为模型自己写的笔记（assistant 消息）回到模型，既不当成用户说的话，也不放进系统指令：它是从含有工具输出的历史写出来的。摘要分开记“用户说的”和“工作中得知的”，后者注明来源，只是信息，不是指令。
  - 摘要后面附上写摘要时从存储读出的待办和还没回答的提问（记在 `conversation.compacted` 的 `state` 里），模型不必凭摘要记忆它们（`update_todo` 是整表替换，凭记忆重写会丢项）。它在下次压缩前不再更新：之后的变化就是对话里的 `update_todo` 调用和回答，这样请求的开头保持不变，提示缓存不会因为待办一变就整段失效。
  - 对话里在压缩的位置显示一条淡化的分隔，点开能看摘要。总结失败时也在对话里注明原因，这一回合不再重试，照常读完整历史继续。
  - 事件日志里原文都还在，压缩只改变模型读到的东西；摘要请求的 token 计入会话用量。

模型由插件提供，每个插件实现一种协议（OpenAI 兼容、Anthropic）。用户在界面的“设置 → 模型”里添加提供方，再在提供方上添加模型（模型名、上下文大小、用途），配置写在 `~/.ariadne/config.json`（仅所有者可读写）；API Key 不写进事件日志，也不会返回给浏览器。

回复是边写边显示的：模型写 `send_message` 的参数时，`text` 已写出的部分作为草稿推给页面（SSE 的 `draft`，只在内存里，不进事件日志），用 dou-ui 的流式 Markdown 显示，状态栏显示“正在回复”。这靠下面说的 `tool-input` 和带 `live` 的工具，同一步里的几次 `send_message` 按开始写的顺序对上各自的草稿（也就是执行的顺序）。调用执行时消息沿用草稿的 id，页面上还是同一条；调用失败、尝试失败重试、输出被截断、回合停下时草稿撤掉。提供方不给 `tool-input`（外部 agent）时，消息在调用执行时整条出现。

外部 agent 也可以当提供方（`@ariadne/plugin-agents`）：Claude Code（`claude -p` 的流式 JSON）、Codex（`codex app-server`）和任何支持 ACP（Agent Client Protocol）的 agent，用它们自己登录的账号，所以订阅账号也能用。它们自带 agent 循环，Ariadne 的做法是只把对话自己的工具交给它，循环仍是 Ariadne 的：

- 工具：Claude Code 和 ACP agent 通过本机的 MCP 端点（`127.0.0.1` 随机端口，路径里带每个会话自己的随机令牌）拿到这一步的工具；ACP agent 不支持 HTTP 的 MCP 时，用一个转发到这个端点的本地小程序（`mcp-stdio.ts`）。Codex 用 app-server 的客户端工具（`dynamicTools`，它调用时回来问客户端）。工具调用由 agent 发起后挂起，作为这一步的 `tool-call` 交给 agent 循环，照常执行、记事件、进追踪、走确认，结果随下一次请求还给 agent。一步在 agent 发起调用之后安静 150 毫秒时结束，同时发起的调用算同一步。
- 它自带的工具：Claude Code 和 Codex 全部关掉。Claude Code 用 `--tools ""`，只放行这组 MCP 工具，权限模式 `dontAsk`，不读用户的设置、hooks 和斜杠命令；Codex 关掉 shell、看图、联网搜索、子 agent 等功能和用户自己的 MCP 服务，开讨论时不给它执行环境（`thread/start` 的 `environments: []`），所以它还留着的自带工具（`apply_patch`，代码模式下 `exec` 里的命令）没有地方执行，只会报“没有可用的执行环境”；它用自己的只读模式，审批交给客户端（`approvalsReviewer: "user"`）并一律拒绝，不让用户配置里的自动审查放行；ACP 协议没有办法关掉 agent 自带的工具：它拿不到 Ariadne 的文件系统和终端，权限请求只在工具名正好是这组工具之一时放行（`mcp__ariadne__<name>`、`ariadne/<name>`、`<name> (ariadne MCP Server)` 等写法），其余拒绝；不请求权限就直接执行的自带工具（很多 agent 读文件不问）拦不住，所以 ACP agent 只应接信任的程序。agent 进程的工作目录是插件数据目录下每个会话自己的空目录。
- 它所在的机器：agent 程序跑在用户自己的电脑上，会把这台电脑的工作目录、shell、系统和沙箱告诉模型；工作区是 SSH 或远程守护进程时，这些都不是干活的地方，模型照着写命令就会以为自己在本机。Codex 关掉这些说明（`include_environment_context`、`include_permissions_instructions`、`include_apps_instructions`、`skills.include_instructions` 都设为 false，不带内置 skill，不读工作目录里的 AGENTS.md；`$CODEX_HOME/AGENTS.md` 里用户自己的全局指令没有配置能关掉，还是会给模型看）；低于 0.135 的 Codex 不认 `environments`，会悄悄忽略，所以 `initialize` 返回的 userAgent 里版本太旧时直接报错，不开会话；Claude Code 和 ACP 关不掉，所以有工具的对话在系统指令末尾加一段说明：程序讲的目录、shell、系统和沙箱是那个程序的，工作区在工具执行的地方，可能是另一台机器，读写和执行只用给它的工具（`PLACE_NOTE`）。
- 会话：外部进程按对话（请求的 `conversation`，子调研各有自己的）保活。下一次请求如果是在它看过的内容后面接着（比较消息的指纹：用户消息比开头、回复比调用、结果比调用 id，所以清理旧结果和图片过期不影响），只把新的部分交给它：它在等的调用结果，或者回答之后来的新消息；它在等结果时来的消息附在最后一个结果后面。系统指令变了，把新的指令随下一次输入交给它。接不上（历史被总结、服务重启、换了模型或工具）就关掉旧进程，开新会话，把整段记录写成一份交给它。闲置 20 分钟的会话关掉，每种最多同时 16 个。没有 `conversation` 的请求（摘要）用完即关。
- 系统指令：Claude Code 用 `--system-prompt-file`，Codex 用 `baseInstructions`，ACP 没有系统指令，放在第一条消息开头。
- 用量：Claude Code 按消息 id 累计、回合结束时按 `result` 的总数补齐，它报的花费（`total_cost_usd`）直接记下；Codex 按 `thread/tokenUsage/updated` 的累计值求差；ACP 用 `session/prompt` 返回的 `usage`（有的话）。
- 思考深度：Claude Code 传 `--effort`，Codex 传给 `turn/start` 的 `effort`，ACP 不传。模型名填 `default` 或留它自己的默认；ACP 的模型在 agent 列出的模型里时用 `session/set_model` 选。
- 这类提供方在设置里只有“命令”一项，没有请求头、请求体和超时（`ModelProvider.program`）。追踪里的“请求体”是启动它的命令行和交给它的工具名。

- 按角色分配：讨论串干活，默认模型先给讨论串；协调器不选就和讨论串一样。两个角色各有思考深度（默认、低、中、高），同一个模型时协调器可以想得浅一些。“默认”不发思考参数，因为不支持的模型收到会报错；低中高在 Anthropic 协议是自适应思考（`thinking: {type: "adaptive"}`）加 `output_config.effort`，4.6 之前的模型不支持；在 OpenAI 兼容协议是 `reasoning_effort`。设了不止一个模型时，协调器的系统指令里列出它们和用户写的用途，`create_thread` 多一个 `model` 参数，协调器按工作挑；不给就用讨论串的默认。用户在讨论串输入框左下角随时换，从下一步起生效（`thread.model_set`），思考深度仍按讨论串角色。讨论串记的是模型设置的 id；那个模型被删了就回到讨论串的默认。
- 分流：用户在讨论串里说话时协调器会看一眼该不该转到别处。协调器等着的只有这些（加上不需要反应的进展汇报）时，这一回合用“分流用”的模型和思考深度；没设就和协调器一样。协调器最近一次读的输入已超过分流模型压缩线的八成时仍用协调器的模型，免得小模型按自己的上限清理或总结协调器的历史。换成别的模型读不到协调器那份提示缓存，所以便宜模型只在协调器的对话不长、或主力模型很贵时才划算。
- 思考：模型返回的思考按块记在 `turn.step` 的 `reasoning` 里。Anthropic 协议总是把带签名的思考块原样发回（新模型不设也会思考，工具调用的回合里协议要求发回，当前模型读不了的由服务丢掉）；OpenAI 兼容协议读 `reasoning_content` / `reasoning`，思考只发回给写下它的提供方（类型和设置都相同）和模型，步骤请求和摘要请求都一样（步骤和摘要记着各自调用的哈希，对话中途换了模型，之前的思考就不再发送）；Anthropic 不比模型名，签名的思考由服务自己判断能不能读，工具调用中途换模型时它仍要求 tool_use 前有思考；有思考时每条助手消息都带 `reasoning_content` 发回，没有思考的给空串（DeepSeek 等默认思考的服务带工具时要求之前的每条助手消息都有）。摘要时模型的思考去掉签名后记在 `conversation.compacted` 的 `reasoning` 里，随摘要那条助手消息一起发回；Anthropic 协议不发没签名的思考，所以不受影响。
- 用量：每一步的 token（`turn.step` 的 `usage`，摘要请求的也算）按会话累计，输入框的上下文圆环点开能看到它自己的；整个项目的在项目设置的“用量”页（搜索框里输“用量”也能到）：讨论串数、总 token、缓存命中率（读缓存占输入的比例）、输入 / 输出 / 缓存写入 / 缓存读取的明细条，以及用量最多的几个会话和占比。输入 token 是模型读的全部，其中读缓存的另记 `cached`，写入缓存的另记 `cacheWrite`（Anthropic 的 cache_creation），输出里花在思考上的另记 `reasoning`（都是服务说了才有）；这几项按会话累计在 conversations 表里。输入框左下角的圆环是上下文占用：最近一步模型读了多少，对比当前模型的压缩线（上下文大小的六成，见下文），到压缩线为满，八成变黄，接近满变红。
- 花费估算（可选，默认关）：“设置 → 模型”里每个模型可以填价格（币种为美元或人民币，每百万 token 的输入、输出、缓存读取、缓存写入，后两项不填按输入价算），选模型时已按 models.dev 的公开目录填好标价，也可以点“按模型目录重填”（只填进表单，保存才生效）；同一个模型名有多家时，先按提供方的类型和地址匹配，再按模型自己的厂商。每次请求记下当时估的花费（`usage.cost`，金额和币种）：服务自己报了花费（Claude Code）就用它的，否则按模型价格算（没读缓存的输入、缓存读取、缓存写入、输出各按各的价），没价格就不记。花费按会话、按币种累计在 conversations 表里。打开“用量里显示估算花费”后，项目用量和输入框旁圆环的弹层里多一行“估算花费”，两种币种都有时并列显示。订阅账号下 Claude Code 报的花费是按 API 价折算的参考值，并不是实际扣费。
- 追踪：讨论串标题栏的菜单里有“追踪”，协调器的在项目列表的右键菜单里（“协调器追踪”），都占满整个页面。表格按回合列出每个请求（步骤和摘要都算，整个会话连续编号）、它的工具调用，以及重试、摘要失败、旧工具结果的清理和 `AGENTS.md` 的变化；每行有输入、缓存读取、缓存写入、输出、思考 token，耗时和在回合里的时间线；表格比列宽窄时横向滚动，事件列固定在左边。选中一行在右侧看详情，两边的分隔线可以拖动（比例记在浏览器里）：请求有概要（模型、思考深度、发出 / 首个输出 / 结束的时间、结束原因、token）、请求体（提供方插件按记录的参数重建的 HTTP 请求体，不含凭据）、消息（相对上一步新加的标出来并展开）和响应；工具调用有参数、结果和工具定义。平时的对话里不显示工具调用。为了能重建，每个请求记下它用的系统指令、工具定义，以及提供方类型、模型名、思考深度和去掉密钥的提供方设置：内容按哈希在项目里只存一次（`prompt.recorded`），`turn.step` 的 `input` 记它们的哈希；其余部分就是 `sawSeq` 之前的对话记录，消息按当时的内容（之后的编辑不算）。时间是请求实际发出、第一次有输出（思考的开始也算）和记下结果的时刻；工具的开始时间从上一步或上一个记下的结果算起（同时跑的只读工具因此看起来是接连的）。
- 提示缓存：Anthropic 请求打四个缓存点（`cache_control: ephemeral`，5 分钟）：最后一个工具定义、系统指令、上一次请求的结尾（最后一条之前的那条 user 消息）和这次的结尾。一个回合里每一步只在对话末尾追加，所以下一步能从缓存读到这一步的全部，只为新增的部分付全价；上一次结尾那个点保证即使一步追加了很多块，也一定能读到。系统指令（记忆、计划、工作区）变了只让它之后的部分重算，工具定义的缓存不受影响。压缩或清理旧工具结果之后从新前缀重新缓存；摘要旁的待办和提问固定在写摘要的那一刻，不会每步改动开头。摘要请求的前缀之后没有请求会用到，`ModelRequest.cache: false` 让它不写缓存。OpenAI 兼容接口不打标记，DeepSeek 这类服务按前缀自动缓存，前缀稳定就够。`prefix.test.ts` 守着“每次请求都以上一次的完整内容开头”，压缩后待办一直在变时也一样。
- 每一步怎么读：对话记录一个回合里只整读一次，之后只读新加的（`listTranscript` 的 `after`）；记录里的消息被编辑过（`messagesChangedSince`）才整读。请求的消息每步只拼一次，要清理或压缩时才重拼。
- 页面怎么刷新：事件按类型决定要重取哪些部分（项目详情、对话、计划、产物、记忆），同一帧里的事件合成一次，重取一个接一个跑，慢的回答不会盖掉新的。回合进行中的事件（步骤、工具结果、待办）不重取计划、产物和记忆；`prompt.recorded` 什么都不重取。对话第一次整页取，之后带 `since`（上次回答里的 `lastSeq`）只取那之后新发或改过的消息和提示（消息、提问卡片、提示各有 `changed_seq`），按 id 合进已显示的内容。
- SQLite 用 WAL 加 `synchronous = NORMAL`（崩溃不损坏，只有断电可能丢最新几次提交），`busy_timeout` 5 秒。

离开后的回顾：用户超过 10 分钟没碰一个项目、再回来时，如果这期间有讨论串做完、改动被合并，或者有新的事在等用户，协调器对话里出现一行折叠的回顾（`user.returned`），展开是这些讨论串现在的样子，已经处理掉的“等你”自动消失。内容直接从事件日志和“需要我”列表算出，不调用模型，模型也看不到它。“在不在”由页面判断（动了鼠标、键盘，或回到页面），每个项目各算各的，上次在的时间记在这个浏览器里；多久算离开由服务端定。一个项目只留最新的一条，已经回顾过的不再重复。

通知：“设置 → 通知”打开浏览器通知后，页面不在前台时，有新的提问、讨论串汇报可以审阅、做完、受阻，或某一个回合出错，都会弹出通知，点开就跳到对应的项目和讨论串；同一个讨论串的新通知替换旧的。开关记在这个浏览器里。标签页标题前面是所有项目“需要我”的总数。

首次上手：

- `bun run start` 启动后自动打开浏览器（`ARIADNE_OPEN=0` 关掉）。第一次运行（还没有数据库）立刻打开；之后先等 12 秒（比页面最长的重连间隔略长），已经开着的页面会自己重连（服务端看有没有人连上事件流），没人连上才开新的。没有图形界面（Linux 上没有 `DISPLAY` / `WAYLAND_DISPLAY`）时不开。
- 还没有模型时，首屏列出本机已有的配置：模型插件的 `find` 在环境变量里找 Key、看 agent 程序是否装好并登录（`GET /api/settings/found`，密钥不出服务端）。点“用它”（`POST /api/settings/found/use`）会向服务要模型列表，挑一个开始用（目录里能调用工具、不是小模型和专用模型的里面最新的），按模型目录填好参数并验证连接；环境变量里的 Key 抄进 `config.json`，下次怎么启动都一样。
- 模型表单默认只有类型、地址、Key、模型四项。模型名的下拉来自服务自己的列表（插件的 `models`，`POST /api/settings/model-list`，用表单里还没保存的地址和 Key），选中后上下文、单次最多输出、看图片和价格按 models.dev 的目录填进折叠的那一栏，用户改过的不覆盖。保存照常保存，新加的模型和改了地址或 Key 的提供方各问一句（`checkModel`：发一个 “Hi”，有回应就停；agent 程序只看命令在不在），连不上的在表单里对应的模型下面写出原因。
- 有了模型，没有打开项目时（以及点侧边的“+”）首屏是一个输入框加一个可选的目录。发出第一条消息时在一个事务里建项目、接上目录、把消息发给协调器（`POST /api/projects` 的 `source`、`message`）；目录先连一次，连不上就不建。项目名取目录名；没有目录时先用第一句话的前 24 个字顶着（`project.created` 带 `unnamed`），协调器的工具里多一个 `name_project`，它在第一个回合起好名字，改过名（谁改都算）就不再有这个工具。
- 记忆的范围：`remember` 的 `scope: "everywhere"` 把一行写进用户的全局指令（“设置 → 指令”里的同一份），对话里留一行“给所有项目记下了”，可以就地撤销（`memory.everywhere`）；`forget` 可以按原文去掉这样的一行。

### 计划图

计划图是项目的有向无环图，节点分任务、里程碑和决策三种，每个节点有说明和验收标准，连线表示依赖。

- 每次修改是一个修订（`plan.revised`），带理由，记下撤销它所需的操作。任何一次修订都可以撤销，只要之后的修改和撤销不冲突：撤销一次编辑时，如果那个字段之后又被改过，撤销会被拒绝，不会覆盖后来的修改。
- 协调器的小改动立即生效：加节点、改标题和说明、改依赖。协调器改到、用户还没点开看过的节点在图上用小圆点标出；点开节点后它的圆点消失，等协调器再改它时才重新出现，所有改过的节点都看过后就算跟上了。计划页上方不再逐条列出这些修订：修订理由是协调器写的，不是给用户读的。“看过”记在浏览器里（每个项目一份），第一次打开时之前的修改都算看过。协调器的对话里留一行“改了计划：理由 · 加了 N 个节点”，可以就地撤销；托管自动开的讨论串也在那里留一行。加的节点和计划里已有的（或同一次里另一个）标题相同（不计大小写、空白和标点）时，整次修改被拒绝，协调器要先读计划、只加缺的。开工的节点有依赖还没完成时（中间没人做的里程碑和决策看穿过去），图上那条依赖画成虚线，节点和详情里标出是哪些。
- 撤销只在修改记录里。点“撤销”先列出撤销会做什么：逐条的改动、跟着被删节点一起断开的依赖（之后的修改连上去的）、会暂停的讨论串；之后的修改挡住了撤销时，说明是哪个节点或哪条依赖后来又改过、删掉了（`error.planUndoChanged`、`error.planUndoGone`、`error.planUndoLink`），不执行。撤销是一次新的修订（`revertOf`），理由是“撤销：原理由”。被撤销的修订标“已撤销”，可以“恢复”：恢复就是撤销那次撤销，原修订重新算作有效，之后还能再撤销。撤销只有一层：只能撤销原修订和它当前那次撤销，恢复本身不能再撤销（`error.planUndoRestore`），要撤就再撤销原修订，这样每次修订是否有效都看它自己的“已撤销”就知道。用户撤销或恢复会唤醒协调器，让它按新的计划调整，不要自己再改回去。
- 节点从计划里删掉时（用户删除、撤销“加节点”、用户同意的删除提议），上面还在进行的讨论串会暂停（`thread.stopped`，理由是这次修订的理由；用户删的由用户停，协调器先前暂停的也由用户接管，只有用户能让它继续）。节点被恢复时讨论串不会自动继续。
- 大改动先等用户同意：删除节点、修改验收标准、增改里程碑。协调器把一次修改里的这些操作合成一个提议（`plan.proposed`），放进“需要我”，问题里逐条列出会改什么（删除节点时注明上面还有几个讨论串）；用户同意后才生效。等确认的提议改到的节点标“待确认”；“在图上预览”把提议套到当前计划上画出来（服务端用同一套规则算好，随提议下发，前端只负责画）：新增的节点和连线是绿色虚线，要删的节点和连线是红色虚线、节点淡化，要改的节点是蓝色虚线，计划已经变得套不上时说明原因。协调器撤销一次修订也一样：撤销里有大改动（比如撤销“加节点”就是删除），也要先等用户同意。
- 用户同意时计划已经变了、提议不再适用的话，提议不生效，记为失效（`plan.proposal.stale`）：计划页提示用户这次同意没有生效，协调器收到说明并被唤醒，重新看计划后再提议。提示一直留着，直到用户点“知道了”（`plan.proposal.dismissed`）或协调器发出新的提议，不会因为一次无关的小改动就消失。
- 计划有两种视图：图（依赖关系）和看板（按节点状态分列）。图上的节点卡片显示在做它的讨论串、阶段、PR 编号和检查状态；等用户回答或审阅的节点整块着色并标“等你”。
- 用户可以直接在图上改计划：打开“编辑计划图”后，从节点底部拖线到另一个节点表示后者依赖前者，选中连线按 Delete 删除；选中节点按 Delete 会先确认（节点上有进行中的讨论串时说明有几个会暂停），“加节点”新建任务节点，侧栏里改标题、说明和验收标准。每个动作是一次用户修订（`author: user`），立即生效，不需要确认，能在修改记录里撤销；协调器下一个回合会收到说明。连线拒绝成环和重复；保存节点内容时带上原值（`expect`）。协调器在此期间改过同一字段的话，表单旁会显示现在的值，用户选“保留我的，再保存一次”或“改用现在的”，输入的内容不会丢；冲突时服务端拒绝保存（`error.planConflict`）。修订理由逐条写出这次改了什么，协调器从说明里就能知道。拖动节点的位置只记在浏览器里，“重新排列”恢复自动布局。
- 节点的状态由在做它的讨论串推出：没有讨论串是“未开始”，有讨论串受阻是“受阻”，等用户回答或审阅是“等你处理”，全部完成是“已完成”，其余是“进行中”。停下的讨论串不参与推算；节点上的讨论串全都停下时显示“已停下”。
- 讨论串可以绑定到节点。它的系统提示里有节点的说明、验收标准，以及上游节点已完成的讨论串的总结；上游讨论串汇报完成时，下游节点上还在做的讨论串会收到它的总结并被唤醒。

### 工作区

项目有一个项目来源：本地目录、GitHub 仓库、GitLab 仓库、SSH 远程目录或远程 daemon。讨论串第一次用文件或命令工具时才准备工作区：

- git 仓库：从仓库当前的 HEAD 为讨论串建一个 `git worktree`，分支是 `ariadne/<thread id 的末尾>`，讨论串之间互不可见。重启后沿用原来的 worktree；worktree 目录被手动删掉的话，先 `git worktree prune` 再在原分支上重建。项目来源是仓库的子目录时，工作区根目录是 worktree 里对应的子目录。
- 普通目录：所有讨论串共用这个目录。
- GitHub 仓库：在插件的数据目录里为仓库建一个共享的 bare clone（`~/.ariadne/plugins/github/repos/<owner>/<name>.git`），远端分支取到 `refs/remotes/origin/*`，取远端时不会动到讨论串的分支；每个讨论串从远端默认分支建自己的 worktree 和分支 `ariadne/…`。
- GitLab 仓库：和 GitHub 一样（共享 clone、worktree、推送都是同一份代码，`@ariadne/plugin-local` 的 `hostedClone`），目录先按实例（主机和端口，再加实例地址里的路径）再按项目的完整路径分层（`~/.ariadne/plugins/gitlab/repos/<主机>/<group>/<sub>/<project>.git`），不同实例上同路径的项目各有各的 clone。支持子组和自建实例：实例地址可以带路径（比如 `https://example.com/gitlab`），留空时用 GitLab.com 或仓库地址里的实例。
- SSH 远程目录：见下文“SSH 远程工作区”。
- 文件工具的路径都相对工作区根目录，越出根目录（包括经符号链接）的路径会被拒绝。命令在工作区里用项目设置的 shell 执行，默认「自动」：Linux、macOS 和远端用 bash，Windows 本地有 PowerShell 7（`pwsh`）就用它，没有用系统自带的 PowerShell 5.1。交给 PowerShell 的命令用 `-EncodedCommand` 传，不会被拆引号，输出设成 UTF-8。命令有超时，输出过长时只保留末尾。
- 新工作区的安装：用户没写安装脚本时，不按文件名猜（有 `pnpm-lock.yaml` 也说明不了用哪个版本、是不是套了别的工具），由第一个需要依赖的讨论串按仓库自己的说法（README、CONTRIBUTING、CI 配置、写明的包管理器和版本）找出装法，用 `note_setup` 装：命令在它的工作区里跑一遍，成功了才记到项目上（`project.setup.noted`），设置里显示，用户可以改或清空。还没记的项目，讨论串第一次打开工作区时会被告知。
  - 记下的命令只在讨论串自己的工作区里跑（`isolated`）：所有讨论串共用的目录（不是 git 仓库的本地目录、远端目录）是用户自己的，不动。用户自己写的安装脚本照旧在哪都跑。
  - 记下的命令是讨论串选的，所以要过用户的命令规则：`note_setup` 不收规则要询问或禁止的命令；规则后来变了，新工作区就不跑它，并告诉讨论串。
  - 新工作区不等安装：工作区马上交给讨论串，安装作为一条后台命令在跑，状态行能看到、能停，读、改文件照常进行。`run_command` 先等它结束再跑；失败或被停下时，等它的那次结果里会说，之后不会自己再跑。时限是“命令最长时限”。
- 工作区里的命令不需要审批；推送、部署这类影响工作区外、又无法撤销的操作，讨论串要先问用户。

讨论串的 worktree 尽量只占它改动的部分。提交历史本来就是所有 worktree 共用的（本地仓库的 `.git`、托管仓库的共享 clone）；签出的文件在文件系统支持写时复制时也共用：

- 新建 worktree 时先试一下能不能克隆（在仓库的 git 目录里拿一个小文件克隆到 worktree 要去的目录）。能，就用 `git worktree add --no-checkout` 只建出 worktree，再把这个提交跟踪的文件从用户的签出里逐个克隆过来（符号链接照原样建，子模块目录留给 git），然后 `git reset` 让索引和文件对上、`git reset --hard` 只重写不一样的那些：用户签出里没提交的改动、暂存的新文件、删掉的文件都不会带进讨论串。克隆出来的文件不占额外空间，任一边改了才各自分开。签出期间 worktree 的 git 目录里有一个 `ariadne-checkout-pending` 标记，写完才删；签出失败时把这个 worktree 移除再报错，服务中途停掉的（标记还在，或者还没有索引）下次打开时重做，不会把一个没有文件的 worktree 当成就绪的。
- 被忽略的 `node_modules`、`vendor`、`.pnpm-store`（任意层级，符号链接除外）整个目录克隆过来，讨论串不用重装依赖；它们仍被忽略，不会进讨论串的提交。构建产物不复制；Python 虚拟环境也不复制，它的脚本和 `activate` 用绝对路径指向原来的环境，克隆出来的会装进用户自己的环境。
- GitHub、GitLab 仓库没有用户签出可借：第一个 worktree 由 git 写出，之后的从同仓库另一个讨论串的 worktree 克隆，那个讨论串改过的文件同样由 `reset --hard` 改回来。
- 各平台的克隆：Linux 是 reflink（btrfs、XFS、bcachefs 等；ext4 不支持），macOS 是 APFS 的 clonefile，Windows 是 ReFS 卷（Dev Drive）内的复制，Windows 11 24H2（build 26100）起系统会把它变成块克隆，更早的版本按不能克隆处理；NTFS 不支持。文件在服务进程里克隆（`copyFile` 的 `COPYFILE_FICLONE_FORCE`，Windows 上先用 PowerShell 的 `Get-Volume` 确认两边在同一个 ReFS 卷），目录在 Linux、macOS 上用 `cp --reflink=always`、`cp -c`。SSH 和 daemon 的远端在 Linux 上用 `cp --reflink=always --parents` 做同样的事，macOS 远端只克隆依赖目录。
- 克隆要求两边在同一个卷上。本地仓库和 `~/.ariadne` 不在同一个卷、而仓库所在的卷能克隆时（比如仓库在 Dev Drive 上），worktree 改放到仓库旁边的 `<仓库的上级目录>/.ariadne-worktrees/`；两处都不能克隆时仍放在 `~/.ariadne` 下，旁边不留目录。
- 不能克隆（ext4、NTFS）时 worktree 就是普通的 worktree：签出各占一份，讨论串自己装依赖（`bun install` 本来就从全局缓存硬链接）。这时只靠下面的闲置回收省空间；Windows 上设置的“工作区”页会提示把仓库放到 Dev Drive。

没有用 overlayfs，也没有自己实现文件系统：overlayfs 只有 Linux 有，非特权挂载只在命名空间里可见，等于所有命令必须进沙箱，服务端的文件工具和用户的编辑器也看不到合并后的目录；Windows 上要做到同样的效果只能靠投影文件系统（文件一读就整份落盘，还要管理员开系统功能）、第三方内核驱动或注入子进程，都是原生代码，出问题时的表现正是命令行为不符合预期。

本地目录的工作区直接建在用户的仓库上（worktree 和分支都在这个仓库里），用户不用额外拉取就能看到讨论串的分支。worktree 目录在 `~/.ariadne/plugins/local/worktrees/`、`~/.ariadne/plugins/github/worktrees/` 和 `~/.ariadne/plugins/gitlab/worktrees/` 下（SSH 在远端的 `~/.ariadne-worktrees/`；本地仓库在另一个能克隆的卷上时在仓库旁边的 `.ariadne-worktrees/`），用完会自动清理，见下文。

### 参考来源

项目的来源只有一个，讨论串在它上面建工作区、改代码、开 PR。项目另外可以带至多 8 个参考来源（`ProjectView.references`，`project.references.set`），只读，种类和项目来源相同：

- 参考来源不建工作区，也不挂进文件系统：读的是插件已有的只读视图（`workspace.view()`），托管仓库是默认分支的最新提交，本地和远端目录是目录里现在的文件。命令看不到参考来源。
- 协调器、讨论串和审阅讨论串的 `list_dir`、`read_file`、`search`、`find_files` 多一个可选的 `source` 参数，填参考来源的名字就读它，不填读自己的工作区（协调器是项目来源的只读视图）。名字只在 `WorkspaceManager.referenceView` 一处认。`search`、`find_files` 的路径和读文件走同一套检查（不出根目录、不进 `.git`、不跟着链接出去），找到的文件也再查一遍。提示词里列出每个参考来源的名字和位置。
- 只读视图可以自带 `files` 和 `search`（本地目录用 ripgrep，托管仓库的 clone 用 `git ls-tree` 和 `git grep`，远端目录在远端跑）；没有的视图靠逐个目录读文件来找。
- 名字从位置的最后一段取（`referenceName`），重名时加序号，用户不用起名。
- 密钥存在 config.json 的 `sourceSecrets` 里，键是 `reference.<id>.<字段>`；没填、种类和项目来源相同、令牌发往的地方也相同（插件的 `secretsFor`，GitLab 是实例地址）时才用项目来源的。
- 添加有两处：项目设置的“项目来源”页；协调器的 `add_reference` 工具，先连一次确认读得到，再在对话里出一张确认卡片（同时进“需要我”），用户点“添加”才加上，同一回合就能读。连不上的不出卡片。
- 讨论串也有 `add_reference`：任务要读而自己够不着的东西（没克隆的仓库、不在工作区那台机器上的目录），或者值得项目留下的来源。它的卡片是三选一：“加入项目”“仅这个讨论串”“不用”，讨论串建议的那个标为推荐（`callApproval` 的卡片可以是选择块，`no` 指明哪一项是拒绝）。选“仅这个讨论串”的记在讨论串上（`ThreadView.references`，`thread.references.set`），只有它自己读得到，名字和项目的参考来源错开，`referenceView` 先认讨论串自己的；不占项目的 8 个名额，只进它自己的提示词。回答后的卡片上悬停可以“收回”或“加入项目”（`removeThreadReference`、`keepThreadReference`）；之后卡片上写着“已收回”或“已加入项目”（`ThreadView.endedReferences`），讨论串下一回合读到一条说明（`reference-ended`）：读不到了，或者项目里它现在叫什么（项目里已有同名或同一个来源时名字会变）。项目已满时用户选了“加入项目”，这次回答作废，讨论串再问时是一张新卡片。协调器只能加到项目。
- AI 请求的位置比用户手填的多一道检查（`reference-guard.ts`，在连接之前）：Ariadne 自己的数据目录（`~/.ariadne`）、常见凭据目录（`~/.ssh`、`~/.aws`、`~/.config/gh` 等）以及它们里面的路径直接拒绝；包含这些位置的目录（根目录、主目录、`~/.config`）也拒绝，让它改要具体的目录。本机按真实路径比。远端只能按写法比：先算掉 `.` 和 `..`（`..` 越过 `~` 或相对路径起点的直接拒绝），再拒绝根目录、主目录（`~`、`/root`、`/home/<名字>`、`/Users/<名字>`）、路径里出现凭据目录名的，以及以 `.config`、`.local/share` 这类装着凭据目录的名字结尾的；远端的符号链接和不在这些位置的主目录认不出来。项目设置里用户自己添加的不受这道检查。
- 本地目录可以只给一个文件（日志、转储）：只读视图里只有这一个文件（`singleFileView`），它不能当项目来源（`viewOnly`）。
- 页面打开时问一次哪些参考来源现在读不到（`GET /api/projects/:id/references/status`，每个最多等 5 秒），读不到的那一行换成警告图标；原因以 key 和参数返回，由页面翻译。

### 交付前审阅

有代码来源的项目默认开启（项目设置“工具”页可关）。讨论串报告 `ready` 且有要合并的提交或 PR 时，这次交付先不进 `review`，也不报告给协调器，而是交给一个审阅讨论串：

- 审阅讨论串第一次用到时创建（`thread.created` 带 `reviewOf`），模型和作者相同，不挂在计划节点上；同一作者之后的轮次和交付都复用它。界面上它嵌在作者下面，不进「需要我」，也不发通知。
- 每轮记 `review.requested`（轮次、作者分支的 head）唤醒审阅讨论串。它只读作者的工作区（列目录、读文件、搜索、`read_changes` 看带行号的改动），外部工具和协调器一样只拿标成只读的，按仓库的 `review` 做法文件审，没有时用内置的说明；只报 bug、漏掉的验收标准和安全问题，不提风格。
- `submit_review` 记 `review.submitted`：`pass` 时作者进入 `review`，协调器收到带轮次的报告；`changes` 时评论（文件、行、引文、类别）作为一条笔记唤醒作者。
- 作者再报告 `ready` 时必须逐条回复（`fixed`，或 `declined` 加理由），记 `review.replied`，然后进入下一个回合。最多 2 轮：第 2 轮仍有评论时，作者回复后这次交付直接交给用户。交付到了用户手里之后再报告 `ready`，又从第 1 轮开始。
- 审阅讨论串一回合结束却没给结论（没有新输入要读）、回合失败或开始不了、或被停下时，记 `review.abandoned`：和 `pass` 一样，交付进入 `review`，协调器收到报告（注明最后一个回合没有结论），用户收到通知。被中断的回合不算，重启后接着审。审阅讨论串停着的时候，之后的交付不再送审。
- 作者报告 `done` 或 `failed` 时这次交付结束，没回复的评论不再要回复。
- 改动视图把 AI 评论按行显示成只读评论串，带作者的回复；作者修好的评论串显示为已解决。卡片、「需要我」和讨论串列表用图标加数字显示审过几轮。

### 托管推进

项目设置“托管推进”页打开（默认关，要求交付前审阅也开着：关掉审阅时托管一起关），项目就自己往下走，用户只在需要决定的时候出现：

- 自动合并：交付在这一次报告之后通过了 AI 审阅（最后一个回合是 `pass`），讨论串处在 `review`，就按项目的合并方式（用户在这个项目里上次合并用的方式，没合并过是压成一个提交）合并。本地目录、SSH 和 daemon 用“查看与合并改动”里的合并，提交说明是讨论串的标题，记 `branch.merged`（`auto`）；GitHub、GitLab 先重新读一次 PR，检查全部通过才由插件调合并接口（`RepoCapability.mergePullRequest`，只在 PR 的最新提交还是审过的那个时合并），之后 `pull_request.closed` 带 `auto`。检查还在跑时等着，仓库监视器下次读到变化再看；PR 的最新提交一个检查都没有时先等一分钟（仓库的 CI 可能推送之后才登记检查），一分钟后还是没有才算通过；检查失败照常唤醒讨论串去修，修完的交付重新审阅。讨论串的对话里留一行“审阅通过，已自动合并”。
- 不合并时交给用户：审阅之后分支（或 PR）又有新提交、托管仓库的分支没有打开的 PR、合并被拒（签出挡住、平台不让合并、工作区不能合并、找不到分支），或合并出错，记 `autopilot.held`（带这次看的提交，同一个提交不再试），对话里说明原因，讨论串照旧留在“需要我”里等用户。有冲突时什么都不合并，和用户合并时一样记 `branch.conflicted` 交还讨论串；PR 的冲突带 `pullRequest`，讨论串先 `sync_branch`，合并 `origin/<基线>`，解决后推送、再报告 `ready`。
- 自动开工：协调器一回合结束、也没有等着它的新输入时（失败的回合不等），依赖都已完成、上面还没有讨论串的任务节点各开一个讨论串（`thread.created` 带 `auto`），标题是节点标题，第一条消息说它依赖的节点都已完成（讨论串里标成“托管推进的消息”），开讨论串和这条消息在一个事务里写入，说明、验收标准和上游的产出本来就在它的系统提示里。协调器自己在回合里开、自己写说明的讨论串优先；托管只补上剩下的。同时在做的讨论串（不算审阅讨论串、已完成和暂停的）到了项目的“同时进行的回合”上限（没设时用全局的槽位数）就不再开，项目的 token 预算用完也不开。决策节点不自动开，等协调器和用户；等用户同意的计划提议改到的节点也不开。协调器收到一条不唤醒它的说明。
- 阶段关口：依赖都已完成的里程碑不开讨论串，而是进“需要我”问一句“「里程碑」之前的都完成了，进入下一阶段？”（系统的确认卡片，`purpose` 是 `milestone:<节点 id>`）。同意后里程碑算完成（计划图上显示已完成，下游节点可以开工）；等回答时节点显示“等你”。托管中途才打开时，下游已经有讨论串的里程碑算已经走过：不问，下游其他节点照常开工。答“先不”后不再问，直到托管重新开始（重新打开或暂停后继续）；协调器收到回答并被唤醒。里程碑从计划里删掉时，还没回答的问题撤回。
- 暂停：项目顶部在托管打开时显示一个按钮，托管中是带涟漪的圆点，点一下暂停（`project.autopilot.paused`），变成静止的圆点“托管已暂停”，再点继续。暂停时不自动合并、不自动开工、不问关口；在跑的讨论串照常工作。
- 托管不跳过需要用户的事：受阻、失败、预算用完、两轮审阅后还有评论、审阅没有结论（`review.abandoned`）的交付都照旧进“需要我”。打开托管的项目里，审阅通过不再弹通知（没合并时 `autopilot.held` 会弹）。
- 所有项目排在一个队列里依次看，一次慢的合并请求会让别的项目等一会；目前本地单用户，先这样。
- 协调器的系统提示里写明托管开着（以及是否暂停），让它不去问用户要不要开工或合并。

托管推进由服务端的 `Autopilot` 驱动：订阅事件，有关的事件（报告、审阅结论、合并、PR 同步、计划修订、回答、回合结束、设置和暂停）之后约一秒看一次那个项目，按项目排队，启动时把所有项目看一遍，接住停机期间的变化。

### 做法文件

做法文件（skill）是写给模型的工作方法。一个做法文件是一个 `<名字>.md`，或者一个文件夹 `<名字>/`，里面放 `SKILL.md` 和它用到的文件（脚本、参考资料等）；名字就是文件名或文件夹名，同一处两种都有时文件夹生效。

从四处读，每处有一个标记：

| 位置                                           | 标记          |
| ---------------------------------------------- | ------------- |
| 仓库的 `.ariadne/skills/`                      | `repo`        |
| 仓库的 `.agents/skills/`（多个工具共用的目录） | `repo-agents` |
| 本机的 `~/.ariadne/skills/`                    | `user`        |
| 本机的 `~/.agents/skills/`                     | `user-agents` |

不同位置的同名做法文件都保留，不互相覆盖。名字只在一处出现时就叫这个名字；在多处出现时，每一个都叫 `<名字>@<标记>`（如 `review@repo`、`review@user-agents`），提示词的清单、`read_skill` 和输入框的 `/` 菜单都用这个全名。模型只给出不带标记的名字时，`read_skill` 会列出有哪几个，让它指明；没有说明是哪一个时模型优先用仓库的。名字会随别处是否有同名项而变：原来叫 `deploy` 的，在另一处也放了 `deploy` 之后就变成 `deploy@repo`，旧消息或仓库指令里写的 `deploy` 这时不再唯一，由模型按上面的规则选。

不递归查找，不读其他目录。第一行（或 front matter 的 `description`，可以是多行）写什么时候用；提示词里只列名字和这一行，模型需要时用 `read_skill` 读全文（上限 32k 字符，每处最多 40 个）。输入框的 `/` 菜单可以点名一个做法文件，它会随消息告诉模型。协调器每回合重新读，讨论串在仓库指令变化时重新读。

文件夹形式的做法文件读全文时会附上文件夹的位置和里面的文件清单（最多 60 个，三层以内，最多看 30 个文件夹），模型按 `SKILL.md` 里写的相对路径用 `read_skill` 的 `file` 参数按需读；只读文本，读不到文件夹以外的东西。文件夹里没有 `SKILL.md` 时不算做法文件，同名的 `<名字>.md` 照常生效。

软链接：本机目录里，做法文件本身（单个文件或整个文件夹）可以是指向别处的链接；文件夹内部的链接只在目标仍落在这个文件夹里时才读，链接的子文件夹不跟随。仓库里的按工作区的规则读，协调器看的是 git 里的内容，所以仓库里用链接放的做法文件协调器读不到。

名叫 `review` 的做法文件只有放在 Ariadne 自己的目录（`.ariadne/skills/`、`~/.ariadne/skills/`）里才替换内置的审阅指引；共用目录里的 `review` 多半是给别的工作方式写的，只当普通做法文件。仓库和本机自己的目录里都有时，用仓库的。

### 查看与合并改动

讨论串第一次打开工作区时记下它的基线分支（`workspace.opened` 的 `base`）：本地目录和 SSH 是签出当时所在的分支，GitHub、GitLab 是远端的默认分支。签出处在分离的 HEAD 上时没有基线，看不了改动，也合并不了。之后工作区被移除再打开，沿用记下的基线，不看签出现在在哪个分支上。

- 改动按 PR 的方式比较：从分支和基线最近的共同提交，到分支最新的提交，只算已提交的内容（GitHub、GitLab 的基线是共享 clone 里的 `origin/<默认分支>`）。改名按 git 的相似度识别。worktree 里没提交的文件单独列出数量，它们不在改动里，也不会被合并；讨论串的系统提示也说明了这一点。
- 界面上讨论串面板顶部和计划节点里的“改动”打开改动视图：左边是按目录排列的文件（只有一个子目录的目录合成一行），右边是 `@dou-ui/code` 的 `DouCodeDiff`。文件内容按需读取，超过 512 KB 的和二进制文件不显示内容。
- 本地目录和 SSH 由用户点“合并到 <基线>”：默认压成一个提交（squash），也可以保留每个提交（合并提交）；提交说明默认是讨论串的标题，作者是 git 里配置的 `user.name`、`user.email`（本地读用户自己的配置，SSH 读远端用户的）。合并不碰讨论串的 worktree：先用 `git merge-tree --write-tree`（需要 git 2.38+）算出结果，有冲突就什么都不改；没有冲突时写出提交，基线没有签出在任何地方就用 `update-ref` 从原来的位置移过去（期间基线有了新提交则拒绝，再合并一次即可），基线签出在用户的目录里就在那里 `merge --ff-only`，文件跟着更新，签出里未提交的改动挡住时拒绝，什么都不丢。更新签出时不读用户的全局 git 配置（免得执行讨论串写进去的 filter），所以仓库的 `.gitattributes` 里有 `filter=`（比如 Git LFS）时拒绝在签出里合并，请用户自己合；全局的 `core.autocrlf` 也不生效。讨论串正在跑一个回合时不能合并。
- 合并记 `branch.merged`：协调器收到说明并被唤醒；讨论串下次工作时读到，squash 之后继续改要先把基线合进自己的分支，后面的改动才单独比较。冲突记 `branch.conflicted`，唤醒讨论串：在自己的分支上合并基线、解决冲突、跑检查、提交，再报告 `ready`。两者都在讨论串的对话里留一行，用户能看到发生了什么。
- 合并可以撤销：讨论串对话里那行合并通知上有“撤销”，只对它最近一次在这里做的合并有效。撤销把基线移回合并前的提交（`BranchCapability.undoMerge`）：基线没有签出时用 `update-ref`，签出在用户目录里时在那里 `git reset --keep`，文件跟着回去，签出里没提交的改动留着，改的是同一批文件时拒绝。只在这次合并还是基线最新的提交、也没有别的分支包含它时才撤销；之后又有新提交、已经推送，或者合并之后开出来的讨论串的分支带着它（移回去会丢东西、下次拉取又回来，或者合并那个讨论串时被撤销的改动跟着回来），这时拒绝并说明原因，由用户自己在终端里处理。撤销记 `branch.merge_undone`：讨论串的 `merged` 清空，回到 `review` 等用户再合并；被移除的 worktree 建回来；通知行显示“已撤销”；协调器收到说明并被唤醒，讨论串下次工作时读到；托管推进不会自己把撤销掉的那个提交再合并一次（记在 `autopilot_held`）。PR 的合并在托管平台上，不在这里撤销。
- GitHub、GitLab 的改动通过 PR 合入，界面只看改动，不替托管平台合并；打开了托管推进的项目例外，见“托管推进”。

worktree 在改动合入之后自动移除，分支保留：用户合并了分支（在 Ariadne 里，或者在终端里合并到基线），或者 PR 已合并或关闭，并且讨论串处于 `review` 或 `done`。worktree 里有没提交的文件（被忽略的 `node_modules` 之类不算）就留着。相关事件之后过一会儿检查一次，另外每 10 分钟扫一遍，接住在 Ariadne 之外的合并。讨论串处于 `review` 或 `done`、一天没有任何动静（`activeAt`）时，worktree 也会移除来腾空间（`reason: idle`）：改动都在分支上，看改动和合并不需要 worktree，界面上照常能看能合并（`workspace.parked`），合入之后不再算作闲置回收；有没提交的文件、回合在进行、或者留着给用户试的后台命令还在跑时不动它。闲置回收还多查一层 git 不算作改动、但删了就找不回来的东西，有就留着：依赖目录（`node_modules`、`vendor`、`.pnpm-store`）以外的被忽略文件（`.env`、构建产物、本地数据），HEAD 不在分支上（游离 HEAD 上的提交、进行中的 rebase 或 bisect），进行中的合并、cherry-pick、revert。依赖目录不保留，重建时重新克隆或安装；stash 存在仓库里，不受影响。合入之后的移除不查这一层：被忽略的文件随 worktree 删除。闲置回收之后用户在 Ariadne 之外合并了分支，巡检发现后不再算作闲置回收。移除记 `workspace.removed`，只有用户自己移除的在讨论串的对话里留一行；讨论串再用文件或命令工具时在原分支上重建 worktree，读 `AGENTS.md` 不会因此把它建回来。设置的“工作区”页按项目列出 worktree 和占用的空间（`du`），也可以手动移除；worktree 和签出共用存储的项目不显示大小（`du` 会把共用的部分算成各占一份），在项目名旁的图标提示里注明“写时复制”，Windows 上不共用存储的项目同样用图标提示 Dev Drive，同样只移除没有未提交改动的。

项目来源的设置按插件给出的 schema 填写。标成 secret 的设置（比如访问令牌）存在 `~/.ariadne/config.json`，不写进事件日志，也不返回给浏览器；GitHub 令牌留空时依次使用 `GH_TOKEN`、`GITHUB_TOKEN` 和 `gh auth token`。GitLab 令牌（需要 `api` 权限）留空时使用 `GITLAB_TOKEN`、`GITLAB_ACCESS_TOKEN` 或 `GL_TOKEN`，但只发给 `GITLAB_HOST` 指的实例（没设置时是 GitLab.com），否则用 `glab config get token --host <实例>`，调用时清空 glab 也会读的 `GITLAB_TOKEN`、`GITLAB_ACCESS_TOKEN`、`OAUTH_TOKEN`、`GL_TOKEN`、`CI_JOB_TOKEN`，只拿 glab 为这个实例保存的令牌：为一个实例签发的令牌不会被发给别的实例。GitLab 实例地址只接受 https（本机的 localhost 除外），API 请求和服务端的 git（GitHub、GitLab 都是）都不跟随重定向，令牌不会被带到别的主机。令牌只在服务端自己的 git 命令里通过环境变量交给 git，并绑定到仓库地址，不落盘，也不出现在命令行参数里。服务端的取远端和推送用自己保存的地址、关掉 hook，不读 worktree 里可被改写的 remote；共享 clone 的 `pushurl` 指向一个无效地址，讨论串直接 `git push` 会失败。

讨论串的命令环境里去掉了服务端的凭据（`GH_TOKEN`、`GITHUB_TOKEN`、`GITLAB_TOKEN`、`GITLAB_ACCESS_TOKEN`、`GL_TOKEN`、`CI_JOB_TOKEN`、`OAUTH_TOKEN`、`ARIADNE_*`、`GIT_CONFIG_*`），令牌不会意外出现在工具结果、事件日志和模型输入里。

讨论串的命令没有沙箱：以用户身份直接运行，能读写用户能读写的一切，包括 Ariadne 的数据目录（`~/.ariadne`：本地令牌、`config.json` 里的 API Key 和访问令牌、数据库）。早先有过一层只遮住这些路径、把 git 的 `config` 和 `hooks` 锁成只读的沙箱（Linux 的命名空间、macOS 的 `sandbox-exec`，Windows 没有），它让 `git config`、`git submodule init`、安装 hook 的依赖脚本、用本机浏览器配置的自动化、自己也要建沙箱的程序在里面失败，而用户的 SSH 密钥、git 凭据、shell 启动脚本本来就在它外面，护住的只有 Ariadne 自己的令牌；三个平台行为也不一致。所以去掉了，剩下的约束是下面这些，都不依赖隔离：

- 服务端自己的 git 命令不读全局和系统配置，不运行 hook 和 fsmonitor，只允许远端用的协议（GitHub、GitLab 是 `https`，本地仓库不联网）。讨论串能写仓库的 `.git/config`、`hooks/` 和用户的 `~/.gitconfig`，但这些改动不能让服务端的 git 执行命令。
- 共享 clone 的分支 ref 对所有讨论串可写：一个讨论串能移动别的讨论串的 `ariadne/…` 分支，那个讨论串推送时，推上去的就是被改过的提交。
- Linux 和 macOS 上，讨论串的命令都在自己的进程组里运行，命令结束（或超时）时整组结束，留下的后台进程不会一直运行；特意脱离进程组的进程（`setsid`）仍能留下来。它占着输出时，命令结束后最多再等 1 秒读输出，工具调用不会因此挂住。
- Windows 没有进程组：超时或讨论串被停下时，用 `taskkill /T /F` 结束命令和它启动的进程；命令自己结束后留在后台的进程不会被结束。
- 文件工具在服务端读写文件：先按路径检查不越出工作区，再以不跟随符号链接的方式打开，并确认打开的正是检查过的那个文件，其间被换成符号链接或别的文件就拒绝。被拒绝的写入可能在被换去的地方留下一个空文件或空目录：服务端不按路径回头删除，那样会再次跟随被换的链接，删掉工作区外的文件。
- 推送由服务端自己执行，用它保存的地址和令牌；讨论串在命令里直接推送依然会失败。

“不合并、不推其他分支”靠工具面和提示约束，防的是失误，不是蓄意越权的讨论串：讨论串和用户的账户之间没有隔离。

### SSH 远程工作区

SSH 来源（内置插件 `plugin-ssh`）让讨论串在另一台机器上签出和执行命令，填主机（`user@host` 或 `~/.ssh/config` 里的 Host）、可选的端口和远端的绝对路径。

- 连接用系统自带的 `ssh` 和用户自己的配置、密钥、ssh-agent，不保存任何密钥，也不支持密码登录：`BatchMode=yes`，从不提问。主机指纹不认识时连接直接失败并给出原因，用户先在终端里 ssh 一次确认指纹；Ariadne 不会替用户接受新指纹。不过用户自己的 ssh 配置里放宽的指纹策略（`StrictHostKeyChecking no` 或 `accept-new`）同样生效。
- 连接不转发任何东西（`ForwardAgent=no`、`ForwardX11=no`、`ClearAllForwardings=yes`、`Tunnel=no`、`GSSAPIDelegateCredentials=no`），也不运行 `LocalCommand`：远端的命令连不回这台机器，用不了本机的 agent 去登录别处。本地的 `ssh` 进程拿到的环境同样去掉了服务端的凭据，`SendEnv` 带不过去。
- 远端的 `PATH` 里有 `ariadne-daemon` 时（第一次调用前用 `command -v` 找），只起一个长驻的 `ssh` 进程运行 `ariadne-daemon --stdio`，之后每次调用只是这条 relay 会话里的一个通道（见下文“relay 会话”），不再为每次调用起本机的 `ssh` 进程和远端的登录 shell。先用一次空调用确认对方说的是同一版协议；找不到、路径里有登录 shell 可能拆开的字符、或者是不支持 `--stdio` 的旧版本时，回到下面的做法。这个 `ssh` 进程空闲两分钟后退出。ssh 断了时新起的 daemon 没有原来的会话，进行中的调用以退出码 255 结束。
- 没有 daemon 时，每次调用起一个 `ssh` 进程，同一台主机的调用共用一条连接（`ControlMaster`，套接字在 `~/.ariadne/plugins/ssh/cm/`，空闲两分钟后断开），每次调用只有几十毫秒的开销；数据目录的路径太长、放不下 Unix 套接字时，或者在 Windows 上（系统自带的 OpenSSH 不支持 `ControlMaster`），就每次新连，并显式关掉复用（`ControlMaster=no`、`ControlPath=none`），不会挂到用户在终端里开的、可能带着转发的主连接上。
- 远端是 git 仓库时，和本地目录一样为每个讨论串建一个 worktree，放在远端用户的 `~/.ariadne-worktrees/<仓库路径的哈希>/<thread id>`，分支是 `ariadne/…`，从签出当前的 HEAD 建出；子目录、手动删掉后重建、依赖目录的写时复制（远端支持 reflink 时）都和本地目录相同。服务端在远端运行的 git 关掉 hook 和 fsmonitor。不是 git 仓库的目录由所有讨论串共用。
- 远端只需要 bash、git 和常见的 POSIX 工具（`realpath`、`cat`、`cp`）。登录 shell 的引号规则各不相同（fish 的单引号里仍有反斜杠转义，csh 不接受单引号里换行），所以交给登录 shell 的命令行固定是 `exec bash --norc --noprofile -s`，没有任何要引的东西；脚本和参数从输入送给 bash，参数只按 bash 的规则加引号。bash 从管道或套接字读输入时一次读一个字节、读完一整行才执行，所以调用脚本的那一行之后的输入原样留给脚本：要写入的文件内容，或者看守进程读的输入。这个 bash 不读启动文件，登录 shell 自己读过的那些设好的环境（比如 `PATH`）照样带过来。sh、bash、zsh、fish、tcsh 作登录 shell 都有对照测试。
- 文件工具在远端读写：路径先在本机规范化，不允许 `..` 和绝对路径，再在远端把最近的已有目录解析成真实路径，确认仍在根目录里；经符号链接出去的、指向不存在位置的链接（写入会顺着它在外面建文件）都会被拒绝。远端的文件工具和命令以同一个用户运行，这层检查防的是失误，不是隔离。
- 命令用 bash 在工作区里运行，有自己的进程组。脚本另起一个看守进程读连接的输入：超时、讨论串被停下或者连接断了，本机就关掉输入，看守进程结束整个进程组，留在组里的后台进程也一起结束；特意脱离进程组的（`setsid`）和本地目录一样挡不住。输出过长时只保留末尾，和本地相同。
- 命令以 SSH 登录的用户身份运行，能读写那个用户能读写的一切。项目设置的来源页会注明命令在哪台机器上运行。
- SSH 来源只提供 `workspace`，没有 PR 和检查（搭配代码托管时有，见下文）；看改动、合并和自动清理 worktree 与本地目录相同，git 都在远端运行。
- 讨论串在远端 worktree 里的 `git push` 推不出去：命令的环境里加上 git 配置（`GIT_CONFIG_COUNT`，接在用户环境里已有的后面），把所有推送地址改写成一个不存在的路径 `/git-push-is-blocked/…/`，报错里就能看到原因。`url.<路径>.pushInsteadOf=""` 改写每个远端和直接写出的地址；远端单独设了 `pushurl` 的，`pushInsteadOf` 管不到，每次运行命令前读出这些地址，再用 `insteadOf` 改写。`insteadOf` 拉取也用，而且按前缀匹配：以某个 `pushurl` 开头的拉取地址另加一条改写成它自己的规则，更长，拉取时它优先；`pushurl` 和某个远端的拉取地址完全相同时分不开，这个推送地址不改写，推送拦不住（`git remote set-url --push` 填了同一个地址时会这样）。只改环境，用户签出里的配置不动，用户自己在那台机器上推送不受影响；拉取照常。没有代码托管时，推送归用户：合并后用户自己推。搭配代码托管时，推送只走 `push_branch`（见下文）。这挡住的是失误和习惯，不是蓄意绕开的讨论串：命令可以清掉环境变量，或者用别的程序连远端，远端用户的凭据它都拿得到。

SSH 来源的远端代码（工作区、脚本、对 `RemoteShell` 的约定）在 `@ariadne/remote` 包里，SSH 和下面的 daemon 都只提供传输：把一段 bash 脚本和参数交给远端的 `bash --norc --noprofile -s`，送输入、收输出和退出码、能中途结束。

### 远程 daemon

daemon 来源（内置插件 `plugin-daemon`）给连不了 SSH 的机器用：容器、只开一个端口的云主机。远端运行 `ariadne-daemon`（`@ariadne/daemon`，`bun run build:daemon` 打出 Linux 和 macOS 的单文件程序），项目来源里填它的地址、配对码和远端目录。工作区、worktree、改动和合并与 SSH 来源完全相同。

- 方向只有一个：Ariadne 去连 daemon，daemon 不主动连任何地方，Ariadne 自己照旧只听 127.0.0.1。daemon 默认只听远端的 `127.0.0.1:7429`；`--listen` 换成别的地址时启动日志会提醒其他机器也能连上来。
- 连接总是 TLS。daemon 第一次启动时用 `openssl` 生成一张自签的 P-256 证书（名字是 `ariadne-daemon`），Ariadne 不走 CA：每次连接先取 daemon 的证书，核对它的 SHA-256 指纹和配对码里的一致，再把这张证书当成唯一可信的根去建真正的连接，令牌只在这条连接上发出。指纹对不上就断开，并说明是另一台机器在应答，或者 daemon 换了证书。
- 配对码是 256 位随机令牌加证书指纹，第一次启动或 `ariadne-daemon pair` 时打印一次。daemon 只存令牌的 SHA-256（`~/.ariadne-daemon/token.sha256`），每次认证都重新读，`pair` 换掉的旧令牌立即失效（已经连着的连接不受影响）。令牌放在 `Authorization` 头里，不进 URL；同一个地址十分钟内错十次，之后的十分钟一律拒绝。
- Ariadne 这边，配对码是来源的私密设置，和 GitHub 令牌一样存在 `~/.ariadne/config.json`，不进事件日志、追踪和错误信息，浏览器只知道它设过没有。
- 一条 WebSocket（`/v2/relay`）上跑一个 relay 会话，每个调用是其中一个 `exec` 通道。连之前先用 `/v1/hello` 核对令牌和协议版本，版本不同直接拒绝，并提示两边用同一个版本；这个地址各版本都不变，新旧两边总能互相认出来。连接断了，Ariadne 在两分钟内不停重连并接回原来的会话，进行中的调用照常跑完，输出一个字节也不丢；令牌被拒、指纹对不上这类重连也没用的情况不再重试。两分钟内没接回来，调用以退出码 255 结束，daemon 关掉这些调用的输入（命令的看守进程据此结束进程组），两秒后再强制结束。
- daemon 直接运行每个调用，没有沙箱：讨论串的命令以运行 daemon 的用户身份执行，能读到 `~/.ariadne-daemon`（证书私钥和令牌哈希）。给 daemon 单独一个用户，就把它和那台机器上的其他东西分开了。
- 拿到令牌就等于拿到 daemon 所在用户的 shell，和 SSH 私钥一样。所以默认只听回环、远端不存明文、连接必须过 TLS，建议用一个单独的系统用户运行 daemon。
- daemon 暂不支持在 Windows 上运行。
- `ariadne-daemon --stdio` 不监听端口，在标准输入输出上跑同一种 relay 会话，供 SSH 来源使用：谁能连上由 ssh 决定，所以不需要令牌和证书，也不需要 openssl。

### relay 会话

`@ariadne/relay` 是 Ariadne 和远端之间的传输层：一条连接上跑多个通道，带背压，断线后能接回。daemon 和经 SSH 启动的 daemon 都用它，以后别的长连接（比如给浏览器推流）也用它。

- 连接（`Link`）只要求按顺序、整帧送达：WebSocket 本身有消息边界；管道这类字节流在每帧前面加一个变长整数表示长度。
- 帧：一个字节的类型，后面是这个类型的字段，最后是载荷。通道号、流号、额度这些数字都是变长整数；控制消息用 msgpack（不用它的记录扩展：那份结构表存在连接上，接回会话时会丢）；命令的输入输出是原样的字节，不转码。一个输出帧的开销是 3 到 8 个字节。
- 通道：`OPEN` 打开（带类型和参数），`DATA` 带流号（`exec` 通道里 0 是输入，1、2 是标准输出和错误输出），`CONTROL` 发控制消息，`CLOSE` 两个方向一起关，带退出码或错误。同一个通道上的写入、控制消息和关闭按调用的顺序发出。
- 背压：每个通道每个方向先有 2MB 的额度，收到的一方每处理完四分之一就用 `CREDIT` 还回去，发的一方额度用完就等；WebSocket 连接本身积压超过 4MB 时也等（管道看不到积压，只靠通道额度限住）。daemon 读命令输出时等着写进通道，输出再多也只是让命令慢下来，不会在内存里堆积。
- 接回：`OPEN` 及之后的类型都要可靠送达，两边各自给发出的这些帧计数，留到对方用 `ACK` 确认（每 64 帧或 256KB，最迟 100 毫秒确认一次）。重连后，`HELLO` 和 `WELCOME` 里各自报出收到了多少帧，对方从那里开始重发，所以不丢也不重。服务端没有这个会话了（重启过，或者等得太久），客户端的通道以错误结束，下一个通道开新会话。
- 客户端每 15 秒发一次 `PING`，45 秒没收到任何东西就当连接已经断了，主动重连。没有通道时连接断了就断了，下次要用再连。

### 远程目录搭配托管仓库

SSH 和 daemon 来源可以再选一个代码托管（GitHub 或 GitLab，`ContextProvider.hosting`）：讨论串在远端写代码，PR、检查和 issue 走托管仓库，推送在本机做，托管的令牌从不去远端。

- 远端目录必须是这个托管仓库的签出：连接时比对它 `origin` 的主机和路径（`https`、`ssh://`、`git@host:path` 写法都认），不是就拒绝，免得把别的仓库的提交推上去。
- 提交在两边的 git 之间用 git bundle 搬（`GitObjects`）：本机在自己的共享 clone 里 fetch，再把远端没有的提交打包，经同一条连接送过去，更新远端的 `origin/*`；推送时反过来，把讨论串的分支从远端打包带回本机的 clone，再由本机推送。打包只含对方没有的提交，两边共有的提交作为前提。远端用户自己的分支不动。
- 新讨论串的分支从刚同步过的 `origin/<默认分支>` 建出，改动对比的也是它；合并走 PR，所以没有“合并到基线”。推送后远端的 `origin/<分支>` 跟着更新。托管仓库上已经删掉的分支，同步时远端签出里对应的 `origin/<分支>` 也删掉，和 `git fetch --prune` 一样；`origin/HEAD` 指向别的 ref，不动。
- 其余同托管仓库：推送和开 PR 用 `push_branch`、`open_pull_request`，公开仓库第一次推送前问一次。讨论串自己在远端用 `git push`（用远端的凭据）推不出去，见上面的 SSH 一节。

### 仓库、PR 与 CI

项目来源是托管仓库时，讨论串多五个工具：`repo_status`、`sync_branch`、`push_branch`、`open_pull_request`、`read_check_log`。

- 讨论串推送自己的分支、开 PR 不需要先问用户：只动它自己的 `ariadne/…` 分支，PR 可以关闭，合并由用户决定（托管推进的项目除外）。公开仓库例外：第一次推送前进“需要我”问一次（带 `purpose` 的 Attention，按仓库区分）。同意对整个项目有效；同时想推送的讨论串共用一张卡片（`attention.joined`），卡片上列出所有在等的讨论串，它们都显示为“等你”，回答后一起被唤醒；拒绝只对等这张卡片的讨论串有效，之后别的工作可以再问。用户关掉的 PR，`open_pull_request` 不会再开新的，讨论串要问用户或报告受阻。
- 推送从不强推；远端分支变过的话推送被拒，提示讨论串用 `sync_branch` 取回远端的提交（只更新 `origin/*`，不动本地分支），合并 `origin/<分支>` 或 `origin/<默认分支>` 后再推送。PR 被 squash 合并后继续工作，先合并最新的默认分支，下一个 PR 只含新的改动。
- 开了 PR 的讨论串由仓库监视器定期（默认每分钟）读取 PR 和最新提交的检查，有变化才记一条 `pull_request.synced`。最新提交的检查失败时记 `checks.failed`，唤醒那个讨论串去读日志、修复、再推送；同一个提交只唤醒一次。连续第 3 次失败时，讨论串被告知不要再试，报告受阻、说明试过什么，讨论串进入 `blocked`、出现在“需要我”；之后的失败不再唤醒它，只继续计数。检查通过、PR 被合并或关闭，或用户在讨论串里发消息，就重新计数。协调器用 `message_thread` 仍能唤醒它，它推送后的失败照样不唤醒它，直到计数重来。PR 被合并或关闭时记 `pull_request.closed`，协调器收到说明。
- 界面在讨论串标题旁显示 PR 编号、检查状态，可以手动刷新；看板卡片上也显示。
- GitLab 上 PR 是 merge request：`PullRequestInfo.reference` 是 `!12`（GitLab 里 `#12` 指 issue），界面和工具结果都用它。草稿 MR 用标题前缀 `Draft:`。检查来自提交的 commit status（流水线里的 job 和外部 CI 报的状态），同名的只取最新一个；允许失败的 job 失败记为 `neutral`，手动 job 记为 `skipped`，都不算失败。日志是 job 的 trace，去掉终端颜色和折叠段标记，外部状态没有日志。`internal` 可见性对实例上所有登录用户可见，按公开仓库处理，第一次推送前同样先问用户。找讨论串分支的 MR 时只认本项目自己的分支，fork 里同名分支的 MR 不算。
- 消息里的 MR 链接（`<实例>/<group>/<project>/-/merge_requests/<编号>`）和 GitHub 的 PR 链接一样显示成 `group/project!12`，悬停看状态、标题、作者和文件数（GitLab 不给增删行数，卡片上不显示；超过 1000 个文件时也不显示文件数）。认得的实例：GitLab.com、`GITLAB_HOST` 指的实例，以及本次启动以来连接过的 GitLab 来源的实例；读卡片先用链接所在项目的来源里填的令牌，再试同一实例上其他来源的令牌，最后是同上的环境变量和 `glab`；读不到（401、403、404）才换下一个，令牌不会发给别的实例。

### Issue

项目来源有 `tracker` 能力时（内置的 GitHub、GitLab 来源有），issue 是工作的上下文。

- 协调器和讨论串都能用 `list_issues`、`read_issue` 读 issue，用 `link_issue` 把 issue 关联到计划节点（或取消）；讨论串只能关联到自己的节点。关联记成 `plan.issue_linked` / `plan.issue_unlinked`，立即生效，节点详情里列出、写明是谁关联的、能取消；agent 关联或取消时在它自己的对话里显示一行。用户也可以在节点详情里按编号关联。搜索只用词语：`repo:`、`org:`、`is:` 这类限定词和 AND/OR/NOT 会被去掉，结果也只保留本仓库的，令牌能读到的其他仓库不会混进来。删掉节点时它的关联一起删掉。节点的讨论串在系统指令里看到关联的 issue 编号，内容用 `read_issue` 读。
- issue 的标题、正文和评论是任何能提 issue 的人写的，工具结果里放进以内容哈希命名的数据块（`fenced()`，和项目记忆、AGENTS.md 同一套），并说明它们是信息不是指令。`read_plan` 和系统指令里只放编号，不放标题。
- 改 issue（`comment_on_issue` 评论、`set_issue_state` 关闭或重新打开）会通知别人、撤不回，只有讨论串能做，而且每次都要用户同意这一个改动：卡片里写着 issue 和完整的评论内容或关闭原因（带 `purpose` 的 Attention，按 issue、动作和内容的完整 SHA-256 区分，正在问的同样改动共用一张卡片）。用户同意后讨论串用同样的参数再调一次才真正执行。一次同意只用于一次改动：执行前记 `issue.writing`（带用到的 attentionId），成功后记 `issue.written`；之后同样的改动（比如关闭、重新打开后再关闭，或再发一遍同样的评论）要重新问，换了内容也要重新问。同意按项目区分。等同一张卡片的几个讨论串共用这次同意：其中一个做了改动，其余的会收到一条通知（谁做的、链接）；还没读到这条通知就再调用的，直接得到“已经做过”，不会被重新问，也不会再发一遍；读到之后再要同样的改动就是新的工作，照常重新问。改动正在进行时（同一进程里请求还没回来），再调用的讨论串被告知“正在做”，并加入这张卡片，结果出来后一起收到通知；正在进行的改动不会被当成“中途断掉”。如果记了 `issue.writing` 却没等到结果（Ariadne 中途停了，或者请求失败），这次同意就作废，讨论串被告知先用 `read_issue` 核对改动是否已经生效，没有生效再调用才会重新问用户，不会盲目再做一次；卡片上其余的讨论串也会收到这条消息。拒绝的不做。讨论串的对话里显示一行“在 … 下发表了评论 / 关闭了 …”，带链接。
- issue 请求和仓库请求用同一个服务端的 API 客户端，令牌只在服务端，讨论串的命令读不到。
- GitLab：issue 编号是项目内的 `iid`；搜索用项目自己的 issues 接口，本来就只在这个项目里找；读 issue 时去掉 GitLab 自动写的系统备注（改标签、改描述之类），只留最新 20 条评论；关闭没有原因可选，`not_planned` 和 `completed` 都只是关闭（卡片上仍按讨论串给的原因显示）。

### 产物

产物有三种，各用对应的 dou-ui 包展示和编辑，存下来的内容就是那个组件的数据格式：

| 种类   | 内容                                                                         | 界面                                                         |
| ------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 文档   | Markdown                                                                     | `@dou-ui/editor` 块编辑器                                    |
| 画板   | `@dou-ui/flow` 的 `FlowDocument`，节点是白板的形状、便签、文字、笔迹和图片   | `DouFlowEditor` 加 `whiteboardKit()`                         |
| 仪表盘 | `{ dashboard, data, takenAt }`：`@dou-ui/dashboard` 的文档，加上格子读的数据 | `DouDashboard`，内置格子：统计数字、文字、表格、图表、透视表 |

- 仪表盘默认是静态快照：数据在写入时复制进来，每个数据源只是交回存下的值，不再请求；界面显示“数据截至”的时间。要更新就写入新的数据，`takenAt` 随之更新。
- 插件可以用 `registerDashboardSource({ kind, title, description, settings, fetch })` 提供实时数据。仪表盘带上 `source: { kind, settings }` 就成了“实时数据”：agent 用 `create_dashboard` / `update_dashboard` 的 `source` 建立时先取一次，之后 agent 用 `refresh_dashboard`、用户在仪表盘上点“刷新数据”时再取，取回的数据集替换同名的那些，存成一个新版本（`takenAt` 为当时），所以每个版本仍是一份能回放的快照。`list_dashboard_sources` 列出插件提供的来源；`update_dashboard` 给 `source: null` 就变回静态快照。来源所在的插件没加载时刷新会报错，已有的数据不受影响。模型给的 `settings` 先按来源的 schema 检查（只认声明过的字段、类型要对、必填要有，缺的用默认值），而且会原样记进事件日志，所以标了 `secret` 的字段不能在这里设，凭据放在插件自己的配置里。每次取数最多等 30 秒，取回的必须是一个对象、不超过 2MB，建立和刷新走同一套检查。
- 保存前 core 检查内容的形状（id 不重复、连线两端存在、格子读的数据源存在、只用注册过的类型），不合格的拒绝，错误原因回给 agent 修正。
- agent 一般不写坐标：画板工具收条目和连线。新画板用 dou-ui 的 `layoutGraph` 沿连线分层排版（默认从上到下，可选从左到右）：盒子按文字长度定宽高，层间留出最长标签的宽度，跨层的长连线把经过点写进 `points`，从中间各层的空隙穿过；不相连的几部分分块打包，孤立条目排成网格。agent 想摆出排版做不到的构图（左右对比、环形）时可以给坐标，这时保留它的构图，按 x、y 分别拉伸到条目不重叠、带标签的连线放得下标签。
- 修改按 id 合并，只改给出的字段，用户画的笔迹、贴的图片和挪过的位置都保留。新条目放在它连出的条目旁边（隔一个标签的距离），否则放在已有内容下方，再挪到不重叠；条目改字变高时，它下方的条目一起往下挪。`relayout` 把笔迹和图片以外的条目整张重排。连线选两个条目相对的一边，两端挪过的连线清掉 `points`。
- 画板检查：建好、改完和读取画板时，工具结果带上 `problems`，列出条目重叠、文字放不下、连线穿过条目、标签压在条目或别的标签上（连线按经过点之间的直线估算）。用户改过的画板 agent 读到时也能看到，自己用 `update_whiteboard` 修。
- 文档里也能放画板（`@dou-ui/editor/flow` 的 `whiteboardBlock`），Markdown 里是 `dou-whiteboard` 代码围栏，内容为 `{ height, board }`。页面和服务端的文档扩展必须一致，否则一边不认识的块在另一边写回 Markdown 时会丢掉。agent 读到的文档里，每块画板换成 `whiteboard` 围栏，内容是和画板工具一样的条目和连线（每行一个，不带坐标），并按“第几块画板”列出 `problems`；写回时（`document-boards.ts`）和读到时一字不差的围栏保留原样，改过的围栏按它在各块画板中的位置对应回原来那块，当作整张画板按 id 合并（没写的条目和连线删掉，用户的笔迹和图片只能挪），新的围栏按画板的规则排版，高度按排出来的大小定（最多 480px）。边写边显示时，没写完的画板先显示成占位。搜索收录画板上的文字，产物列表的预览跳过画板。文档里的画板暂时不能评论（dou-ui#447）。
- 仪表盘工具同样按 id 合并，新格子按顺序排进 12 列。
- 占位：agent 可以先放占位、再逐个填上。文档里是单独一行的 `<pending>这里要写什么</pending>`（编辑器扩展 `pending` 块，灰字加方括号），画板里是 `kind: "pending"` 的条目（虚线灰框的自定义节点），仪表盘里是 `type: "pending"` 的格子（`props.text`）。画板条目和仪表盘格子之后用同一个 id 改成真正的类型，位置和连线不变；`pending` 不出现在用户的工具栏和控件面板里。
- 边写边显示：模型写工具参数时，provider 把已写出的参数文本以 `tool-input` 流出，runner 宽松解析这段没写完的 JSON（`partial-json.ts`），约每 120 毫秒交给带 `live` 的工具。`update_document`（`edits` 逐条替换，或 `content` 整篇重写、按行对齐出“已写到哪”）、`update_whiteboard`（只取已写完整的条目和连线）和 `update_dashboard`（只取已写完整的格子，加上已写完整的数据集）在有人打开着这个产物时，把目前为止的内容写进它的共享房间，页面上内容随写随出；调用真正执行时接着这份内容收尾，只产生一个版本。调用失败、被打断或模型中途断开时，已写进去的部分用 Yjs 的 UndoManager 撤回。写到一半的内容不存成版本，也不写进 `artifact_shared`（留着的是开始写之前的状态，进程被强杀后重开看到的也是它）；服务停止时还没写完的先撤回。用户在这期间自己改的内容，等这次写入结束时单独存成用户的版本（存的那一刻先把 agent 的部分撤出、存完再放回），撤回时则按平常的间隔存。每一片的间隔不少于 120 毫秒，也不少于上一片耗时的 3 倍，长文档上不会占满服务。没人打开时不写，行为和以前一样。新建产物不流式显示，所以提示里让 agent 先建带占位的骨架、再分次填。
- agent 的光标：往共享房间里写的时候，服务端在房间的 awareness 里放上写的那一方（“协调器”或讨论串标题），文档里是带名字的光标（`editor` 字段，用 dou-ui 的 `cursorAt` 得到），画板里是内容有变的条目的外框，仪表盘里是刚写的格子的外框（`dashboard` 字段），写完后留 2.5 秒。占位条目用 `ports: 'sides'`，连接点和内置形状一样悬停时才显示。仪表盘也在共享房间里：格子在 `widgets`，数据、来源和截取时间在 `snapshot`；用户改布局随改随存，不再有单独的草稿和保存，刷新数据也写进房间，布局的改动保留。仪表盘的改动不作为反馈发给 agent，也没有评论。外部 agent provider（Claude Code、Codex、ACP）不流出工具参数，只有落笔时的光标和占位。
- agent 读画板时，笔迹和图片只列出 id 和位置，不带点阵和图片数据。
- 画板上粘贴、拖入或选取的图片先上传成文件，画板里只存它的地址（`/api/files/<id>`）。旧的画板或别处写进来的 data URL 图片，在保存时由服务端转成文件，内容里换成地址；历史版本保持原样。文件按项目和内容去重，存在数据库的 `files` 表里：它不是投影，重建投影不会丢，也从不删除，旧版本始终能显示。只收 PNG、JPEG、GIF、WebP、AVIF，单个最大 10 MB；不收 SVG（可以带脚本）。
- 图片地址不带令牌也能读（`<img>` 发不了请求头），靠随机的长 id 防猜，并且只允许本站页面引用（`Cross-Origin-Resource-Policy: same-origin`），内容不会变，浏览器可以一直缓存。上传要令牌。
- 每次保存是一个新版本，旧版本可以查看和恢复（恢复也是一个新版本）。改名也是一个新版本。
- 保存时带上起始版本号；期间别人保存过就拒绝，用户和 agent 不会悄悄覆盖对方的修改。
- 用户修改了 agent 写的产物，作者在下一个回合会看到提示。
- 项目的产物总览按种类筛选、按标题和内容搜索，卡片上是内容的摘要（文档开头、画板里的文字、仪表盘的格子标题）、关联的计划节点和数据时间。摘要在产物保存时算好存进投影，列表不再读整份内容。用户也可以在这里新建空的文档、画板和仪表盘。

### 协调器与讨论串的消息

- 讨论串之间不直接通信。讨论串的请求发给协调器，由协调器决定转发、合并还是驳回。上游节点的产出摘要随依赖自动交给下游。
- 协调器发给讨论串的消息在讨论串面板里显示为一条淡化、默认折叠的提示，点开可看全文。
- 讨论串发给协调器的消息不在任何面板展示；需要用户决定的事由协调器推到“需要我”。
- 用户在任何讨论串里发消息时，协调器同时做一次轻量分诊，讨论串不用等它；如果有更合适的讨论串或者应该另开一项工作，协调器把请求转过去，并提醒当前讨论串用一句话告诉用户去了哪里。用户说“就在这里做”时，协调器以后对同类请求不再转交。分诊不需要转交时，协调器不说话。
- 消息只能由作者自己编辑。编辑是一条事件，界面显示“已编辑”，点开能看到编辑的原因和最初的原文；用户读过的消息被编辑后，下次打开时高亮一次。

### 对话里的界面块

协调器和讨论串用 `post_ui` 发一条带界面块的消息：文字写在前面，块排在下面。块的类型只有内置的一组，每种都映射到 dou-ui 的组件，不渲染模型写的脚本或 HTML，插件也不能注册新类型：

| 块        | 用途                                         | 组件                    |
| --------- | -------------------------------------------- | ----------------------- |
| `choice`  | 从 2 到 6 个选项里选一个，可以标推荐         | ChatSuggestions         |
| `confirm` | 对一个动作说同意或不同意，可附上要执行的内容 | ChatConfirm + CodeBlock |
| `form`    | 一次填几个值：文字、数字、单选、多选、开关   | Form                    |
| `table`   | 最多 200 行的数据                            | Table                   |
| `chart`   | 折线、面积、柱状、饼图                       | @dou-ui/chart           |
| `steps`   | 一组有先后的步骤和各自的状态                 | Steps                   |
| `thread`  | 项目里一个讨论串的入口，跟着显示它的状态     | ChatArtifact            |

- 每个块都在 `@ariadne/core` 的 `parseBlock` 里按类型检查，补齐省略的字段后才存进事件；不合规的块整条消息都不发，模型拿到具体哪一项不对。前端直接把存下的块交给组件。
- 选项、确认和表单是“提问”：一条消息最多一个，排在其他块后面。它就是一个 Attention（带 `messageId`），同时出现在消息里和“需要我”里，在哪边回答都一样。回答（`attention.answered`）也按块检查：选项只能选列出的，表单的值必须符合各字段的类型、必填和范围。回答以 `<user_answer>` 交给提问的会话并唤醒它；消息里的块原地显示答案。
- 提问可以撤回：用户没点块、直接打字回答了，或者问题已经不重要了，提问的会话用 `withdraw_ask` 撤回它（`attention.withdrawn`，带一句理由）。撤回的提问离开“需要我”，消息里的块只留下问题和“已撤回：理由”，之后再回答会被拒绝。用户在有未回答提问的对话里发消息时，模型在这条消息后面看到当时还开着的提问（`<open_questions>`，记在 transcript 里，所以可以重放），由它判断这条消息是不是回答了哪一个。只有提问的会话能撤回自己的提问；系统自己的确认（公开仓库的推送、改 issue、计划提议）不能撤回。
- 系统自己的确认（公开仓库的第一次推送、改 issue、计划的大改动）也是 `confirm` 块，只出现在“需要我”里（计划提议另有计划图上的提示条）。
- 表格、图表和步骤只用来展示；agent 自己的进度仍然写在待办清单里，不用步骤块。
- `thread` 块只存讨论串的 id，`postMessage` 检查它是这个项目的讨论串。前端每次按项目里的讨论串列表画：标题、最近一次汇报和当前状态（图标：进行中转圈，其余按状态着色，悬停显示状态名），所以状态变了卡片跟着变；点开在右侧打开这个讨论串。协调器告诉用户开了哪些讨论串时用它。
- 行内的讨论串入口跟消息的 Markdown 渲染一起做：消息里写 `[文字](thread:<id>)`，渲染成可点击的讨论串标题，后面跟着它的状态图标；id 不是这个项目的讨论串时只显示文字。产物和工作区文件的行内引用用同一套写法（`artifact:<id>`，`path:line`）。

### 附件与图片

- 用户在输入框里粘贴、拖入或点回形针选文件，选了就上传（`POST /api/projects/:id/files?for=message`），存进项目的 `files` 表，消息只记文件 id、名字、类型和大小（`message.posted` 的 `attachments`），一条最多 10 个。能发的是图片（PNG、JPEG、GIF、WebP、AVIF，最大 10 MB）和 UTF-8 文本（代码、日志、笔记，最大 1 MB；浏览器怎么叫它的类型不重要，按内容判断，存成 `text/plain`）。超过 5 MB 的图片在浏览器里先缩小再上传（长边最多 2560，JPEG），模型服务收不了更大的。画板仍然只收图片。
- 消息里的图片点开是大图预览，文本文件在新标签页打开。`/api/files/:id` 不需要令牌（`<img>` 带不上），地址是随机的，只允许同源加载，文本按 `text/plain; charset=utf-8` 和 `nosniff` 返回。
- 模型读到的是：文本文件的内容放在名字带内容哈希的数据块里（同 AGENTS.md 的做法，超过 10 万字截断）；图片跟在这条消息的文字后面。两种协议都直接发图片：Anthropic 协议放在消息和 `tool_result` 里，OpenAI 兼容协议放在消息的内容数组里，工具结果里的图片因为协议不支持，紧跟在这一步所有工具结果后面，作为一条注明来自哪次调用的用户消息。
- 图片在每次请求时才从 `files` 表读出、编码，transcript 里只有文件 id，所以事件日志不会因为图片变大，追踪视图也按文件显示。一次请求最多带最新的 20 张图片，更早的换成一句“之前看过”的说明；超过 5 MB 或模型服务不认的类型（AVIF）也只用文字说明。估算上下文时每张图片按 1600 token 算。
- “设置 → 模型”里每个模型有“看图片”开关，默认打开；关掉后（例如只收文字的模型）图片一律换成文字说明，模型知道有图但看不到。每一步记下这次有没有发图片（`turn.step` 的 `input.images`），追踪视图据此重建当时的请求。带图片的请求被拒、又不是可重试的错误时，报错会提示去关掉这个开关（`error.modelRequestImages`），不支持图片的服务（例如 DeepSeek）会一直这样拒绝。
- 讨论串的消息里链到工作区图片的 Markdown 链接，发出时存一份进 `files`，改写成 `file:fil_…`。代码里的链接只是文字，不改写：围栏代码块（同种字符、不短于开头的围栏才算结束，没结束就到消息末尾）、缩进代码块（空行之后缩进四格或一个 Tab；在列表里从列表项内容的缩进算起）和行内代码（同样长度的反引号之间，不跨空行）。
- `read_file` 读到 PNG、JPEG、GIF、WebP（按扩展名，再核对文件头）时，把图片存进 `files` 并交给模型看（`tool.finished` 的 `files`）；超过 5 MB 的会让模型先缩小一份再读。读到不是文本的其他文件时说明是二进制，不再把乱码交给模型。工作区为此多了 `readBytes`（SSH 工作区用 base64 传）。

### 联网

- `fetch_url`：服务端抓取一个 http 或 https 地址交给模型。网页转成接近 Markdown 的文字（标题、列表、带地址的链接和图片、代码块），去掉脚本、样式、导航和页脚；纯文本、JSON、XML 原样给；PNG、JPEG、GIF、WebP 存进 `files` 当图片给模型看；其他类型说明读不了，讨论串可以用 `run_command` 下载到工作区。一次最多 2 万字，用 `offset` 接着读；响应最多读 5 MB，30 秒没答完就放弃。
- 抓到的文字放在名字带内容哈希的 `web_page_…` 数据块里，标明是网站作者写的信息，不是指令。模型的系统指令也写明不照网页里的要求做、不把私密内容放进要抓取的地址。
- 只读公网：服务和 Ariadne 本身、本机其他服务、局域网在同一台机器上，网页不应借它摸到这些。解析出的地址只要有一个是回环、私有、链路本地、共享（100.64/10）、组播或未指定地址（IPv4 映射的 IPv6 地址按里面的 IPv4 算）就拒绝；198.18/15 不拒，开 fake-ip 模式的代理会把所有域名解析到这一段；重定向手动一跳一跳地跟，每一跳都重新检查，最多 5 跳；带用户名密码的地址不抓。不带 cookie 和任何凭证。检查和连接之间域名可能被换成别的地址（DNS rebinding），这一点没有防住；本机服务要访问时在讨论串里用 `run_command`。
- `web_search`：有东西能搜时才有这个工具，按这个顺序用：插件带来的搜索服务（`registerSearchProvider`，装了几个时可以选用哪个）；模型接口自带的搜索（`ModelProvider.search`）；用户在「设置 → 模型」里填了 Key 的搜索服务（Tavily）。
  - 模型接口自带的搜索：Anthropic 接口用 Messages 的搜索工具，OpenAI 兼容接口用 `responses` 端点的搜索工具，都只在地址是官方地址时才算有（中转地址和其他厂商的兼容接口当作没有）。一次搜索是对话之外的一个单独请求：让模型搜一下、用不超过三百词说清结果，连同它读到的页面（标题、地址、引用的原文）一起作为工具结果交回，对话自己的请求格式不变。先问对话自己的模型，再问子调研的模型和设置里其他的模型，最多问两个；失败就落到填了 Key 的搜索服务。接口明确拒绝搜索时（4xx，超时和限流除外，比如账号关掉了搜索、这个模型不支持），这个模型在重新保存模型设置之前不再算作能搜，设置里的 Key 输入框随之出现。这个请求的 token 记一条 `search.answered`，计入这个对话的用量。
  - 都没有时没有这个工具，`fetch_url` 的说明里会告诉模型：需要搜索时让用户去设置里填搜索 Key。设置里的 Key 输入框也只在这种时候出现（配了模型、它们的接口都不带搜索、也没有插件带来搜索服务），或者已经存了 Key。Key 存在 `config.json` 的 `search.apiKey`，不发给浏览器。
  - 插件自己保管它的凭证（环境变量或它自己的配置），Ariadne 不经手；搜索出错的原文不交给模型，也不进事件日志，免得带出密钥。结果放在 `search_results_…` 数据块里。
- 协调器和讨论串都有这两个工具；协调器只用来快速看一眼用户给的链接，成规模的调研交给讨论串。
- 接受的风险：能联网就可能被网页或文件里的指令诱导，把项目内容拼进地址发出去。系统指令要求不这样做，但挡不住；和上面的 DNS rebinding 一样，目前没有技术手段防住。

### 外部工具（MCP）

- 外部工具用 MCP 协议接入，Ariadne 自己实现客户端（`@ariadne/mcp`）：本机命令（stdio，每行一条 JSON-RPC）和 HTTP（每条消息一个 POST，回答是 JSON 或事件流，会话 id 跟着后续请求）两种连接方式。客户端只取工具、调工具，不向服务提供采样、根目录或追问，只回应它的 ping。
- 服务在“设置 → MCP”里配置，存在 `~/.ariadne/config.json` 的 `mcp.servers`：名称、标识（小写字母、数字和横线，最多 20 个字符，是工具名的一部分）、命令和参数（或地址）、工作目录、环境变量（或请求头）和每个工具的标记。环境变量和请求头的值当作密钥：只留在服务端，页面只拿到名字，留空保存就保留原值。不从仓库里读任何配置。
- 每个项目在“项目来源”的编辑表单里选用哪几个服务（`project.mcp.set`），选了的服务的工具才出现在这个项目的会话里，模型看到的名字是 `mcp__<标识>__<工具名>`。
- 工具多时按需查看：一个会话的外部工具定义合起来超过约 8000 token（服务多，或者一个服务带几十个工具），就不再逐个交给模型，换成两个工具：`mcp_call` 的说明里按服务列出每个工具的名字和一句话（服务自己写的描述的第一句），`mcp_describe` 按名字给出完整说明和参数，`mcp_call` 按名字带参数调用，确认、输出处理都和直接调用一样。工具列表在一个对话里保持不变，查到的定义作为工具结果留在对话末尾，所以提示缓存不受影响：查到之后不往工具列表里加工具。
- 每个工具有三种标记：“只读”直接调用；“要同意”（默认，没标过的工具都是这样）每次调用先出一张确认卡片，卡片上是完整的参数，出现在“需要我”里；“不用”不交给模型。协调器只拿到“只读”的工具，其余的只给讨论串。
- 同意只对这一次、这组参数有效（`attention` 的 `purpose` 是服务、工具和参数按键排序后的 SHA-256），用掉时记一条 `approval.used`，同样的调用再来就再问；参数换了也再问。拒绝后，同样的调用一直按拒绝处理，直到用户在这个讨论串里再写一句话。参数按缩进 JSON 超过 1 万字的调用直接拒绝，用户看不完的东西不让同意。
- 服务第一次被用到时才启动或连接，之后一直保持；设置改了（工具标记除外）就断开，下次用时重连。一个回合开始时最多等还没连好的服务 5 秒，等不到这一回合就不带它的工具，连接在后台继续；启动加列出全部工具共用一个 60 秒的时限。失败的原因和本机命令最后写到 stderr 的内容显示在设置里，之后 1 分钟内不再重试，连续失败时间隔逐次加倍、最多 15 分钟，点“连接”立刻重试。HTTP 服务不认得会话了（404）不算失败：下次用时重新 `initialize`，当时那次调用服务没有执行，换新会话再发一次。服务说工具变了（`notifications/tools/list_changed`），下次用时重新列出。一次调用最多 5 分钟，用户停下这一回合时调用随之取消（`notifications/cancelled`）；单条消息超过 20 MB 就断开连接，进行中的调用立刻失败。
- 本机命令和讨论串的命令一样直接运行（见“工作区”），工作目录不能设在 Ariadne 的目录里；环境变量从去掉服务端凭证的环境出发，再加上用户给的；它有自己的进程组，关掉或它自己退出时，它启动的进程一起结束。HTTP 服务不跟随重定向，请求头只发到用户填的地址。
- 工具返回的文字放在名字带内容哈希的 `tool_output_…` 数据块里，标明是工具写的信息，不是指令；图片存进 `files` 交给模型看；超过 5 万字时只留开头和结尾，讨论串的工作区已经开着时，在 `.ariadne/output/` 里拿到全文（`*.mcp.txt`，可以再搜索或分段读）；不会为了存它新开一个工作区，协调器、评审和还没有工作区的讨论串只拿到截短的。服务拒绝调用时写的理由也放进同样的数据块；协议版本对不上时不转述服务给的版本号。工具输出、错误信息和 stderr 里出现的环境变量或请求头的值（4 个字符以上）都替换成 `[secret]`，普通的值（比如 `NODE_ENV=production`）也一样，宁可多替换；连接失败时模型只拿到简短原因，stderr 只给用户看。确认卡片和设置页显示工具的真名，服务自报的标题只作补充。
- 接受的风险：服务和它的工具描述是用户自己选的，Ariadne 信任它们不说谎；“只读”是用户的判断，Ariadne 不核实。HTTP 服务还没有 OAuth 登录，需要令牌时填在请求头里。

### 项目记忆

项目记忆是项目的长期偏好和事实（“提交信息用中文”“接口在 packages/server”），项目里所有会话都遵守。

- 协调器在用户说出长期偏好、或确认了工作反复要用的事实时，用 `remember` 记下，用户收回时用 `remember` 改写或 `forget` 删掉；进度、计划和一次性的请求不进记忆。
- 记忆会进到每个会话的指令里，所以只有用户自己的话能改它：`remember` 和 `forget` 只在这一回合的输入里有用户的消息、对提问的回答或在讨论串里写的话时可用。只由讨论串汇报或转来的消息触发的一回合里，它们被拒绝；讨论串读到的文件、日志和网页可能带着伪装成偏好的指令。讨论串听到用户直接告诉它的偏好时在汇报里提一句，协调器向用户确认后再记下。
- 记忆以 `<project_memory_…>` 数据块出现在协调器和每个讨论串的系统提示里，带着条目 id，记下或改动后下一步就生效。每条存成一行（换行压成空格），显示时尖括号（包括全角的）也被替换，一条记忆伪造不出新的提示段落；数据块的标签名带着内容哈希的前 12 位（和 AGENTS.md 共用一套做法），内容写不出自身的哈希，也就闭合不了数据块，块内任何写法的裸标签名都会被拆成普通词；提示说明它们是关于工作的偏好，不能推翻工作方式和需要用户同意的规则。
- 协调器每次改动记忆，在它的对话里留一行说明（记下了什么、改成什么、删了什么），带“撤销”：撤销新增就删掉，撤销修改就恢复原文，撤销删除就加回来。
- 用户在项目设置“指令”页的“记忆”里查看、添加、修改和删除，和项目指令放在一起。每条最多 500 字，每个项目最多 50 条。每次修改是一个事件（`memory.saved`、`memory.removed`），记着是谁改的、撤销的是哪一次改动。

### 插件

模型协议、项目来源、仪表盘的实时数据来源和网页搜索由插件提供。插件有两种来源：随 Ariadne 一起发布的内置插件（`packages/plugin-*`），和用户本机路径上的第三方插件。

- 第三方插件在“设置 → 插件”里填绝对路径（可以用 `~/`）加载：路径是文件，或者是带 `package.json`（按 `exports["."]`、`module`、`main` 找入口）或 `index.ts` / `index.js` 的目录。入口的默认导出是插件（`definePlugin({ id, name, setup })`）。加载成功后路径写进 `~/.ariadne/config.json` 的 `plugins`，以后每次启动都加载；加载失败的不保存，原因显示在设置里。启动时加载失败的插件也列在设置里，带着原因。
- 插件的 `setup` 抛错，或者注册了别的插件已有的协议或项目来源，它注册过的东西全部撤回。移除插件时，它注册的协议和项目来源立即撤下；已经连上的工作区要到重启后才断开。改了插件代码要重启 Ariadne 才生效。
- 插件和服务在同一个进程里运行，能读到服务端的一切（包括令牌和 API Key），只应加载信任的代码。插件只从用户在设置里填的路径加载，不会因为项目的仓库里带了插件就自动执行：GitHub 仓库可能是别人的，打开一个项目不应让仓库里的代码进到服务端进程。Ariadne 的插件数据目录（`~/.ariadne/plugins/`，讨论串的 worktree 和仓库的克隆都在这里）和仓库旁边的 `.ariadne-worktrees/` 下的路径也会被拒绝加载。讨论串在自己 worktree 里写的代码因此不会进到服务端进程。设置里的插件路径讨论串的命令改得了，所以插件应放在讨论串不工作的目录里。
- 插件只用 `@ariadne/plugin-sdk` 的类型（`import type`）时不需要安装任何东西；运行时用到 SDK 的函数的话，插件要自己带上依赖（或打包）。

### 设置

全局设置在 `~/.ariadne/config.json`，项目设置是事件 `project.settings.set`（项目视图的 `settings`）。

- 指令：全局指令和项目指令以 `user_instructions` 块进协调器和讨论串的提示词；协调器每回合还通过项目来源的只读视图读根目录的 AGENTS.md（上限 1 MiB）。
- 命令规则：`allow` / `ask` / `deny` 三种，模式里 `*` 匹配任意内容。命令按 shell 的读法拆成简单命令（`;`、`&&`、`||`、`|`、`&`、括号、换行；`2>&1`、`> out`、`&> log` 这类重定向不算分隔，`$(…)` 和反引号里的命令也拆出来），每部分既按原文、也按实际运行的样子匹配：去掉开头的 `FOO=1`、`env`、`sudo`、`nohup` 这类包装、程序的目录，以及 git 子命令前的全局选项（`git -C dir push` 按 `git push` 算）；`bash -c '…'`、`pwsh -Command …`、`cmd /c …` 里的命令行再拆成各自的部分。别的命令带着跑的命令（`then git push`、`{ git push; }`、`eval`、`xargs`、`timeout 10 …`、`sudo -u root …`）也要拦住，所以 deny 和 ask 还在每部分从每个词起的后半截上匹配，带空格的单词（`eval "git push"`、`bash -ce "…"`）当作命令行再拆一次，含反引号的命令行去掉反引号再读一遍（PowerShell 的转义），`pwsh -EncodedCommand` 解码后再拆；宁可多问。只有一种情况不问：命令只是打印或查找一段文字（`echo`、`printf`、`grep`、`rg`，以及 `git commit`、`git tag`、`git log` 这类带说明或模式的子命令），文字里提到的命令不算在运行，`git commit -m "说明 git push 的流程"`、`rg "npm publish"` 都直接运行；同一条命令行里还有会执行文字的东西（shell、`eval`、`xargs`，比如 `echo "git push" | sh`）时照旧要问。deny 规则没有这个例外。allow 只按实际运行的样子匹配，而且只放行它字面写出的部分：`allow timeout *` 不抵消 `timeout 10 git push` 上的 `ask git push*`，`allow timeout 10 git push` 可以。同一部分内 deny > allow > ask；整条命令只要有一部分 deny 就拒绝，有一部分 ask 就要问（别的部分命中 allow 也不抵消），没有命中就直接运行。`ask` 发确认块进「需要我」，同意只能用一次（`approval.used`，MCP 的一次性同意也用它）。新装时带 8 条 ask 规则，和用户自己加的一样可以改、可以删：`git push*`、`npm publish*`、`pnpm publish*`、`yarn publish*`、`bun publish*`、`cargo publish*`、`gh pr merge*`、`gh release create*`。它们都是后果离开本机、收不回来，而讨论串正常干活又用不到的命令。规则只看敲出来的命令行：藏在脚本里的发布（`bun run release`）和子命令前带选项的写法（`pnpm -r publish`）拦不到，提示词里“不可撤销的事先问”仍然管着这些。保存过的规则列表（哪怕是空的）以用户的为准，不再补默认规则。
- 上限：命令默认/最长超时（120/600 秒）、命令输出上限（30k 字符）、压缩时机（上下文的 60%，上下文按至多 40 万算）、模型重试次数（4）、重复调用几次后停下（4）。
- 预算：项目设置里每个讨论串和整个项目的 token 上限（输入加输出），默认不限。用到上限时回合不开始或在下一步前停下，错误 `error.budgetThread` / `error.budgetProject` 进「需要我」。
- 模型请求参数：提供方可加请求头（值只存在服务端）、额外请求字段（不能覆盖 model、messages、tools、stream、system）和无响应超时（每次尝试单独计时，超时算可重试的错误）；模型可设单次最多输出。
- 工作区：项目的命令环境变量（值存在 config.json 的 `projectEnv`，页面只拿到名字）、新工作区的安装脚本（新建工作区后先跑一次，结果附在第一个工具结果里）、改动后检查（这两项没写时输入框里显示 Ariadne 自己认出的值，原样保存仍归 Ariadne 管，改过或清空就以用户的为准，`workspace.auto`）、命令用的 shell（默认自动）、分支前缀。分支名由 create_thread 的 `branch` 参数生成可读的 `<前缀><slug>-<id 末 6 位>`，没有时是 `<前缀><id 末 12 位>`。
- 交付前审阅：项目设置 `review.enabled`，默认开，见“交付前审阅”。
- 托管推进：项目设置 `autopilot`（`enabled` 默认关、`method` 是这个项目上次合并用的方式，没合并过是 `squash`、`threads` 默认 3），暂停是单独的 `project.autopilot.paused`，见“托管推进”。
- 工具开关：项目可关掉 fetch_url、web_search、run_command（连同读后台输出和结束后台命令）、issue 写入、只读子调研几组内置工具。
- 快捷键：搜索、聚焦输入框、上/下一个讨论串、停止回合、快捷键列表都能改绑（`input.keys`），每个动作一个单键组合，不能重复。
- 数据：设置里看数据目录用量，`VACUUM INTO` 备份数据库到 `<home>/backups`。服务每天自动备份一份（启动时和之后每小时看一次：当天还没有自动备份、且上次备份之后数据库有写入才做），文件名带 `-auto`，只留最近 7 份；用户点“立即备份”做的不会被自动清掉。项目右键菜单可导出项目（事件日志和文件的 JSON）。

## 能力

项目来源通过能力接入。上层只依赖能力，不依赖具体的 provider。

| 能力        | 典型提供者                   | 负责                                                                                                                                |
| ----------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `workspace` | 本地目录、SSH、remote daemon | 准备一个可写目录，并在其中提供 `fs` 与 `exec`；是 git worktree 时还提供 `branches`：改动、合并（托管仓库没有）、移除和列出 worktree |
| `repo`      | GitHub、GitLab               | 远端仓库、分支、PR（托管推进时合并）、CI 状态与日志                                                                                 |
| `tracker`   | GitHub、GitLab               | Issue 等任务记录                                                                                                                    |

`workspace`、`repo` 和 `tracker` 见上文“工作区”“仓库、PR 与 CI”和“Issue”。

```
  core         领域模型、事件存储与投影，不依赖 HTTP
  plugin-sdk   插件作者使用的类型与 definePlugin
  mcp          MCP 客户端：stdio 与 HTTP 两种连接
  remote       远端工作区：脚本、worktree，SSH 和 daemon 共用
  daemon       远端运行的 ariadne-daemon
  agent        agent loop、调度、协调器与讨论串的工具、插件宿主
  plugin-*     内置插件：OpenAI 兼容与 Anthropic 两种模型协议，本地目录、GitHub 仓库、GitLab 仓库、SSH 远程目录与远程 daemon 项目来源
  server       本地 HTTP 服务、鉴权、事件流与用户设置
  web          Vue + dou-ui 的浏览器界面
```

- 依赖方向：`i18n` ← `core` ← `agent` ← `server`，`i18n` ← `daemon`，`plugin-sdk` ← `plugin-*`、`mcp`、`agent`，`mcp` ← `agent`，`remote` ← `plugin-ssh`、`plugin-daemon`；`web` 只依赖 `i18n`，以及 `core` 和 `plugin-sdk` 导出的类型。
- 存储：`bun:sqlite` 单文件，一张事件表加若干投影表；投影与事件在同一个事务里写入。
- 服务默认只监听 `127.0.0.1`，请求需要携带本地 token。
- 终端里打印的文字也走 `@ariadne/i18n`（`cli.*`）：本地服务用设置里选的界面语言；`ariadne-daemon` 跑在别的机器上，读不到设置，按终端的语言（`LC_ALL`、`LC_MESSAGES`、`LANG`），中文和英文以外的、没设的、`C` 都按中文。
- `bun run start` 用构建好的页面启动本地服务：页面没构建过，或者 `web`、它引用的 `core`、`i18n`、`plugin-sdk` 源码、`bun.lock` 比构建结果新，就先构建。
