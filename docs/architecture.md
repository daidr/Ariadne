# 架构

本文描述 Ariadne 的领域概念与分层。设计取舍的依据见 [设计哲学](./philosophy.md)。

## 领域概念

| 概念                    | 定义                                                           | 关键规则                                                                       |
| ----------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Project 项目            | 工作的范围                                                     | 持有上下文源、计划图、协调器、threads、artifacts 和项目记忆                    |
| Context Source 上下文源 | 某个 provider 的一个实例，如“本地目录 ~/code/x”                | 声明自己提供哪些能力（见下文），一个 provider 可以只实现一部分                 |
| Coordinator 协调器      | 每个项目一个长期会话，用户的主要对话对象                       | 工具集小：改计划、开 / 停 thread、给 thread 发消息、向用户要决定；不直接改代码 |
| Thread                  | 一个执行单元：一个会话 + 一个工作区                            | 可绑定到计划节点；用结构化 Report 上报状态；用户可以直接进入对话               |
| Plan 计划图             | 项目的有向无环图：任务、里程碑、决策节点                       | 每次修改是一个带理由的 Revision，可查看差异、可回退                            |
| Attention 待决定        | 一个等用户回答的结构化问题                                     | 来自协调器或 thread，统一出现在“需要我”列表                                    |
| Artifact 产物           | AI 产出的可归档产物：文档、画板、仪表盘                        | 属于项目，可关联计划节点；每次修改是一个新版本；类型由插件注册                 |
| Todo 待办清单           | 协调器和每个 thread 各一张，实时显示正在做、接下来做、在等什么 | 由 AI 用工具更新，每次更新是一个事件；取代过程消息                             |
| Event 事件              | 只追加的事实                                                   | 所有状态都由事件投影而来                                                       |

### Thread 阶段

thread 的阶段按“它在等谁”划分，从上到下第一条匹配的生效：

| 阶段      | 条件                                            | 是否需要用户 |
| --------- | ----------------------------------------------- | ------------ |
| `answer`  | 有未回答的 Attention                            | 是           |
| `working` | 正在执行一轮                                    | 否           |
| `queued`  | 有新输入，在等槽位                              | 否           |
| `blocked` | 上一轮失败（如模型请求出错），等用户重试        | 是           |
| `review`  | 最近的 Report 是 `ready`                        | 是           |
| `blocked` | 最近的 Report 是 `blocked` 或 `failed`          | 是           |
| `done`    | 最近的 Report 是 `done`                         | 否           |
| `queued`  | 还没有开始过                                    | 否           |
| `idle`    | 最近的 Report 是 `waiting`（本轮结束）          | 否           |
| `working` | 其他情况：开始过、还没报告，或刚报告 `progress` | 否           |

未回答的问题排在 `done` 前面：thread 报告完成时如果还有问题没答，它仍然停在 `answer`，问题也留在“需要我”里，直到用户回答。

“需要我”是服务端算出的一张列表：每个未回答的 Attention 一条，再加上每个处于需要用户阶段、但没有未回答 Attention 的 thread 一条。界面上所有“需要我”的数字都取这张列表的长度，前端不自己推导。

### 轮次与 agent loop

协调器和每个 thread 各有一个会话，会话里的 agent 一轮一轮地工作：

- 会话收到新输入（用户的消息、协调器转来的消息、thread 的汇报、用户对问题的回答）后排队等一轮。调度器按槽位启动：默认 3 个槽位，另留 1 个只给“回应用户消息”的一轮，用户不用排在后台工作后面。
- 一轮里，agent 反复请求模型、执行模型调用的工具，直到模型不再调用工具；最后的文字作为一条消息发给用户，没有文字就不发。
- 每次模型回复（`turn.step`）和每个工具结果（`tool.finished`）都是事件。模型的输入每一步都从这些事件重建，所以一轮可以重放，也可以在中断后接着做。
- 模型回复记下它看到的最新事件（`sawSeq`）。回复期间到达的输入排在这次回复之后，不会被当成已读，会再触发一轮。
- 服务停止时正在进行的轮次记为 `interrupted`，下次启动时继续；没有结果的工具调用补一条错误结果。
- 模型请求失败或用户点停止后，不会为触发这一轮的输入自动重试，界面给出原因和“重试”；这一轮进行期间新到、模型还没看到的输入仍会排队处理。
- 回复被截断（超出单次回复的 token 上限）时，这一轮以失败结束并说明原因，不把截断的文字当成完整回复。
- 用户回答问题后，答案交给提问方（协调器或那个 thread）并唤醒它，已经汇报完成的 thread 也一样。

模型由插件提供，每个插件实现一种协议（OpenAI 兼容、Anthropic）。用户在界面的“模型设置”里添加提供方并选默认模型，配置写在 `~/.ariadne/config.json`（仅所有者可读写）；API Key 不写进事件日志，也不会返回给浏览器。

### 计划图

计划图是项目的有向无环图，节点分任务、里程碑和决策三种，每个节点有说明和验收标准，连线表示依赖。

- 每次修改是一个修订（`plan.revised`），带理由，记下撤销它所需的操作。任何一次修订都可以撤销，只要之后的修改和撤销不冲突。
- 协调器的小改动立即生效：加节点、改标题和说明、改依赖。界面高亮最近一次修订改到的节点，并提供“撤销”。
- 大改动先等用户同意：删除节点、修改验收标准、增改里程碑。协调器把一次修改里的这些操作合成一个提议（`plan.proposed`），放进“需要我”；用户同意后才生效，此时计划已经变了、提议不再适用的话就不生效。
- 节点的状态由在做它的 thread 推出：没有 thread 是“未开始”，有 thread 受阻是“受阻”，等用户回答或审阅是“等你处理”，全部完成是“已完成”，其余是“进行中”。
- thread 可以绑定到节点。它的系统提示里有节点的说明、验收标准，以及上游节点已完成的 thread 的总结；上游 thread 汇报完成时，下游节点上还在做的 thread 会收到它的总结并被唤醒。

### 工作区

项目有一个上下文源，目前是本地目录。thread 第一次用文件或命令工具时才准备工作区：

- git 仓库：从仓库当前的 HEAD 为 thread 建一个 `git worktree`，分支是 `ariadne/<thread id 的末尾>`，thread 之间互不可见。重启后沿用原来的 worktree。
- 普通目录：所有 thread 共用这个目录。
- 文件工具的路径都相对工作区根目录，越出根目录（包括经符号链接）的路径会被拒绝。命令在工作区里用 bash 执行，有超时，输出过长时只保留末尾。
- 工作区里的命令不需要审批；推送、部署这类影响工作区外、又无法撤销的操作，thread 要先问用户。

本地目录的工作区直接建在用户的仓库上（worktree 和分支都在这个仓库里），用户不用额外拉取就能看到 thread 的分支。远端仓库接入后再按“共享 bare clone + 每个 thread 一个 worktree”的方式准备。

### 产物

第一种产物是文档，内容是 Markdown，界面用块编辑器展示和编辑。

- 每次保存是一个新版本，旧版本可以查看和恢复（恢复也是一个新版本）。
- 保存时带上起始版本号；期间别人保存过就拒绝，用户和 agent 不会悄悄覆盖对方的修改。
- 用户修改了 agent 写的文档，作者在下一轮会看到提示。

### 协调器与 thread 的消息

- thread 之间不直接通信。thread 的请求发给协调器，由协调器决定转发、合并还是驳回。上游节点的产出摘要随依赖自动交给下游。
- 协调器发给 thread 的消息在 thread 面板里显示为一条淡化、默认折叠的提示，点开可看全文。
- thread 发给协调器的消息不在任何面板展示；需要用户决定的事由协调器推到“需要我”。
- 用户在任何 thread 里发消息时，协调器同时做一次轻量分诊，thread 不用等它；如果有更合适的 thread 或者应该另开一项工作，协调器把请求转过去，并提醒当前 thread 用一句话告诉用户去了哪里。用户说“就在这里做”时，协调器以后对同类请求不再转交。分诊不需要转交时，协调器不说话。
- 消息只能由作者自己编辑。编辑是一条事件，界面显示“已编辑”；用户读过的消息被编辑后，下次打开时高亮一次。

## 能力

上下文源通过能力接入。上层只依赖能力，不依赖具体的 provider。

| 能力        | 典型提供者                   | 负责                                          |
| ----------- | ---------------------------- | --------------------------------------------- |
| `workspace` | 本地目录、SSH、remote daemon | 准备一个可写目录，并在其中提供 `fs` 与 `exec` |
| `repo`      | GitHub、GitLab               | 远端仓库、分支、PR、CI 状态与日志             |
| `tracker`   | GitHub、GitLab               | Issue 等任务记录                              |

本地 `workspace` 见上文“工作区”。

## 分层

```
packages/
  i18n         文案与翻译，服务端和前端共用
  core         领域模型、事件存储与投影，不依赖 HTTP
  plugin-sdk   插件作者使用的类型与 definePlugin
  agent        agent loop、调度、协调器与 thread 的工具、插件宿主
  plugin-*     内置插件：OpenAI 兼容与 Anthropic 两种模型协议，本地目录上下文源
  server       本地 HTTP 服务、鉴权、事件流与用户设置
  web          Vue + dou-ui 的浏览器界面
```

- 依赖方向：`i18n` ← `core` ← `agent` ← `server`，`plugin-sdk` ← `plugin-*`、`agent`；`web` 只依赖 `i18n`，以及 `core` 和 `plugin-sdk` 导出的类型。
- 存储：`bun:sqlite` 单文件，一张事件表加若干投影表；投影与事件在同一个事务里写入。
- 服务默认只监听 `127.0.0.1`，请求需要携带本地 token。
