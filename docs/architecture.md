# 架构

本文描述 Ariadne 的领域概念与分层。设计取舍的依据见 [设计哲学](./philosophy.md)。

## 领域概念

| 概念                    | 定义                                                                                                         | 关键规则                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Project 项目            | 工作的范围                                                                                                   | 持有上下文源、计划图、协调器、threads、artifacts 和项目记忆                    |
| Context Source 上下文源 | 某个 provider 的一个实例，如“本地目录 ~/code/x”                                                              | 声明自己提供哪些能力（见下文），一个 provider 可以只实现一部分                 |
| Coordinator 协调器      | 每个项目一个长期会话，用户的主要对话对象                                                                     | 工具集小：改计划、开 / 停 thread、给 thread 发消息、向用户要决定；不直接改代码 |
| Thread                  | 一个执行单元：一个会话 + 一个工作区                                                                          | 可绑定到计划节点；用结构化 Report 上报状态；用户可以直接进入对话               |
| Plan 计划图             | 项目的有向无环图：任务、里程碑、决策节点                                                                     | 每次修改是一个带理由的 Revision，可查看差异、可回退                            |
| Attention 待决定        | 一个等用户回答的界面块：选项、确认或表单                                                                     | 来自协调器、thread 或系统，出现在提问的消息里，也统一出现在“需要我”列表        |
| Artifact 产物           | AI 产出的可归档产物：文档、画板、仪表盘                                                                      | 属于项目，可关联计划节点；每次修改是一个新版本；类型由插件注册                 |
| Todo 待办清单           | 协调器和每个 thread 各一张，按步骤顺序显示在各自的对话里：做完的打勾，正在做、在等什么、接下来做什么一目了然 | 由 AI 用工具更新，每次更新是一个事件；取代过程消息                             |
| Event 事件              | 只追加的事实                                                                                                 | 所有状态都由事件投影而来                                                       |

### Thread 阶段

thread 的阶段按“它在等谁”划分，从上到下第一条匹配的生效：

| 阶段      | 条件                                            | 是否需要用户 |
| --------- | ----------------------------------------------- | ------------ |
| `answer`  | 有未回答的 Attention                            | 是           |
| `stopped` | 被协调器或用户停下，还没有继续                  | 否           |
| `working` | 正在执行一轮                                    | 否           |
| `queued`  | 有新输入，在等槽位                              | 否           |
| `blocked` | 上一轮失败（如模型请求出错），等用户重试        | 是           |
| `blocked` | PR 的检查连续失败 3 次（见“仓库、PR 与 CI”）    | 是           |
| `done`    | 最近的 Report 是 `ready`，之后改动已合入        | 否           |
| `review`  | 最近的 Report 是 `ready`                        | 是           |
| `blocked` | 最近的 Report 是 `blocked` 或 `failed`          | 是           |
| `done`    | 最近的 Report 是 `done`                         | 否           |
| `queued`  | 还没有开始过                                    | 否           |
| `idle`    | 最近的 Report 是 `waiting`（本轮结束）          | 否           |
| `working` | 其他情况：开始过、还没报告，或刚报告 `progress` | 否           |

协调器可以用 `stop_thread` 自己停下一个 thread，必须写明原因（如“方向跑偏了”“和另一个 thread 重复”）；用户也可以在 thread 面板上点“停下”，原因可不填。用户停下的 thread 只有用户能继续，协调器会收到说明，不再指望它；协调器停下的 thread，用户也可以点“改由我停下”接管这次停止。停下时记一条 `thread.stopped`：正在跑的一轮和它的命令立即被中止，调度器的槽位随之空出；之后新到的消息只排队，不会启动它。thread 面板顶部显示谁停的、为什么停，用户点“继续”、在 thread 里发消息或回答它的提问都会继续，三者一样记一条 `thread.resumed`；协调器也可以用 `resume_thread` 让自己停下的 thread 继续。继续后 thread 收到一条说明，带着当初停下的原因接着做；由用户继续时协调器也会收到。

“改动已合入”指用户在报告之后合并了它的分支（见“查看与合并改动”），或者它的 PR 已被合并：用户审阅完、收下了，就不再留在“需要我”里。之后 thread 再报告 `ready`，又回到 `review`。

未回答的问题排在 `done` 前面：thread 报告完成时如果还有问题没答，它仍然停在 `answer`，问题也留在“需要我”里，直到用户回答。

“需要我”是服务端算出的一张列表：每个未回答的 Attention 一条，再加上每个处于需要用户阶段、但没有未回答 Attention 的 thread 一条。界面上所有“需要我”的数字都取这张列表的长度，前端不自己推导。

### 轮次与 agent loop

协调器和每个 thread 各有一个会话，会话里的 agent 一轮一轮地工作：

- 会话收到新输入（用户的消息、协调器转来的消息、thread 的汇报、用户对问题的回答）后排队等一轮。调度器按槽位启动：默认 3 个槽位，另留 1 个只给“回应用户消息”的一轮，用户不用排在后台工作后面。两个数字在“设置 → 模型”里可调，保存后立即生效：正在跑的一轮做完，新的一轮按新的上限启动。每个项目还可以在项目来源的设置里单独限制“这个项目最多同时工作”几个回合（`project.slots.set`），在总数之内再限一层，免得一个项目占满所有槽位；回应用户消息的一轮不受项目上限限制，仍可用留出的槽位。
- 一轮里，agent 反复请求模型、执行模型调用的工具，直到模型不再调用工具；最后的文字作为一条消息发给用户，没有文字就不发。
- 一轮没有步数上限，长任务不会做到一半被截断。防的是原地打转：同样的工具调用得到同样的结果，在最近 12 步里第 3 次出现时，结果后面附一句提醒模型换个做法（在等检查或回复就结束这一轮，到时会被唤醒）；第 4 次就停下这一轮，以失败结束并说明原因。不必相邻，两三个调用来回循环也算；隔很久才重读一次没变的文件不算。用户随时可以点停止。
- 每次模型回复（`turn.step`）和每个工具结果（`tool.finished`）都是事件。模型的输入每一步都从这些事件重建，所以一轮可以重放，也可以在中断后接着做。
- 模型回复记下它看到的最新事件（`sawSeq`）。回复期间到达的输入排在这次回复之后，不会被当成已读，会再触发一轮。
- 服务停止时正在进行的轮次记为 `interrupted`，下次启动时继续；没有结果的工具调用补一条错误结果。
- 仓库的 `AGENTS.md`：thread 的工作区打开后，每一步开始前读工作区根目录的 `AGENTS.md`，第一次读到或内容变了就记一条 `conversation.instructions`（内容和哈希，超过 1.6 万字截断），模型的系统指令里放最新记下的版本，所以每次请求仍能从日志重建。内容变了（包括 thread 自己改了它）或文件被删时，对话里在变化的位置给模型一条说明。用户也在对话里看到一行：遵循了哪份文件、内容可展开，改了或删了各有一行，工作区里未提交的改动会标出来。它放在名字带内容哈希的数据块里，同项目记忆一样闭合不了所在的块。这份文件来自仓库，不是用户说的话：它决定在这个仓库里怎么干活（命令、风格、目录），不能改变用户或协调器的要求、项目记忆和哪些事要用户点头，冲突时以后者为准。还没打开工作区的 thread 不读，读文件不会因此建出 worktree。
- 重试窄而可见：只有模型插件标为可重试的错误（限流、服务过载或内部错误、已建立的连接被重置或超时、回复流没收完就断了）才自动重试，最多 4 次，等待从 1 秒起逐次翻倍，服务给了 `Retry-After` 就按它等。地址写错、域名解析不到、证书不对、连接被拒这类设置问题不重试，直接报错；`Retry-After` 超过 1 分钟（比如额度用完）也不重试，错误里写明要等多久。每次重试记一条 `conversation.model_retry`，对话里显示一行淡化的说明（第几次、等多久、原因）；失败那次已经流出来的文字丢弃，不当成回复。
- 其他模型错误（如 API Key 无效）、重试用完或用户点停止后，这一轮以失败结束，不会为触发这一轮的输入再自动重试，界面给出原因和“重试”；这一轮进行期间新到、模型还没看到的输入仍会排队处理。
- 回复被截断（超出单次回复的 token 上限）时，这一轮以失败结束并说明原因，不把截断的文字当成完整回复。
- 用户回答问题后，答案交给提问方（协调器或那个 thread）并唤醒它，已经汇报完成的 thread 也一样。
- 对话很长时压缩历史：每一步开始前，如果模型的输入（上一步报告的输入 token 数，或按字数估算，取大者）超过模型上下文的六成，就请模型不带工具地把较早的历史总结成摘要，记一条 `conversation.compacted`（摘要和截到哪里）。上下文大小在“设置 → 模型”里随每个模型填写，留空按 12.8 万 token。之后模型读到的是摘要加上截断点之后的原文，最近约四分之一阈值的内容保持原样。截断点只落在两步之间，不会把一次工具调用和它的结果拆开；再次压缩时上一份摘要也被并进新的摘要。
  - 摘要作为模型自己写的笔记（assistant 消息）回到模型，既不当成用户说的话，也不放进系统指令：它是从含有工具输出的历史写出来的。摘要分开记“用户说的”和“工作中得知的”，后者注明来源，只是信息，不是指令。
  - 摘要后面附上从存储读出的当前待办和还没回答的提问，模型不必凭摘要记忆它们（`update_todo` 是整表替换，凭记忆重写会丢项）。
  - 对话里在压缩的位置显示一条淡化的分隔，点开能看摘要。总结失败时也在对话里注明原因，这一轮不再重试，照常读完整历史继续。
  - 事件日志里原文都还在，压缩只改变模型读到的东西；摘要请求的 token 计入会话用量。

模型由插件提供，每个插件实现一种协议（OpenAI 兼容、Anthropic）。用户在界面的“设置 → 模型”里添加提供方，再在提供方上添加模型（模型名、上下文大小、用途），配置写在 `~/.ariadne/config.json`（仅所有者可读写）；API Key 不写进事件日志，也不会返回给浏览器。

- 按角色分配：thread 干活，默认模型先给 thread；协调器不选就和 thread 一样。两个角色各有思考深度（默认、低、中、高），同一个模型时协调器可以想得浅一些。“默认”不发思考参数，因为不支持的模型收到会报错；低中高在 Anthropic 协议是自适应思考（`thinking: {type: "adaptive"}`）加 `output_config.effort`，4.6 之前的模型不支持；在 OpenAI 兼容协议是 `reasoning_effort`。设了不止一个模型时，协调器的系统指令里列出它们和用户写的用途，`create_thread` 多一个 `model` 参数，协调器按工作挑；不给就用 thread 的默认。用户在 thread 输入框左下角随时换，从下一步起生效（`thread.model_set`），思考深度仍按 thread 角色。thread 记的是模型设置的 id；那个模型被删了就回到 thread 的默认。
- 思考：模型返回的思考按块记在 `turn.step` 的 `reasoning` 里。Anthropic 协议总是把带签名的思考块原样发回（新模型不设也会思考，工具调用的回合里协议要求发回，当前模型读不了的由服务丢掉）；OpenAI 兼容协议读 `reasoning_content` / `reasoning`，有思考的助手消息带着 `reasoning_content` 发回（DeepSeek 等默认思考的服务在工具调用回合里要求这样）。
- 用量：每一步的 token（`turn.step` 的 `usage`，摘要请求的也算）按会话累计，thread 标题栏显示它自己的，项目面板的 Threads 页显示整个项目的；只显示 token，不估算花费。输入 token 是模型读的全部，其中读缓存的另记 `cached`，输出里花在思考上的另记 `reasoning`（服务说了才有）。输入框左下角的圆环是上下文占用：最近一步模型读了多少，对比当前模型的上下文大小，过半变黄，到压缩线（六成）变红。
- 追踪：thread 标题栏的菜单里有“追踪”，占满整个页面。表格按回合列出每个请求（步骤和摘要都算，整个会话连续编号）、它的工具调用，以及重试、摘要失败和 `AGENTS.md` 的变化；每行有输入、缓存、输出、思考 token，耗时和在回合里的时间线。选中一行在右侧看详情：请求有概要（模型、思考深度、发出 / 首个输出 / 结束的时间、结束原因、token）、请求体（提供方插件按记录的参数重建的 HTTP 请求体，不含凭据）、消息（相对上一步新加的标出来并展开）和响应；工具调用有参数、结果和工具定义。平时的对话里不显示工具调用。为了能重建，每个请求记下它用的系统指令、工具定义、摘要旁的当前状态，以及提供方类型、模型名、思考深度和去掉密钥的提供方设置：内容按哈希在项目里只存一次（`prompt.recorded`），`turn.step` 的 `input` 记它们的哈希；其余部分就是 `sawSeq` 之前的对话记录，消息按当时的内容（之后的编辑不算）。时间是请求实际发出、第一次有输出（思考的开始也算）和记下结果的时刻；工具一个接一个跑，从上一步或上一个工具结束算起。

通知：“设置 → 通知”打开浏览器通知后，页面不在前台时，有新的提问、thread 汇报可以审阅、做完、受阻，或某一轮出错，都会弹出通知，点开就跳到对应的项目和 thread；同一个 thread 的新通知替换旧的。开关记在这个浏览器里。标签页标题前面是所有项目“需要我”的总数。

第一次使用时，协调器的空白对话里是一份“开始使用”的步骤：设置模型、新建项目、选择工作目录（可选）、告诉协调器要做什么。做完的步骤打勾，当前一步带着对应的按钮（打开设置、新建项目）；模型、项目和工作目录都有了以后，换回普通的空白提示。

### 计划图

计划图是项目的有向无环图，节点分任务、里程碑和决策三种，每个节点有说明和验收标准，连线表示依赖。

- 每次修改是一个修订（`plan.revised`），带理由，记下撤销它所需的操作。任何一次修订都可以撤销，只要之后的修改和撤销不冲突：撤销一次编辑时，如果那个字段之后又被改过，撤销会被拒绝，不会覆盖后来的修改。
- 协调器的小改动立即生效：加节点、改标题和说明、改依赖。用户上次点“知道了”之后协调器改到的节点在图上描边标出，计划页逐条列出这些修订，每条都能撤销。“知道了”记在浏览器里（每个项目一份），第一次打开时之前的修改都算看过；计划只带最近 50 次修订，看过的那次已经不在其中时，页面会说明只标出了最近 50 次里的改动。
- 大改动先等用户同意：删除节点、修改验收标准、增改里程碑。协调器把一次修改里的这些操作合成一个提议（`plan.proposed`），放进“需要我”，问题里逐条列出会改什么（删除节点时注明上面还有几个 thread）；用户同意后才生效。等确认的提议改到的节点标“待确认”；“在图上预览”把提议套到当前计划上画出来（服务端用同一套规则算好，随提议下发，前端只负责画）：新增的节点和连线是绿色虚线，要删的节点和连线是红色虚线、节点淡化，要改的节点是蓝色虚线，计划已经变得套不上时说明原因。协调器撤销一次修订也一样：撤销里有大改动（比如撤销“加节点”就是删除），也要先等用户同意。
- 用户同意时计划已经变了、提议不再适用的话，提议不生效，记为失效（`plan.proposal.stale`）：计划页提示用户这次同意没有生效，协调器收到说明并被唤醒，重新看计划后再提议。提示一直留着，直到用户点“知道了”（`plan.proposal.dismissed`）或协调器发出新的提议，不会因为一次无关的小改动就消失。
- 计划有两种视图：图（依赖关系）和看板（按节点状态分列）。图上的节点卡片显示在做它的 thread、阶段、PR 编号和检查状态；等用户回答或审阅的节点整块着色并标“等你”。
- 用户可以直接在图上改计划：打开“编辑计划图”后，从节点底部拖线到另一个节点表示后者依赖前者，选中连线按 Delete 删除；选中节点按 Delete 会先确认（节点上有 thread 时说明有几个会脱钩），“加节点”新建任务节点，侧栏里改标题、说明和验收标准。每个动作是一次用户修订（`author: user`），立即生效，不需要确认，能在修改记录里撤销；协调器下一轮会收到说明。连线拒绝成环和重复；保存节点内容时带上原值（`expect`）。协调器在此期间改过同一字段的话，表单旁会显示现在的值，用户选“保留我的，再保存一次”或“改用现在的”，输入的内容不会丢；冲突时服务端拒绝保存（`error.planConflict`）。修订理由逐条写出这次改了什么，协调器从说明里就能知道。拖动节点的位置只记在浏览器里，“重新排列”恢复自动布局。
- 节点的状态由在做它的 thread 推出：没有 thread 是“未开始”，有 thread 受阻是“受阻”，等用户回答或审阅是“等你处理”，全部完成是“已完成”，其余是“进行中”。停下的 thread 不参与推算；节点上的 thread 全都停下时显示“已停下”。
- thread 可以绑定到节点。它的系统提示里有节点的说明、验收标准，以及上游节点已完成的 thread 的总结；上游 thread 汇报完成时，下游节点上还在做的 thread 会收到它的总结并被唤醒。

### 工作区

项目有一个上下文源：本地目录、GitHub 仓库、GitLab 仓库、SSH 远程目录或远程 daemon。thread 第一次用文件或命令工具时才准备工作区：

- git 仓库：从仓库当前的 HEAD 为 thread 建一个 `git worktree`，分支是 `ariadne/<thread id 的末尾>`，thread 之间互不可见。重启后沿用原来的 worktree；worktree 目录被手动删掉的话，先 `git worktree prune` 再在原分支上重建。上下文源是仓库的子目录时，工作区根目录是 worktree 里对应的子目录。
- 普通目录：所有 thread 共用这个目录。
- GitHub 仓库：在插件的数据目录里为仓库建一个共享的 bare clone（`~/.ariadne/plugins/github/repos/<owner>/<name>.git`），远端分支取到 `refs/remotes/origin/*`，取远端时不会动到 thread 的分支；每个 thread 从远端默认分支建自己的 worktree 和分支 `ariadne/…`。
- GitLab 仓库：和 GitHub 一样（共享 clone、worktree、推送都是同一份代码，`@ariadne/plugin-local` 的 `hostedClone`），目录先按实例（主机和端口，再加实例地址里的路径）再按项目的完整路径分层（`~/.ariadne/plugins/gitlab/repos/<主机>/<group>/<sub>/<project>.git`），不同实例上同路径的项目各有各的 clone。支持子组和自建实例：实例地址可以带路径（比如 `https://example.com/gitlab`），留空时用 GitLab.com 或仓库地址里的实例。
- SSH 远程目录：见下文“SSH 远程工作区”。
- 文件工具的路径都相对工作区根目录，越出根目录（包括经符号链接）的路径会被拒绝。命令在工作区里用 bash 执行，有超时，输出过长时只保留末尾。
- 工作区里的命令不需要审批；推送、部署这类影响工作区外、又无法撤销的操作，thread 要先问用户。

新建的 worktree 没有被 git 忽略的依赖目录。本地目录的仓库里，用户自己的签出中被忽略的 `node_modules`、`vendor`、`.pnpm-store`（任意层级，符号链接除外）会以写时复制的方式克隆进新 worktree：Linux 上是 `cp --reflink=always`（btrfs、XFS 等支持 reflink 的文件系统），macOS 上是 `cp -c`（APFS 的 clonefile）。克隆不占额外空间，任一边改了文件才各自分开；它们仍被忽略，不会进 thread 的提交。先在仓库的 git 目录里拿一个小文件试一下能不能克隆，不能（比如 ext4，或签出和数据目录不在同一个文件系统上）就什么都不复制，worktree 就是普通的 worktree，thread 自己装依赖（`bun install` 本来就从全局缓存硬链接）。构建产物不复制；Python 虚拟环境也不复制，它的脚本和 `activate` 用绝对路径指向原来的环境，克隆出来的会装进用户自己的环境。GitHub、GitLab 仓库的 worktree 来自共享的 bare clone，没有用户签出可借，不做这一步。没有用 overlayfs：它要挂载权限，而且 git worktree 和挂载层叠在一起时，提交、切分支和沙箱的路径都要另外处理，收益只在依赖目录上，reflink 已经覆盖。

本地目录的工作区直接建在用户的仓库上（worktree 和分支都在这个仓库里），用户不用额外拉取就能看到 thread 的分支。worktree 目录在 `~/.ariadne/plugins/local/worktrees/`、`~/.ariadne/plugins/github/worktrees/` 和 `~/.ariadne/plugins/gitlab/worktrees/` 下（SSH 在远端的 `~/.ariadne-worktrees/`），用完会自动清理，见下文。

### 查看与合并改动

thread 第一次打开工作区时记下它的基线分支（`workspace.opened` 的 `base`）：本地目录和 SSH 是签出当时所在的分支，GitHub、GitLab 是远端的默认分支。签出处在分离的 HEAD 上时没有基线，看不了改动，也合并不了。之后工作区被移除再打开，沿用记下的基线，不看签出现在在哪个分支上。

- 改动按 PR 的方式比较：从分支和基线最近的共同提交，到分支最新的提交，只算已提交的内容（GitHub、GitLab 的基线是共享 clone 里的 `origin/<默认分支>`）。改名按 git 的相似度识别。worktree 里没提交的文件单独列出数量，它们不在改动里，也不会被合并；thread 的系统提示也说明了这一点。
- 界面上 thread 面板顶部和计划节点里的“改动”打开改动视图：左边是按目录排列的文件（只有一个子目录的目录合成一行），右边是 `@dou-ui/code` 的 `DouCodeDiff`。文件内容按需读取，超过 512 KB 的和二进制文件不显示内容。
- 本地目录和 SSH 由用户点“合并到 <基线>”：默认压成一个提交（squash），也可以保留每个提交（合并提交）；提交说明默认是 thread 的标题，作者是 git 里配置的 `user.name`、`user.email`（本地读用户自己的配置，SSH 读远端用户的）。合并不碰 thread 的 worktree：先用 `git merge-tree --write-tree`（需要 git 2.38+）算出结果，有冲突就什么都不改；没有冲突时写出提交，基线没有签出在任何地方就用 `update-ref` 从原来的位置移过去（期间基线有了新提交则拒绝，再合并一次即可），基线签出在用户的目录里就在那里 `merge --ff-only`，文件跟着更新，签出里未提交的改动挡住时拒绝，什么都不丢。更新签出时不读用户的全局 git 配置（免得执行 thread 写进去的 filter），所以仓库的 `.gitattributes` 里有 `filter=`（比如 Git LFS）时拒绝在签出里合并，请用户自己合；全局的 `core.autocrlf` 也不生效。thread 正在跑一轮时不能合并。
- 合并记 `branch.merged`：协调器收到说明并被唤醒；thread 下次工作时读到，squash 之后继续改要先把基线合进自己的分支，后面的改动才单独比较。冲突记 `branch.conflicted`，唤醒 thread：在自己的分支上合并基线、解决冲突、跑检查、提交，再报告 `ready`。两者都在 thread 的对话里留一行，用户能看到发生了什么。
- GitHub、GitLab 的改动通过 PR 合入，界面只看改动，不替托管平台合并。

worktree 在改动合入之后自动移除，分支保留：用户合并了分支（在 Ariadne 里，或者在终端里合并到基线），或者 PR 已合并或关闭，并且 thread 处于 `review` 或 `done`。worktree 里有没提交的文件（被忽略的 `node_modules` 之类不算）就留着。相关事件之后过一会儿检查一次，另外每 10 分钟扫一遍，接住在 Ariadne 之外的合并。移除记 `workspace.removed`，thread 的对话里留一行；thread 再用文件或命令工具时在原分支上重建 worktree，读 `AGENTS.md` 不会因此把它建回来。设置的“工作区”页按项目列出 worktree 和占用的空间（`du`，reflink 克隆的依赖目录按完整大小算），也可以手动移除，同样只移除没有未提交改动的。

上下文源的设置按插件给出的 schema 填写。标成 secret 的设置（比如访问令牌）存在 `~/.ariadne/config.json`，不写进事件日志，也不返回给浏览器；GitHub 令牌留空时依次使用 `GH_TOKEN`、`GITHUB_TOKEN` 和 `gh auth token`。GitLab 令牌（需要 `api` 权限）留空时使用 `GITLAB_TOKEN`、`GITLAB_ACCESS_TOKEN` 或 `GL_TOKEN`，但只发给 `GITLAB_HOST` 指的实例（没设置时是 GitLab.com），否则用 `glab config get token --host <实例>`，调用时清空 glab 也会读的 `GITLAB_TOKEN`、`GITLAB_ACCESS_TOKEN`、`OAUTH_TOKEN`、`GL_TOKEN`、`CI_JOB_TOKEN`，只拿 glab 为这个实例保存的令牌：为一个实例签发的令牌不会被发给别的实例。GitLab 实例地址只接受 https（本机的 localhost 除外），API 请求和服务端的 git（GitHub、GitLab 都是）都不跟随重定向，令牌不会被带到别的主机。令牌只在服务端自己的 git 命令里通过环境变量交给 git，并绑定到仓库地址，不落盘，也不出现在命令行参数里。服务端的取远端和推送用自己保存的地址、关掉 hook，不读 worktree 里可被改写的 remote；共享 clone 的 `pushurl` 指向一个无效地址，thread 直接 `git push` 会失败。

thread 的命令环境里去掉了服务端的凭据（`GH_TOKEN`、`GITHUB_TOKEN`、`GITLAB_TOKEN`、`GITLAB_ACCESS_TOKEN`、`GL_TOKEN`、`CI_JOB_TOKEN`、`OAUTH_TOKEN`、`ARIADNE_*`、`GIT_CONFIG_*`），令牌不会意外出现在工具结果、事件日志和模型输入里。

thread 的命令在工作区沙箱里运行，看不到 Ariadne 的数据目录（`~/.ariadne`，或 `ARIADNE_HOME`：本地令牌、`config.json` 里的 API Key 和访问令牌、数据库）和浏览器的配置目录（页面把令牌存在浏览器里），也就拿不到令牌去调用本机的 Ariadne 接口。

- 沙箱只遮住这些路径，其余照旧：命令仍以用户身份运行，文件系统的其他部分、网络和用户自己的 git、ssh 凭据都还在，工具链不用另装。想再遮住别的路径（比如 `~/.ssh`），写进 `config.json` 的 `sandbox.hide`。
- 遮住的目录整个换成空的 tmpfs，再把工作区要用的路径放回去，所以命令运行期间新写进去的文件（比如以先写临时文件再改名的方式保存的 `config.json`）也看不到。工作区本身留着：worktree 目录，以及 git 要写的目录（本地仓库的 `.git`、GitHub 和 GitLab 的共享 bare clone）。GitHub、GitLab 的 worktree 在 `~/.ariadne` 下面，放回去的只有它和共享的 clone，令牌、设置、数据库和别的 thread 的 worktree 都看不到。工作区就在用户主目录这种情况下，`~/.ariadne` 依然被遮住。
- 服务端之后会在沙箱外运行的东西，thread 只能读不能改：git 目录（本地仓库的 `.git`、共享 clone）里的 `config` 和 `hooks/`，Ariadne 自己的代码目录，设置里加载的插件路径（在设置里加上就立即只读，不用等重启），用户的 `~/.gitconfig` 和 `~/.config/git`。因此 thread 不能用 `git config` 写仓库配置，需要时用 `git -c`。Ariadne 自己的仓库作为工作区时，它的 worktree 和 `.git` 仍然可写，只有 `config`、`hooks` 只读。
- 服务端自己的 git 命令不读全局和系统配置，不运行 hook 和 fsmonitor，只允许远端用的协议（GitHub、GitLab 是 `https`，本地仓库不联网）。即使 thread 在别处改了这些配置（比如沙箱不可用时），也不能让服务端的 git 执行命令。
- 共享 clone 的分支 ref 对所有 thread 可写：一个 thread 能移动别的 thread 的 `ariadne/…` 分支，那个 thread 推送时，推上去的就是被改过的提交。沙箱不防这一点，它防的是令牌和设置。
- Linux 优先用 bubblewrap（`bwrap`），没有时用 util-linux 的 `unshare`（需要内核允许非特权用户命名空间），挂载方式相同，命令在嵌套的用户命名空间里仍以用户自己的 uid 运行。两种都有自己的进程列表，看不到服务进程和它的环境变量；命令结束时，它留下的后台进程会一起结束。
- macOS 用系统自带的 `sandbox-exec`，按路径拒绝读写遮住的路径，再放开工作区要用的、锁住只读的。它只管文件，不隔离进程：命令能看到并结束服务进程。这比 Linux 弱，项目来源下方会注明。
- Linux 和 macOS 上，thread 的命令都在自己的进程组里运行，命令结束（或超时）时整组结束，留下的后台进程不会一直运行；特意脱离进程组的进程（`setsid`）在 macOS 上仍能留下来。它占着输出时，命令结束后最多再等 1 秒读输出，工具调用不会因此挂住。
- Windows 没有进程组：超时或 thread 被停下时，用 `taskkill /T /F` 结束命令和它启动的进程；命令自己结束后留在后台的进程不会被结束。
- 文件工具在服务端读写文件：先按路径检查不越出工作区，再以不跟随符号链接的方式打开，并确认打开的正是检查过的那个文件，其间被换成符号链接或别的文件就拒绝。被拒绝的写入可能在被换去的地方留下一个空文件或空目录：服务端不按路径回头删除，那样会再次跟随被换的链接，删掉工作区外的文件。
- 启动时检测能用哪一种。都不能用（Windows 等其他系统，或内核关了用户命名空间）时，命令照现在这样直接运行，启动日志和项目来源下方都会提示 thread 的命令没有隔离。`config.json` 里 `"sandbox": { "mode": "off" }` 可以关掉沙箱，界面同样提示。改动在重启后生效。
- `git push` 不受影响：推送由服务端自己执行，在沙箱外，用它保存的地址和令牌；thread 在命令里直接推送依然会失败。
- 插件拿到同一个沙箱（`ctx.sandbox.wrap(argv, { keep, readOnly })`），第三方的上下文源可以让自己的命令也在里面运行。

“不合并、不推其他分支”靠工具面和提示约束，防的是失误，不是蓄意越权的 thread；沙箱防的是 thread 冒用用户在 Ariadne 里的身份，不是把 thread 和用户的整个账户隔开：沙箱外的其他文件（比如 shell 的启动脚本）thread 仍然能改。

### SSH 远程工作区

SSH 来源（内置插件 `plugin-ssh`）让 thread 在另一台机器上签出和执行命令，填主机（`user@host` 或 `~/.ssh/config` 里的 Host）、可选的端口和远端的绝对路径。

- 连接用系统自带的 `ssh` 和用户自己的配置、密钥、ssh-agent，不保存任何密钥，也不支持密码登录：`BatchMode=yes`，从不提问。主机指纹不认识时连接直接失败并给出原因，用户先在终端里 ssh 一次确认指纹；Ariadne 不会替用户接受新指纹。不过用户自己的 ssh 配置里放宽的指纹策略（`StrictHostKeyChecking no` 或 `accept-new`）同样生效。
- 连接不转发任何东西（`ForwardAgent=no`、`ForwardX11=no`、`ClearAllForwardings=yes`、`Tunnel=no`、`GSSAPIDelegateCredentials=no`），也不运行 `LocalCommand`：远端的命令连不回这台机器，用不了本机的 agent 去登录别处。本地的 `ssh` 进程拿到的环境同样去掉了服务端的凭据，`SendEnv` 带不过去。
- 同一台主机的调用共用一条连接（`ControlMaster`，套接字在 `~/.ariadne/plugins/ssh/cm/`，空闲两分钟后断开），每次调用只有几十毫秒的开销；数据目录的路径太长、放不下 Unix 套接字时就每次新连，并显式关掉复用（`ControlMaster=no`、`ControlPath=none`），不会挂到用户在终端里开的、可能带着转发的主连接上。
- 远端是 git 仓库时，和本地目录一样为每个 thread 建一个 worktree，放在远端用户的 `~/.ariadne-worktrees/<仓库路径的哈希>/<thread id>`，分支是 `ariadne/…`，从签出当前的 HEAD 建出；子目录、手动删掉后重建、依赖目录的写时复制（远端支持 reflink 时）都和本地目录相同。服务端在远端运行的 git 关掉 hook 和 fsmonitor。不是 git 仓库的目录由所有 thread 共用。
- 远端只需要 bash、git 和常见的 POSIX 工具（`realpath`、`cat`、`cp`）。登录 shell 的引号规则各不相同（fish 的单引号里仍有反斜杠转义，csh 不接受单引号里换行），所以交给登录 shell 的命令行固定是 `exec bash --norc --noprofile -s`，没有任何要引的东西；脚本和参数从输入送给 bash，参数只按 bash 的规则加引号。bash 从管道或套接字读输入时一次读一个字节、读完一整行才执行，所以调用脚本的那一行之后的输入原样留给脚本：要写入的文件内容，或者看守进程读的输入。这个 bash 不读启动文件，登录 shell 自己读过的那些设好的环境（比如 `PATH`）照样带过来。sh、bash、zsh、fish、tcsh 作登录 shell 都有对照测试。
- 文件工具在远端读写：路径先在本机规范化，不允许 `..` 和绝对路径，再在远端把最近的已有目录解析成真实路径，确认仍在根目录里；经符号链接出去的、指向不存在位置的链接（写入会顺着它在外面建文件）都会被拒绝。远端的文件工具和命令以同一个用户运行，这层检查防的是失误，不是隔离。
- 命令用 bash 在工作区里运行，有自己的进程组。脚本另起一个看守进程读连接的输入：超时、thread 被停下或者连接断了，本机就关掉输入，看守进程结束整个进程组，留在组里的后台进程也一起结束；特意脱离进程组的（`setsid`）和本地目录一样挡不住。输出过长时只保留末尾，和本地相同。
- 本机的工作区沙箱不管远端：命令以 SSH 登录的用户身份运行，能读写那个用户能读写的一切。项目来源下方会注明这一点。SSH 到本机自己（`localhost`）时，命令同样不在沙箱里，能读到 Ariadne 的令牌和设置。
- SSH 来源只提供 `workspace`，没有 PR 和检查（搭配代码托管时有，见下文）；看改动、合并和自动清理 worktree 与本地目录相同，git 都在远端运行。thread 在远端用 `git push` 推送属于“工作区外、无法撤销”的操作，每次都要先问用户；公开仓库“第一次推送前问一次、对整个项目有效”的规则只适用于有 `repo` 能力、由服务端推送的来源。

SSH 来源的远端代码（工作区、脚本、对 `RemoteShell` 的约定）在 `@ariadne/remote` 包里，SSH 和下面的 daemon 都只提供传输：把一段 bash 脚本和参数交给远端的 `bash --norc --noprofile -s`，送输入、收输出和退出码、能中途结束。

### 远程 daemon

daemon 来源（内置插件 `plugin-daemon`）给连不了 SSH 的机器用：容器、只开一个端口的云主机。远端运行 `ariadne-daemon`（`@ariadne/daemon`，`bun run build:daemon` 打出 Linux 和 macOS 的单文件程序），项目来源里填它的地址、配对码和远端目录。工作区、worktree、改动和合并与 SSH 来源完全相同。

- 方向只有一个：Ariadne 去连 daemon，daemon 不主动连任何地方，Ariadne 自己照旧只听 127.0.0.1。daemon 默认只听远端的 `127.0.0.1:7429`；`--listen` 换成别的地址时启动日志会提醒其他机器也能连上来。
- 连接总是 TLS。daemon 第一次启动时用 `openssl` 生成一张自签的 P-256 证书（名字是 `ariadne-daemon`），Ariadne 不走 CA：每次连接先取 daemon 的证书，核对它的 SHA-256 指纹和配对码里的一致，再把这张证书当成唯一可信的根去建真正的连接，令牌只在这条连接上发出。指纹对不上就断开，并说明是另一台机器在应答，或者 daemon 换了证书。
- 配对码是 256 位随机令牌加证书指纹，第一次启动或 `ariadne-daemon pair` 时打印一次。daemon 只存令牌的 SHA-256（`~/.ariadne-daemon/token.sha256`），每次认证都重新读，`pair` 换掉的旧令牌立即失效（已经连着的连接不受影响）。令牌放在 `Authorization` 头里，不进 URL；同一个地址十分钟内错十次，之后的十分钟一律拒绝。
- Ariadne 这边，配对码是来源的私密设置，和 GitHub 令牌一样存在 `~/.ariadne/config.json`，不进事件日志、追踪和错误信息，浏览器只知道它设过没有。
- 一条 WebSocket 同时跑多个调用（`/v1/shell`），先用 `/v1/hello` 核对令牌和协议版本，版本不同直接拒绝并提示两边用同一个版本。连接断了，进行中的调用以退出码 255 结束，下一次调用重新连接。daemon 端连接断开时关掉每个调用的输入（命令的看守进程据此结束进程组），两秒后再强制结束。
- daemon 在远端也用工作区沙箱（和本机同一个 `@ariadne/sandbox`）运行每个调用，遮住 `~/.ariadne-daemon`（证书私钥和令牌哈希）和浏览器的配置目录，`--hide` 可以再加；daemon 自己的代码只读。没有可用的沙箱时启动日志会说明，`--no-sandbox` 可以关掉。
- 拿到令牌就等于拿到 daemon 所在用户的 shell，和 SSH 私钥一样。所以默认只听回环、远端不存明文、连接必须过 TLS，建议用一个单独的系统用户运行 daemon。
- 暂不支持 Windows，也不做断线后接回原来的命令。

### 远程目录搭配托管仓库

SSH 和 daemon 来源可以再选一个代码托管（GitHub 或 GitLab，`ContextProvider.hosting`）：thread 在远端写代码，PR、检查和 issue 走托管仓库，推送在本机做，托管的令牌从不去远端。

- 远端目录必须是这个托管仓库的签出：连接时比对它 `origin` 的主机和路径（`https`、`ssh://`、`git@host:path` 写法都认），不是就拒绝，免得把别的仓库的提交推上去。
- 提交在两边的 git 之间用 git bundle 搬（`GitObjects`）：本机在自己的共享 clone 里 fetch，再把远端没有的提交打包，经同一条连接送过去，更新远端的 `origin/*`；推送时反过来，把 thread 的分支从远端打包带回本机的 clone，再由本机推送。打包只含对方没有的提交，两边共有的提交作为前提。远端用户自己的分支不动。
- 新 thread 的分支从刚同步过的 `origin/<默认分支>` 建出，改动对比的也是它；合并走 PR，所以没有“合并到基线”。推送后远端的 `origin/<分支>` 跟着更新。
- 其余同托管仓库：推送和开 PR 用 `push_branch`、`open_pull_request`，公开仓库第一次推送前问一次。thread 自己在远端用 `git push`（用远端的凭据）仍然属于要先问用户的操作。

### 仓库、PR 与 CI

上下文源是托管仓库时，thread 多五个工具：`repo_status`、`sync_branch`、`push_branch`、`open_pull_request`、`read_check_log`。

- thread 推送自己的分支、开 PR 不需要先问用户：只动它自己的 `ariadne/…` 分支，PR 可以关闭，合并由用户决定。公开仓库例外：第一次推送前进“需要我”问一次（带 `purpose` 的 Attention，按仓库区分）。同意对整个项目有效；同时想推送的 thread 共用一张卡片（`attention.joined`），卡片上列出所有在等的 thread，它们都显示为“等你”，回答后一起被唤醒；拒绝只对等这张卡片的 thread 有效，之后别的工作可以再问。用户关掉的 PR，`open_pull_request` 不会再开新的，thread 要问用户或报告受阻。
- 推送从不强推；远端分支变过的话推送被拒，提示 thread 用 `sync_branch` 取回远端的提交（只更新 `origin/*`，不动本地分支），合并 `origin/<分支>` 或 `origin/<默认分支>` 后再推送。PR 被 squash 合并后继续工作，先合并最新的默认分支，下一个 PR 只含新的改动。
- 开了 PR 的 thread 由仓库监视器定期（默认每分钟）读取 PR 和最新提交的检查，有变化才记一条 `pull_request.synced`。最新提交的检查失败时记 `checks.failed`，唤醒那个 thread 去读日志、修复、再推送；同一个提交只唤醒一次。连续第 3 次失败时，thread 被告知不要再试，报告受阻、说明试过什么，thread 进入 `blocked`、出现在“需要我”；之后的失败不再唤醒它，只继续计数。检查通过、PR 被合并或关闭，或用户在 thread 里发消息，就重新计数。协调器用 `message_thread` 仍能唤醒它，它推送后的失败照样不唤醒它，直到计数重来。PR 被合并或关闭时记 `pull_request.closed`，协调器收到说明。
- 界面在 thread 标题旁显示 PR 编号、检查状态，可以手动刷新；看板卡片上也显示。
- GitLab 上 PR 是 merge request：`PullRequestInfo.reference` 是 `!12`（GitLab 里 `#12` 指 issue），界面和工具结果都用它。草稿 MR 用标题前缀 `Draft:`。检查来自提交的 commit status（流水线里的 job 和外部 CI 报的状态），同名的只取最新一个；允许失败的 job 失败记为 `neutral`，手动 job 记为 `skipped`，都不算失败。日志是 job 的 trace，去掉终端颜色和折叠段标记，外部状态没有日志。`internal` 可见性对实例上所有登录用户可见，按公开仓库处理，第一次推送前同样先问用户。找 thread 分支的 MR 时只认本项目自己的分支，fork 里同名分支的 MR 不算。

### Issue

上下文源有 `tracker` 能力时（内置的 GitHub、GitLab 来源有），issue 是工作的上下文。

- 协调器和 thread 都能用 `list_issues`、`read_issue` 读 issue，用 `link_issue` 把 issue 关联到计划节点（或取消）；thread 只能关联到自己的节点。关联记成 `plan.issue_linked` / `plan.issue_unlinked`，立即生效，节点详情里列出、写明是谁关联的、能取消；agent 关联或取消时在它自己的对话里显示一行。用户也可以在节点详情里按编号关联。搜索只用词语：`repo:`、`org:`、`is:` 这类限定词和 AND/OR/NOT 会被去掉，结果也只保留本仓库的，令牌能读到的其他仓库不会混进来。删掉节点时它的关联一起删掉。节点的 thread 在系统指令里看到关联的 issue 编号，内容用 `read_issue` 读。
- issue 的标题、正文和评论是任何能提 issue 的人写的，工具结果里放进以内容哈希命名的数据块（`fenced()`，和项目记忆、AGENTS.md 同一套），并说明它们是信息不是指令。`read_plan` 和系统指令里只放编号，不放标题。
- 改 issue（`comment_on_issue` 评论、`set_issue_state` 关闭或重新打开）会通知别人、撤不回，只有 thread 能做，而且每次都要用户同意这一个改动：卡片里写着 issue 和完整的评论内容或关闭原因（带 `purpose` 的 Attention，按 issue、动作和内容的完整 SHA-256 区分，正在问的同样改动共用一张卡片）。用户同意后 thread 用同样的参数再调一次才真正执行。一次同意只用于一次改动：执行前记 `issue.writing`（带用到的 attentionId），成功后记 `issue.written`；之后同样的改动（比如关闭、重新打开后再关闭，或再发一遍同样的评论）要重新问，换了内容也要重新问。同意按项目区分。等同一张卡片的几个 thread 共用这次同意：其中一个做了改动，其余的会收到一条通知（谁做的、链接）；还没读到这条通知就再调用的，直接得到“已经做过”，不会被重新问，也不会再发一遍；读到之后再要同样的改动就是新的工作，照常重新问。改动正在进行时（同一进程里请求还没回来），再调用的 thread 被告知“正在做”，并加入这张卡片，结果出来后一起收到通知；正在进行的改动不会被当成“中途断掉”。如果记了 `issue.writing` 却没等到结果（Ariadne 中途停了，或者请求失败），这次同意就作废，thread 被告知先用 `read_issue` 核对改动是否已经生效，没有生效再调用才会重新问用户，不会盲目再做一次；卡片上其余的 thread 也会收到这条消息。拒绝的不做。thread 的对话里显示一行“在 … 下发表了评论 / 关闭了 …”，带链接。
- issue 请求和仓库请求用同一个服务端的 API 客户端，令牌只在服务端，thread 的命令读不到。
- GitLab：issue 编号是项目内的 `iid`；搜索用项目自己的 issues 接口，本来就只在这个项目里找；读 issue 时去掉 GitLab 自动写的系统备注（改标签、改描述之类），只留最新 20 条评论；关闭没有原因可选，`not_planned` 和 `completed` 都只是关闭（卡片上仍按 thread 给的原因显示）。

### 产物

产物有三种，各用对应的 dou-ui 包展示和编辑，存下来的内容就是那个组件的数据格式：

| 种类   | 内容                                                                         | 界面                                                         |
| ------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 文档   | Markdown                                                                     | `@dou-ui/editor` 块编辑器                                    |
| 画板   | `@dou-ui/flow` 的 `FlowDocument`，节点是白板的形状、便签、文字、笔迹和图片   | `DouFlowEditor` 加 `whiteboardKit()`                         |
| 仪表盘 | `{ dashboard, data, takenAt }`：`@dou-ui/dashboard` 的文档，加上格子读的数据 | `DouDashboard`，内置格子：统计数字、文字、表格、图表、透视表 |

- 仪表盘默认是静态快照：数据在写入时复制进来，每个数据源只是交回存下的值，不再请求；界面显示“数据截至”的时间。要更新就写入新的数据，`takenAt` 随之更新。
- 插件可以用 `registerDashboardSource({ kind, title, description, settings, fetch })` 提供实时数据。仪表盘带上 `source: { kind, settings }` 就成了“实时数据”：agent 用 `create_dashboard` / `update_dashboard` 的 `source` 建立时先取一次，之后 agent 用 `refresh_dashboard`、用户在仪表盘上点“刷新数据”时再取，取回的数据集替换同名的那些，存成一个新版本（`takenAt` 为当时），所以每个版本仍是一份能回放的快照。`list_dashboard_sources` 列出插件提供的来源；`update_dashboard` 给 `source: null` 就变回静态快照。来源所在的插件没加载时刷新会报错，已有的数据不受影响。模型给的 `settings` 先按来源的 schema 检查（只认声明过的字段、类型要对、必填要有，缺的用默认值），而且会原样记进事件日志，所以标了 `secret` 的字段不能在这里设，凭据放在插件自己的配置里。每次取数最多等 30 秒，取回的必须是一个对象、不超过 2MB，建立和刷新走同一套检查。
- 保存前 core 检查内容的形状（id 不重复、连线两端存在、格子读的数据源存在、只用注册过的类型），不合格的拒绝，错误原因回给 agent 修正。
- agent 不直接写坐标：画板工具收条目和连线，没给位置的条目放在它连出的条目右边，否则放在已有内容下方，再往下挪到不重叠；连线选两个条目相对的一边。修改按 id 合并，只改给出的字段，用户画的笔迹、贴的图片和挪过的位置都保留。仪表盘工具同样按 id 合并，新格子按顺序排进 12 列。
- agent 读画板时，笔迹和图片只列出 id 和位置，不带点阵和图片数据。
- 画板上粘贴、拖入或选取的图片先上传成文件，画板里只存它的地址（`/api/files/<id>`）。旧的画板或别处写进来的 data URL 图片，在保存时由服务端转成文件，内容里换成地址；历史版本保持原样。文件按项目和内容去重，存在数据库的 `files` 表里：它不是投影，重建投影不会丢，也从不删除，旧版本始终能显示。只收 PNG、JPEG、GIF、WebP、AVIF，单个最大 10 MB；不收 SVG（可以带脚本）。
- 图片地址不带令牌也能读（`<img>` 发不了请求头），靠随机的长 id 防猜，并且只允许本站页面引用（`Cross-Origin-Resource-Policy: same-origin`），内容不会变，浏览器可以一直缓存。上传要令牌。
- 每次保存是一个新版本，旧版本可以查看和恢复（恢复也是一个新版本）。改名也是一个新版本。
- 保存时带上起始版本号；期间别人保存过就拒绝，用户和 agent 不会悄悄覆盖对方的修改。
- 用户修改了 agent 写的产物，作者在下一轮会看到提示。
- 项目的产物总览按种类筛选、按标题和内容搜索，卡片上是内容的摘要（文档开头、画板里的文字、仪表盘的格子标题）、关联的计划节点和数据时间。摘要在产物保存时算好存进投影，列表不再读整份内容。用户也可以在这里新建空的文档、画板和仪表盘。

### 协调器与 thread 的消息

- thread 之间不直接通信。thread 的请求发给协调器，由协调器决定转发、合并还是驳回。上游节点的产出摘要随依赖自动交给下游。
- 协调器发给 thread 的消息在 thread 面板里显示为一条淡化、默认折叠的提示，点开可看全文。
- thread 发给协调器的消息不在任何面板展示；需要用户决定的事由协调器推到“需要我”。
- 用户在任何 thread 里发消息时，协调器同时做一次轻量分诊，thread 不用等它；如果有更合适的 thread 或者应该另开一项工作，协调器把请求转过去，并提醒当前 thread 用一句话告诉用户去了哪里。用户说“就在这里做”时，协调器以后对同类请求不再转交。分诊不需要转交时，协调器不说话。
- 消息只能由作者自己编辑。编辑是一条事件，界面显示“已编辑”，点开能看到编辑的原因和最初的原文；用户读过的消息被编辑后，下次打开时高亮一次。

### 对话里的界面块

协调器和 thread 用 `post_ui` 发一条带界面块的消息：文字写在前面，块排在下面。块的类型只有内置的一组，每种都映射到 dou-ui 的组件，不渲染模型写的脚本或 HTML，插件也不能注册新类型：

| 块        | 用途                                         | 组件                    |
| --------- | -------------------------------------------- | ----------------------- |
| `choice`  | 从 2 到 6 个选项里选一个，可以标推荐         | ChatSuggestions         |
| `confirm` | 对一个动作说同意或不同意，可附上要执行的内容 | ChatConfirm + CodeBlock |
| `form`    | 一次填几个值：文字、数字、单选、多选、开关   | Form                    |
| `table`   | 最多 200 行的数据                            | Table                   |
| `chart`   | 折线、面积、柱状、饼图                       | @dou-ui/chart           |
| `steps`   | 一组有先后的步骤和各自的状态                 | Steps                   |

- 每个块都在 `@ariadne/core` 的 `parseBlock` 里按类型检查，补齐省略的字段后才存进事件；不合规的块整条消息都不发，模型拿到具体哪一项不对。前端直接把存下的块交给组件。
- 选项、确认和表单是“提问”：一条消息最多一个，排在其他块后面。它就是一个 Attention（带 `messageId`），同时出现在消息里和“需要我”里，在哪边回答都一样。回答（`attention.answered`）也按块检查：选项只能选列出的，表单的值必须符合各字段的类型、必填和范围。回答以 `<user_answer>` 交给提问的会话并唤醒它；消息里的块原地显示答案。
- 提问可以撤回：用户没点块、直接打字回答了，或者问题已经不重要了，提问的会话用 `withdraw_ask` 撤回它（`attention.withdrawn`，带一句理由）。撤回的提问离开“需要我”，消息里的块只留下问题和“已撤回：理由”，之后再回答会被拒绝。用户在有未回答提问的对话里发消息时，模型在这条消息后面看到当时还开着的提问（`<open_questions>`，记在 transcript 里，所以可以重放），由它判断这条消息是不是回答了哪一个。只有提问的会话能撤回自己的提问；系统自己的确认（公开仓库的推送、改 issue、计划提议）不能撤回。
- 系统自己的确认（公开仓库的第一次推送、改 issue、计划的大改动）也是 `confirm` 块，只出现在“需要我”里（计划提议另有计划图上的提示条）。
- 表格、图表和步骤只用来展示；agent 自己的进度仍然写在待办清单里，不用步骤块。

### 附件与图片

- 用户在输入框里粘贴、拖入或点回形针选文件，选了就上传（`POST /api/projects/:id/files?for=message`），存进项目的 `files` 表，消息只记文件 id、名字、类型和大小（`message.posted` 的 `attachments`），一条最多 10 个。能发的是图片（PNG、JPEG、GIF、WebP、AVIF，最大 10 MB）和 UTF-8 文本（代码、日志、笔记，最大 1 MB；浏览器怎么叫它的类型不重要，按内容判断，存成 `text/plain`）。超过 5 MB 的图片在浏览器里先缩小再上传（长边最多 2560，JPEG），模型服务收不了更大的。画板仍然只收图片。
- 消息里的图片点开是大图预览，文本文件在新标签页打开。`/api/files/:id` 不需要令牌（`<img>` 带不上），地址是随机的，只允许同源加载，文本按 `text/plain; charset=utf-8` 和 `nosniff` 返回。
- 模型读到的是：文本文件的内容放在名字带内容哈希的数据块里（同 AGENTS.md 的做法，超过 10 万字截断）；图片跟在这条消息的文字后面。两种协议都直接发图片：Anthropic 协议放在消息和 `tool_result` 里，OpenAI 兼容协议放在消息的内容数组里，工具结果里的图片因为协议不支持，紧跟在这一步所有工具结果后面，作为一条注明来自哪次调用的用户消息。
- 图片在每次请求时才从 `files` 表读出、编码，transcript 里只有文件 id，所以事件日志不会因为图片变大，追踪视图也按文件显示。一次请求最多带最新的 20 张图片，更早的换成一句“之前看过”的说明；超过 5 MB 或模型服务不认的类型（AVIF）也只用文字说明。估算上下文时每张图片按 1600 token 算。
- “设置 → 模型”里每个模型有“看图片”开关，默认打开；关掉后（例如只收文字的模型）图片一律换成文字说明，模型知道有图但看不到。每一步记下这次有没有发图片（`turn.step` 的 `input.images`），追踪视图据此重建当时的请求。带图片的请求被拒、又不是可重试的错误时，报错会提示去关掉这个开关（`error.modelRequestImages`），不支持图片的服务（例如 DeepSeek）会一直这样拒绝。
- `read_file` 读到 PNG、JPEG、GIF、WebP（按扩展名，再核对文件头）时，把图片存进 `files` 并交给模型看（`tool.finished` 的 `files`）；超过 5 MB 的会让模型先缩小一份再读。读到不是文本的其他文件时说明是二进制，不再把乱码交给模型。工作区为此多了 `readBytes`（SSH 工作区用 base64 传）。

### 联网

- `fetch_url`：服务端抓取一个 http 或 https 地址交给模型。网页转成接近 Markdown 的文字（标题、列表、带地址的链接和图片、代码块），去掉脚本、样式、导航和页脚；纯文本、JSON、XML 原样给；PNG、JPEG、GIF、WebP 存进 `files` 当图片给模型看；其他类型说明读不了，thread 可以用 `run_command` 下载到工作区。一次最多 2 万字，用 `offset` 接着读；响应最多读 5 MB，30 秒没答完就放弃。
- 抓到的文字放在名字带内容哈希的 `web_page_…` 数据块里，标明是网站作者写的信息，不是指令。模型的系统指令也写明不照网页里的要求做、不把私密内容放进要抓取的地址。
- 只读公网：服务和 Ariadne 本身、本机其他服务、局域网在同一台机器上，网页不应借它摸到这些。解析出的地址只要有一个是回环、私有、链路本地、共享（100.64/10）、组播或未指定地址（IPv4 映射的 IPv6 地址按里面的 IPv4 算）就拒绝；198.18/15 不拒，开 fake-ip 模式的代理会把所有域名解析到这一段；重定向手动一跳一跳地跟，每一跳都重新检查，最多 5 跳；带用户名密码的地址不抓。不带 cookie 和任何凭证。检查和连接之间域名可能被换成别的地址（DNS rebinding），这一点没有防住；本机服务要访问时在 thread 里用 `run_command`。
- `web_search`：搜索由插件提供（`registerSearchProvider`），Ariadne 不内置哪一家；装了才有这个工具，装了几个时可以选用哪个。插件自己保管它的凭证（环境变量或它自己的配置），Ariadne 不经手；插件抛出的错误原文不交给模型，也不进事件日志，免得带出密钥。结果放在 `search_results_…` 数据块里。
- 协调器和 thread 都有这两个工具；协调器只用来快速看一眼用户给的链接，成规模的调研交给 thread。
- 接受的风险：能联网就可能被网页或文件里的指令诱导，把项目内容拼进地址发出去。系统指令要求不这样做，但挡不住；和上面的 DNS rebinding 一样，目前没有技术手段防住。

### 外部工具（MCP）

- 外部工具用 MCP 协议接入，Ariadne 自己实现客户端（`@ariadne/mcp`）：本机命令（stdio，每行一条 JSON-RPC）和 HTTP（每条消息一个 POST，回答是 JSON 或事件流，会话 id 跟着后续请求）两种连接方式。客户端只取工具、调工具，不向服务提供采样、根目录或追问，只回应它的 ping。
- 服务在“设置 → MCP”里配置，存在 `~/.ariadne/config.json` 的 `mcp.servers`：名称、标识（小写字母、数字和横线，最多 20 个字符，是工具名的一部分）、命令和参数（或地址）、工作目录、环境变量（或请求头）和每个工具的标记。环境变量和请求头的值当作密钥：只留在服务端，页面只拿到名字，留空保存就保留原值。不从仓库里读任何配置。
- 每个项目在“项目来源”的编辑表单里选用哪几个服务（`project.mcp.set`），选了的服务的工具才出现在这个项目的会话里，模型看到的名字是 `mcp__<标识>__<工具名>`。
- 每个工具有三种标记：“只读”直接调用；“要同意”（默认，没标过的工具都是这样）每次调用先出一张确认卡片，卡片上是完整的参数，出现在“需要我”里；“不用”不交给模型。协调器只拿到“只读”的工具，其余的只给 thread。
- 同意只对这一次、这组参数有效（`attention` 的 `purpose` 是服务、工具和参数按键排序后的 SHA-256），用掉时记一条 `mcp.called`，同样的调用再来就再问；参数换了也再问。拒绝后，同样的调用一直按拒绝处理，直到用户在这个 thread 里再写一句话。参数按缩进 JSON 超过 1 万字的调用直接拒绝，用户看不完的东西不让同意。
- 服务第一次被用到时才启动或连接，之后一直保持；设置改了（工具标记除外）就断开，下次用时重连。一轮开始时最多等还没连好的服务 5 秒，等不到这一轮就不带它的工具，连接在后台继续；启动加列出全部工具共用一个 60 秒的时限。失败的原因和本机命令最后写到 stderr 的内容显示在设置里，之后 1 分钟内不再重试，连续失败时间隔逐次加倍、最多 15 分钟，点“连接”立刻重试。HTTP 服务不认得会话了（404）不算失败：下次用时重新 `initialize`，当时那次调用服务没有执行，换新会话再发一次。服务说工具变了（`notifications/tools/list_changed`），下次用时重新列出。一次调用最多 5 分钟，用户停下这一轮时调用随之取消（`notifications/cancelled`）；单条消息超过 20 MB 就断开连接，进行中的调用立刻失败。
- 本机命令和 thread 的命令一样在沙箱里运行（见“工作区”）：看不到 Ariadne 的目录和浏览器配置，工作目录也不会让它们重新可见，工作目录不能设在 Ariadne 的目录里；环境变量从去掉服务端凭证的环境出发，再加上用户给的；它有自己的进程组，关掉或它自己退出时，它启动的进程一起结束。HTTP 服务不跟随重定向，请求头只发到用户填的地址。
- 工具返回的文字放在名字带内容哈希的 `tool_output_…` 数据块里，标明是工具写的信息，不是指令；图片存进 `files` 交给模型看；最多 5 万字。服务拒绝调用时写的理由也放进同样的数据块；协议版本对不上时不转述服务给的版本号。工具输出、错误信息和 stderr 里出现的环境变量或请求头的值（4 个字符以上）都替换成 `[secret]`，普通的值（比如 `NODE_ENV=production`）也一样，宁可多替换；连接失败时模型只拿到简短原因，stderr 只给用户看。确认卡片和设置页显示工具的真名，服务自报的标题只作补充。
- 接受的风险：服务和它的工具描述是用户自己选的，Ariadne 信任它们不说谎；“只读”是用户的判断，Ariadne 不核实。HTTP 服务还没有 OAuth 登录，需要令牌时填在请求头里。

### 项目记忆

项目记忆是项目的长期偏好和事实（“提交信息用中文”“接口在 packages/server”），项目里所有会话都遵守。

- 协调器在用户说出长期偏好、或确认了工作反复要用的事实时，用 `remember` 记下，用户收回时用 `remember` 改写或 `forget` 删掉；进度、计划和一次性的请求不进记忆。
- 记忆会进到每个会话的指令里，所以只有用户自己的话能改它：`remember` 和 `forget` 只在这一轮的输入里有用户的消息、对提问的回答或在 thread 里写的话时可用。只由 thread 汇报或转来的消息触发的一轮里，它们被拒绝；thread 读到的文件、日志和网页可能带着伪装成偏好的指令。thread 听到用户直接告诉它的偏好时在汇报里提一句，协调器向用户确认后再记下。
- 记忆以 `<project_memory_…>` 数据块出现在协调器和每个 thread 的系统提示里，带着条目 id，记下或改动后下一步就生效。每条存成一行（换行压成空格），显示时尖括号（包括全角的）也被替换，一条记忆伪造不出新的提示段落；数据块的标签名带着内容哈希的前 12 位（和 AGENTS.md 共用一套做法），内容写不出自身的哈希，也就闭合不了数据块，块内任何写法的裸标签名都会被拆成普通词；提示说明它们是关于工作的偏好，不能推翻工作方式和需要用户同意的规则。
- 协调器每次改动记忆，在它的对话里留一行说明（记下了什么、改成什么、删了什么），带“撤销”：撤销新增就删掉，撤销修改就恢复原文，撤销删除就加回来。
- 用户在侧栏“记忆”里查看、添加、修改和删除。每条最多 500 字，每个项目最多 50 条。每次修改是一个事件（`memory.saved`、`memory.removed`），记着是谁改的、撤销的是哪一次改动。

### 插件

模型协议、上下文源、仪表盘的实时数据来源和网页搜索由插件提供。插件有两种来源：随 Ariadne 一起发布的内置插件（`packages/plugin-*`），和用户本机路径上的第三方插件。

- 第三方插件在“设置 → 插件”里填绝对路径（可以用 `~/`）加载：路径是文件，或者是带 `package.json`（按 `exports["."]`、`module`、`main` 找入口）或 `index.ts` / `index.js` 的目录。入口的默认导出是插件（`definePlugin({ id, name, setup })`）。加载成功后路径写进 `~/.ariadne/config.json` 的 `plugins`，以后每次启动都加载；加载失败的不保存，原因显示在设置里。启动时加载失败的插件也列在设置里，带着原因。
- 插件的 `setup` 抛错，或者注册了别的插件已有的协议或上下文源，它注册过的东西全部撤回。移除插件时，它注册的协议和上下文源立即撤下；已经连上的工作区要到重启后才断开。改了插件代码要重启 Ariadne 才生效。
- 插件和服务在同一个进程里运行，能读到服务端的一切（包括令牌和 API Key），只应加载信任的代码。插件只从用户在设置里填的路径加载，不会因为项目的仓库里带了插件就自动执行：GitHub 仓库可能是别人的，打开一个项目不应让仓库里的代码进到服务端进程。Ariadne 的插件数据目录（`~/.ariadne/plugins/`，thread 的 worktree 和仓库的克隆都在这里）下的路径也会被拒绝加载。thread 在自己 worktree 里写的代码因此不会进到服务端进程；设置里的插件路径在沙箱里只读，thread 也改不了已加载插件的代码，见“工作区”。
- 插件只用 `@ariadne/plugin-sdk` 的类型（`import type`）时不需要安装任何东西；运行时用到 SDK 的函数的话，插件要自己带上依赖（或打包）。

## 能力

上下文源通过能力接入。上层只依赖能力，不依赖具体的 provider。

| 能力        | 典型提供者                   | 负责                                                                                                                                |
| ----------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `workspace` | 本地目录、SSH、remote daemon | 准备一个可写目录，并在其中提供 `fs` 与 `exec`；是 git worktree 时还提供 `branches`：改动、合并（托管仓库没有）、移除和列出 worktree |
| `repo`      | GitHub、GitLab               | 远端仓库、分支、PR、CI 状态与日志                                                                                                   |
| `tracker`   | GitHub、GitLab               | Issue 等任务记录                                                                                                                    |

`workspace`、`repo` 和 `tracker` 见上文“工作区”“仓库、PR 与 CI”和“Issue”。

## 分层

```
packages/
  i18n         文案与翻译，服务端和前端共用
  core         领域模型、事件存储与投影，不依赖 HTTP
  plugin-sdk   插件作者使用的类型与 definePlugin
  mcp          MCP 客户端：stdio 与 HTTP 两种连接
  sandbox      工作区沙箱：bwrap、unshare、sandbox-exec
  remote       远端工作区：脚本、worktree，SSH 和 daemon 共用
  daemon       远端运行的 ariadne-daemon
  agent        agent loop、调度、协调器与 thread 的工具、插件宿主
  plugin-*     内置插件：OpenAI 兼容与 Anthropic 两种模型协议，本地目录、GitHub 仓库、GitLab 仓库、SSH 远程目录与远程 daemon 上下文源
  server       本地 HTTP 服务、鉴权、事件流与用户设置
  web          Vue + dou-ui 的浏览器界面
```

- 依赖方向：`i18n` ← `core` ← `agent` ← `server`，`plugin-sdk` ← `plugin-*`、`mcp`、`agent`，`mcp` ← `agent`，`sandbox` ← `agent`、`daemon`，`remote` ← `plugin-ssh`、`plugin-daemon`；`web` 只依赖 `i18n`，以及 `core` 和 `plugin-sdk` 导出的类型。
- 存储：`bun:sqlite` 单文件，一张事件表加若干投影表；投影与事件在同一个事务里写入。
- 服务默认只监听 `127.0.0.1`，请求需要携带本地 token。
